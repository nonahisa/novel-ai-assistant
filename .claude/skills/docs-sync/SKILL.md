# 文書の整合と版の揃え方

CLAUDE.md から移した手順書（2026-09-17）。文章は移す前のまま。

## 書き方：決めたことを書き、考えた過程は書かない（作者の裁定、2026-09-28）

経緯や途中の見立てが文書に残ると、担当が読むたびに使用量を食い、古い見立てが今の決まりに見え、書きぶりが担当の報告にうつる。

- **設計書・プロンプト設計書・スキル**に書くのは、**決めたこと／なぜ（1〜3行）／測った数字（日付・モデル・件数）／守る決まり**だけ
- 書かないもの：決めるまでの経緯（「一度落ちたので直した」「担当の報告を読んで確かめた」）、担当の「迷った点」「懸念」の写し、途中の見立て（「〜と見ている」「〜かもしれない」）、作業の手順の語り。**経緯は引継ぎ書8章の日付つきの記録にだけ、短く残す**
- 「なぜ」は残す（CLAUDE.md の「コメントは『なぜ』を書く」と同じ）。**「なぜ」＝今の決まりの理由、「経緯」＝そこへ至った道筋**。経緯でしか説明できない理由（実際に起きた事故）は、1行で「〇〇が起きたため（日付）」とだけ書く
- 見立てが覆ったら、古い見立ての文は消す（取り消し線で残さない。残すなら引継ぎ書8章へ）
- 担当の報告を文書へ写すときは、上の形に書き直してから写す（報告の文をそのまま貼らない）
- **今ある分の整理は、2026-10-01 以降に計画して行う**（作者の選択「書き方を決め、10/1 以降に計画して整える」。設計書から順に、Sonnet が下書きし Opus が確かめる。段取りは引継ぎ書の同じ日の記録）

## 設計書を直したら、その場で整合性を取る

**設計書の章立て・番号を変えたら、参照している側も同じ作業の中で直すこと。** 章番号はコード注釈・引継ぎ書・プロンプト設計書・CLAUDE.mdから70か所以上参照されており、放置すると**別の節を指したまま気づかれない**。次の順で確かめる。

1. 参照の書き方は3通りある。**すべてを対象にする**
   - `設計書5.5.1` のように「設計書」が付く形
   - `5.5.1節` のように「節」で終わる形
   - `（5.5.1）` `5.4.1のハッシュ検証` のように、括弧や助詞だけの形（**見落としやすい**）
2. 変換は**元の状態から1回だけ**行う。2回に分けると、1回目で直した番号を2回目がもう一度変換する（旧5.5.1と新5.5.1は別の節を指すため、実際に壊した）
3. 版番号（`1.90.0`）や計算式（`* 1.1`）を巻き込まないよう、**旧設計書に実在した見出し番号と一致するものだけ**を置き換える
4. 直したあと、**全参照が実在する節を指し、内容も合っているか**を見出し一覧と突き合わせて確認する。番号が通っていても、指し先の内容が違っていることがある（実際に3件あった）
5. **節を足したら、冒頭の「## 目次」も作り直す。** 目次には章（`##`）と節（`###`）を、リンク付きで並べる。リンク先は VS Code のプレビューが見出しから作る規則に合わせる（全角の約物を落として空白をハイフンにする）

**番号の重複と、目次の抜け・切れたリンクは `test/unit/cross/designDocToc.test.ts` が止める**（設計書と引継ぎ書の両方）。2つのセッションが同時に節を足して `6.18` が2つできたことがあり、両方がコードから番号で参照されていた。目視では見つからない。

## 引継ぎ書は、冒頭だけで現状が掴めるようにする

`docs/進捗と引継ぎ.md` は**次のセッションが最初に読む文書**である。冒頭に「いまの状態」（版・テスト数・動くもの・触るときの注意）と目次を置き、そこだけで現状が掴めるようにしてある。

**日付順の作業記録は「8. 作業の記録」へ書き足す。** 前は「実装済み・未検証」という節に積んでおり、2,776行中2,151行がそこに入って「次にやること」が2,614行目まで押し下げられていた。新しい記録は8章の末尾へ足し、**1〜7章は現状を映すように直す**（記録を足すだけで済ませない）。

8章は古い順で、新しい記録は末尾に足す（途中や先頭へ入れない）。

**節を足したら `node scripts/handoverToc.mjs` で目次を作り直す。** このスクリプトは**目次だけ**を差し替える。文章には触らない。

**文書の文章を、スクリプトで組み立て直さないこと。** 以前は冒頭の「いまの状態」の表ごと組み立てるスクリプトを使い捨てで書いていた。表の中身（版・テスト数）がスクリプト側に固定されていたため、**走らせるたびに版が 0.6.9 へ巻き戻り**、5回分の修正のあいだ気づかれなかった。機械が触ってよいのは、機械にしか作れないもの（見出しから作る目次）だけである。

## 版は6か所で揃える

`package.json` の版に、次を合わせる。

| 文書 | 直す場所 | 見張っているテスト |
|---|---|---|
| `CHANGELOG.md` | 先頭の見出し | `showVersion.test.ts` |
| `README.md` | 「このリポジトリの版」（1か所。VSIX手順は動的取得なので触らない） | 同上 |
| `docs/設計書.md` | 冒頭の `version` 行 | 同上 |
| `docs/進捗と引継ぎ.md` | 「いまの状態」の表 | 同上 |
| **`docs/プロンプト設計書.md`** | 冒頭の `version` 行と**「（対象：…）」の行** | **`promptDocShape.test.ts`**（別のテスト） |
| **`src/mcp/version.ts`** | `SERVER_VERSION`（MCP サーバーが名乗る版。0.49.0〜） | **`mcpVersion.test.ts`** |

**プロンプト設計書は忘れやすい。** 見張っているのが `showVersion.test.ts` ではなく別のテストなので、ほかの4つを直して安心していると落ちる（2026-08-27に実際に落ちた）。`npm run check` は両方を走らせる。

**CHANGELOG の新しい版の項目は、書いたらスキル `yomiyasu` を通してからコミットする**（作者の指示、2026-10-15）。Marketplace の「Changelog」タブにそのまま出る、外の読み手向けの文だからである。通すのは新しく書いた項目だけで、過去の版の項目は書き直さない。担当に CHANGELOG を書かせるときも、指示にこの一文を写す。

設計書はかつて文書だけの通し番号（0.9）を振っていたが、拡張機能が 0.6.x を名乗っているのにどちらが新しいのか読んだ人に分からないため、拡張機能の版に合わせた。

## 設計書の節の整理を担当に頼むとき

上の「書き方」に合わせて、大きい節から1つずつ直す（2026-10-24 に30回で約6割。記録は引継ぎ書8章の【整理】）。指示は毎回同じ形で足りる。

- **1人1節、作業場（`isolation: "worktree"`）で。** 同じ設計書を同じ作業木で並べるとコミットが混ざる
- **やること**：経緯・覆った見立て・済んだ案を決まりと理由1行へ／重複を1か所へ／名前と動きを src のコードで grep して合わせる（コードは触らない）／作者の裁定は日付と言葉ごと残す／数値は残す（落とすなら理由）／測定の表は8章か docs/measurements に同じ数字があれば指し先へ／「未確認」は2章・実機確認リスト・e2e で合格済みなら改める
- **守ること**：その節の範囲だけ／`###` 以下の見出しの文言と順番は変えない（前後をスクリプトで比べる）／節の番号（「穴1」「①」）はコード・引継ぎ書から grep で指されていないか確かめてから外す／`## ` の章見出しがおかしくても動かさず報告／小節ごとに1コミット、行数はコミットの前に数える／版を上げない・push しない・テストは走らせない／**コミットの説明文のファイルは担当ごとに名前を分ける**（`msg_<節番号>.txt` など。2026-10-25 未明、2人の担当が同じ `msg.txt` を取り合い、説明文が入れ替わった）／日本語を `sed` で置き換えない（Edit・Write）
- **報告**：枝とコミット、小節ごとの行数、削った・寄せたもの、コードで直したもの、迷って残したもの、コードの疑い（ファイル:行）、節の外の切れた指し先。**「30〜40行以内」と指示に書く**（書かないと100行を超え、母艦の会話の使用量を食う。2026-10-25 に書き足してから目に見えて減った）
- **大事な前提の節（5.4・5.5・5.6 など CLAUDE.md が名指しする節）**：作者に一言断ってから頼む。指示に「決まりの中身は1つも変えない。決まりとコードが食い違えば、文書は直さず報告する」と書く（2026-10-25 の 5.4 で、3択の決まりとコードの食い違いが見つかり、作者が選んだ）
- **取り込み**：枝の取り込み方と作業場の依存の入れ方はスキル `team` のとおり（`git cherry-pick "$(git merge-base main <枝>)..<枝>"`／依存は `npm ci`、連結は張らない）。cherry-pick のあと `designDocToc`・`promptDocShape`・`showVersion` を走らせ、8章に【整理】を書いてから push。**疑いは記録だけ**にして、直すかは作者に選択肢で訊く
- **push を続けすぎない。** 走っている CI は次の push で止まるので、記録の push が続くとコードの変更が CI を最後まで通らない（2026-10-24）。配布の前は、コードを含む回が緑になったのを見る

## 担当の枝を合流させるとき

- 版の行がぶつかったら `node scripts/resolveAgentMerge.mjs` を使う（別の担当がいま作っている。名前だけ先に書く）。版以外の塊は自動で解かず、人が見る
- 合流のあと、引継ぎ書の版の表（11行目）の GitHub Release・Marketplace の欄が古い値に戻っていないかを必ず見る（2026-10-11 に2回戻った）

## 版を上げる

**変更を入れたら、同じ作業の中で版を上げる。**

| 変更 | 上げる桁 |
|---|---|
| **VSIX化を伴わない**（不具合修正・小さな追加） | **最下位（パッチ）** 0.6.0 → 0.6.1 |
| VSIX化を伴う配布（説明文の書き換え・機能のまとまり） | マイナー 0.6.1 → 0.7.0 |

版番号の散らばり先は上の「版は6か所で揃える」の表が正である。**揃え忘れると `test/unit/features/showVersion.test.ts`（プロンプト設計書は `promptDocShape.test.ts`）が落ちる**ので、`npm run check` で気づける。

版が動かないまま修正が積み上がると、作者が「ヘルプ → バージョンを確認」で見た版と実際の中身がずれる。
