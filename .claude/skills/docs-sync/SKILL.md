# 文書の整合と版の揃え方

CLAUDE.md から移した手順書（2026-09-17）。文章は移す前のまま。

## 書き方：決めたことを書き、考えた過程は書かない（作者の裁定、2026-09-28）

経緯や途中の見立てが文書に残ると、担当が読むたびに使用量を食い、古い見立てが今の決まりに見え、書きぶりが担当の報告にうつる。

- **設計書・プロンプト設計書・スキル**に書くのは、**決めたこと／なぜ（1〜3行）／測った数字（日付・モデル・件数）／守る決まり**だけ
- 書かないもの：決めるまでの経緯（「一度落ちたので直した」「担当の報告を読んで確かめた」）、担当の「迷った点」「懸念」の写し、途中の見立て（「〜と見ている」「〜かもしれない」）、作業の手順の語り。**経緯は引継ぎ書8章の日付つきの記録にだけ、短く残す**
- 「なぜ」は残す（CLAUDE.md の「コメントは『なぜ』を書く」と同じ）。**「なぜ」＝今の決まりの理由、「経緯」＝そこへ至った道筋**。経緯でしか説明できない理由（実際に起きた事故）は、1行で「〇〇が起きたため（日付）」とだけ書く
- 見立てが覆ったら、古い見立ての文は消す（取り消し線で残さない。残すなら引継ぎ書8章へ）
- 担当の報告を文書へ写すときは、上の形に書き直してから写す（報告の文をそのまま貼らない）
- **今ある分の整理は、下の「設計書の節の整理を担当に頼むとき」の形で進める**（作者の選択「書き方を決め、10/1 以降に計画して整える」。設計書から順に、Sonnet が下書きし Opus が確かめる）

## 設計書を直したら、その場で整合性を取る

**設計書の章立て・番号を変えたら、参照している側も同じ作業の中で直すこと。** 章番号はコード注釈・引継ぎ書・プロンプト設計書・CLAUDE.mdから70か所以上参照されており、放置すると**別の節を指したまま気づかれない**。次の順で確かめる。

1. 参照の書き方は3通りある。**すべてを対象にする**
   - `設計書5.5.1` のように「設計書」が付く形
   - `5.5.1節` のように「節」で終わる形
   - `（5.5.1）` `5.4.1のハッシュ検証` のように、括弧や助詞だけの形（**見落としやすい**）
2. 変換は**元の状態から1回だけ**行う。2回に分けると、1回目で直した番号を2回目がもう一度変換する（旧5.5.1と新5.5.1は別の節を指すため、実際に壊した）
3. 版番号（`1.90.0`）や計算式（`* 1.1`）を巻き込まないよう、**旧設計書に実在した見出し番号と一致するものだけ**を置き換える
4. 直したあと、**全参照が実在する節を指し、内容も合っているか**を見出し一覧と突き合わせて確認する。番号が通っていても、指し先の内容が違っていることがある（実際に3件あった）
5. **節を足したら、冒頭の「## 目次」も作り直す。** 目次には章（`##`）と節（`###`）を、リンク付きで並べる。リンク先は VS Code のプレビューが見出しから作る規則に合わせる（全角の約物を落として空白をハイフンにする）

**番号の重複と、目次の抜け・切れたリンクは `test/unit/cross/designDocToc.test.ts` が止める**（設計書と引継ぎ書の両方）。2つのセッションが同時に節を足して `6.18` が2つできたことがあり、両方がコードから番号で参照されていた。目視では見つからない。

## 引継ぎ書は、冒頭だけで現状が掴めるようにする

`docs/進捗と引継ぎ.md` は**次のセッションが最初に読む文書**である。冒頭に「いまの状態」（版・テスト数・動くもの・触るときの注意）と目次を置き、そこだけで現状が掴めるようにしてある。

**日付順の作業記録は「8. 作業の記録」へ書き足す。** 前は「実装済み・未検証」という節に積んでおり、2,776行中2,151行がそこに入って「次にやること」が2,614行目まで押し下げられていた。新しい記録は8章の末尾へ足し、**1〜7章は現状を映すように直す**（記録を足すだけで済ませない）。

8章は古い順で、新しい記録は末尾に足す（途中や先頭へ入れない）。

**節を足したら `node scripts/handoverToc.mjs` で目次を作り直す。** このスクリプトは**目次だけ**を差し替える。文章には触らない。

**文書の文章を、スクリプトで組み立て直さないこと。** 以前は冒頭の「いまの状態」の表ごと組み立てるスクリプトを使い捨てで書いていた。表の中身（版・テスト数）がスクリプト側に固定されていたため、**走らせるたびに版が 0.6.9 へ巻き戻り**、5回分の修正のあいだ気づかれなかった。機械が触ってよいのは、機械にしか作れないもの（見出しから作る目次）だけである。

## 版は6か所で揃える

`package.json` の版に、次を合わせる。

| 文書 | 直す場所 | 見張っているテスト |
|---|---|---|
| `CHANGELOG.md` | 先頭の見出し | `showVersion.test.ts` |
| `README.md` | 「このリポジトリの版」（1か所。VSIX手順は動的取得なので触らない） | 同上 |
| `docs/設計書.md` | 冒頭の `version` 行 | 同上 |
| `docs/進捗と引継ぎ.md` | 「いまの状態」の表 | 同上 |
| **`docs/プロンプト設計書.md`** | 冒頭の `version` 行と**「（対象：…）」の行** | **`promptDocShape.test.ts`**（別のテスト） |
| **`src/mcp/version.ts`** | `SERVER_VERSION`（MCP サーバーが名乗る版。0.49.0〜） | **`mcpVersion.test.ts`** |

**プロンプト設計書は忘れやすい。** 見張っているのが `showVersion.test.ts` ではなく別のテストなので、ほかの4つを直して安心していると落ちる（2026-08-27に実際に落ちた）。`npm run check` は両方を走らせる。

**CHANGELOG の新しい版の項目は、書いたらスキル `yomiyasu:yomiyasu` を通してからコミットする**（作者の指示、2026-10-15）。Marketplace の「Changelog」タブにそのまま出る、外の読み手向けの文だからである。通すのは新しく書いた項目だけで、過去の版の項目は書き直さない。担当に CHANGELOG を書かせるときも、指示にこの一文を写す。

### 機能の種から入れた機能には、議論の主な参加者の名前を載せる（作者の指示 2026-11-07）

Discord の #機能の種（受付リポジトリの Issue）から生まれた機能を入れたら、**CHANGELOG のその版の項目と GitHub Release のノート**に、議論の主な参加者の名前を載せる。

- **載せるのは、名前の掲載に同意した人だけ**（作者の裁定 2026-11-07「同意した人だけ載せる」）。CHANGELOG と Release ノートは公開され、あとから消しにくいため
  - 種を出した人：Issue の「名前の掲載：同意あり（〇〇）」の行の名前をそのまま使う。そこが「なし」「未確認（コマンドを使わない投稿）」でも、スレッドで訊かれて答えていれば「名前の掲載（議論）：同意あり（…）」の行に載るので、そこに名前があれば載せる。どちらにも無ければ載せない
  - ほかの主な参加者：機能を入れる前に、Discord のボットがそのスレッドで「載せてよい名前」を訊く（Discord のセッションへ頼む）。答えた人だけ、答えた名前で載せる。答えが無い人は載せない
  - **訊くのは種ごと**（作者の裁定 2026-11-07「種ごとに訊く」）。前の種の答えは引き継がない。訊かずに済ませるのは、その種を `/機能の種` で出した人が入力欄で認めたときだけ。同じ種で2度は訊かない
  - 名前は、本人が答えた形のまま書く（Discord の表示名やアカウント名に置き換えない）
- 書き方：その機能の行の末尾に「（#機能の種より。提案：〇〇さん、議論：△△さん・□□さん）」。同意した人が一人もいなければ「（#機能の種より）」だけ
- 種と機能の対応は、受付リポジトリの Issue の番号で控え、引継ぎ書8章の記録にも Issue の番号と載せた名前を残す
- 「主な参加者」の範囲（種を出した人のほか、案の中身を変えた発言をした人）は、機能を入れる担当が Issue とスレッドを読んで選び、迷ったら母艦へ送る

### 不具合の報告から直したものには、報告した人の名前を載せる（作者の決定 2026-11-14）

Discord の #不具合の報告（受付リポジトリの Issue。種別：不具合）から直したものは、**CHANGELOG のその版の項目と GitHub Release のノート**に、報告した人の名前を載せる。Discord の「#更新のお知らせ」が Release ノートを読んで流す。

- Issue には、ボットが次のどれか1行を書く：「- 名前の掲載：同意あり（〇〇）」「- 名前の掲載：なし」「- 名前の掲載：未回答」「- 名前の掲載：未確認（コマンドを使わない投稿）」
- **載せるのは「同意あり」の人だけ。** 名前は「同意あり（…）」の括弧の中をそのまま使う（Discord の表示名に置き換えない）
- 同じ不具合を別々に報告した人がいれば、それぞれの Issue の同意を見る
- 書き方：その直しの行の末尾に「（#不具合の報告より。報告：〇〇さん）」。2人以上なら「報告：〇〇さん・△△さん」。同意した人が一人もいなければ「（#不具合の報告より）」だけ（並びの決まりは上の機能の種と同じ）
- 不具合と直しの対応は Issue の番号で控え、引継ぎ書8章の記録にも Issue の番号と載せた名前を残す

### Release ノートに「試してほしいこと」を置く（作者の決定 2026-11-14）

Discord の「#試してほしいこと」が GitHub Release のノートを読んで流す。

- ノートの `---` の線より上に、見出し `## 試してほしいこと` を置き、下に「- 」の箇条書きで2〜3件書く
- 1件は、会員が1つの操作で試せて、できたかどうかが見て分かるものにする。メニューの場所は最初の一押しから書く
- 試すことが無い版は、見出しごと書かない
- **CHANGELOG には入れない。** Release ノートだけ
- ノートのほかの部分と同じく、yomiyasu を通す（下の「yomiyasu の当て方」）
- 試した人の名前は載せない

### yomiyasu の当て方（このリポジトリの決まり）

yomiyasu は外部の MIT のスキル（https://github.com/nanaism/yomiyasu）。**2026-10-25 からプラグインとして入れている**（作者の依頼「マーケットプレースからインストールすると自動的にバージョンアップできる」）。`~/.claude/settings.json` の `extraKnownMarketplaces.yomiyasu.autoUpdate: true` で自動更新。名前は `yomiyasu:yomiyasu`（`yomiyasu` だけだと Unknown skill）。前はリポジトリの `.claude/skills/yomiyasu` に写して持っていた（v2.2.2）が、更新のたびに写し直す手間をなくすため外した。

- 当てるのは**外の読み手が読む説明文だけ**（作者の裁定、2026-10-04「マーケットプレースやGithubの説明文のみで考えています」。2026-10-15 に CHANGELOG を加えた）：`README.md`、`package.json` の `description`、GitHub のリポジトリの説明、GitHub Release のノート、`CHANGELOG.md` の新しい版の項目、Discord サーバーに貼る文章（ボットのリポジトリの `content/server-texts.md`。作者の指示 2026-10-23）、**共通設計書**（`docs/共通設計書.md`）と **Android の詳細設計書**（作者の裁定 2026-10-27「共通設計書にも当てる」。拡張機能の設計書・プロンプト設計書には今までどおり当てない）
- **当てないもの**：作者への返事・報告、設計書・引継ぎ書、画面の文言、プロンプト、コード内のコメント、小説の本文
- README の決まり（やり方とできることだけを書く。理由・経緯は書かない。キャッチコピーと「テスト中」は残す）が先に立つ。CHANGELOG も、何が変わったか・どう使うかだけを書く
- 検査のスクリプトは Python 3 が要る（2026-10-25 に作者の指示で Python 3.14 を入れた。本体は `%LOCALAPPDATA%\Programs\Python\Python314\python.exe`。入れる前から開いていたシェルでは `python` がストア版の入口のままなので、この道を直に書く）。PowerShell からは `$env:PYTHONIOENCODING = "utf-8"` を先に置く
- スクリプトの置き場は版ごとに変わる（`%USERPROFILE%\.claude\plugins\cache\yomiyasu\yomiyasu\<版>\scripts\`）。毎回いちばん新しい版を引いて呼ぶ：

```powershell
$y = (Get-ChildItem "$env:USERPROFILE\.claude\plugins\cache\yomiyasu\yomiyasu" -Directory | Sort-Object { [version]$_.Name } | Select-Object -Last 1).FullName
$env:PYTHONIOENCODING = "utf-8"
& "$env:LOCALAPPDATA\Programs\Python\Python314\python.exe" "$y\scripts\yomiyasu_check.py" run --stdin --stance=説明
```

- `run` は原文（`--source`）か資料（`--material`）が要る。Release ノートは CHANGELOG の該当版や `git log --format=%B` を資料に渡す。検査の記録は `.yomiyasu/`（git には入らない・配布物からは `.vscodeignore` で外してある。2026-10-25 に一度 VSIX へ紛れ込んで検証が止めた）
- 清書した文を確かめる `--final` は `--stdin` と一緒に使えない。パイプで流すときは `--final -` と書く（2026-11-13、v0.152.x の Release ノートで止まった）。`--material` などに渡すファイルは作業フォルダーの中に置く（外の道は断られる）
- 補助スクリプトのフック（`yomiyasu_hook.py`）は登録しない

設計書はかつて文書だけの通し番号（0.9）を振っていたが、拡張機能が 0.6.x を名乗っているのにどちらが新しいのか読んだ人に分からないため、拡張機能の版に合わせた。

## 設計書の節の整理を担当に頼むとき

整理は 2026-10-26 に済んだ（記録は引継ぎ書8章の【整理】）。また頼むときの決まり：

- **1人1節、作業場（`isolation: "worktree"`）で。** その節の範囲だけ直し、`###` 以下の見出しの文言と順番は変えない。決まりの中身は変えず、コードと食い違えば文書は直さず報告する（5.4・5.5・5.6 など CLAUDE.md が名指しする節は、作者に一言断ってから）。日本語を `sed` で置き換えない
- コミットの説明文のファイルは担当ごとに名前を分ける（`msg_<節番号>.txt` など。同じ `msg.txt` を取り合って入れ替わった）
- 報告は「30〜40行以内」と指示に書く（書かないと100行を超え、母艦の会話を食う）
- 取り込み（スキル `team` のとおり）のあと、`designDocToc`・`promptDocShape`・`showVersion` を走らせ、8章に【整理】を書いてから push する。疑いは記録だけにして、直すかは作者に選択肢で訊く

## 担当の枝を合流させるとき

- 版の行がぶつかったら `node scripts/resolveAgentMerge.mjs` を使う。版以外の塊は自動で解かず、人が見る
- 合流のあと、引継ぎ書の「いまの状態」の版の行の GitHub Release・Marketplace の欄が古い値に戻っていないかを必ず見る（2026-10-11 に2回戻った）

**push を続けすぎない。** 走っている CI は次の push で止まるので、記録の push が続くとコードの変更が CI を最後まで通らない（2026-10-24）。配布の前は、コードを含む回が緑になったのを見る。

## 版を上げる

**変更を入れたら、同じ作業の中で版を上げる。**

| 変更 | 上げる桁 |
|---|---|
| **VSIX化を伴わない**（不具合修正・小さな追加） | **最下位（パッチ）** 0.6.0 → 0.6.1 |
| VSIX化を伴う配布（説明文の書き換え・機能のまとまり） | マイナー 0.6.1 → 0.7.0 |

版番号の散らばり先は上の「版は6か所で揃える」の表が正である。**揃え忘れると `test/unit/features/showVersion.test.ts`（プロンプト設計書は `promptDocShape.test.ts`）が落ちる**ので、`npm run check` で気づける。

版が動かないまま修正が積み上がると、作者が「ヘルプ → バージョンを確認」で見た版と実際の中身がずれる。
