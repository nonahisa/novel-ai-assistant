# AIの出来を比べる（比べの手順）

2026-09-25〜26 の誤字脱字の比べで固めた手順（引継ぎ書8章「【測定】2026-09-26：誤字脱字の比べの続き」）。作者の依頼「推敲等、他も同じ手順で測り、不具合が出たらなおしてください」で、ほかの機能にも同じ形を当てた。

## 手元のAIの札（**最初に読む**。重なると数字が全部狂う）

**2026-09-25〜26 に2度重なった。** 担当ごとに別の場所に札を作っていた・札を見ない統合テストが本物の Ollama へ送っていた。重なると、ほかのモデルが追い出されて読み込み直しになり、時間が2〜3倍に膨らむ（e4b 124秒→331秒、31b 651秒→1094秒）。

- **札の場所は、担当を立てるリーダーが指示に絶対パスで書く。** 同じ時期に動く担当が全員同じ1つを使う。指示に無ければ `%TEMP%\novelai-ollama.lock`（機械で1つ）を使う。**担当が自分で場所を決めない**（相対パスや自分の台の下に作らない）
- 札はフォルダー。`mkdir` で作れたら自分のもの。`owner.txt` に担当名・モデル・時刻を書く。作れなければ30秒おきに待つ。**90分より古い札は放置とみなして外してよい**
- **1モデル撃ち終えるごとに返す**（ほかの担当が待っている）
- 撃つ前に `/api/ps` を見て、自分以外のモデルを `keep_alive:0` で外す。温めて（同じ num_ctx で1回）から測る。`size`・`size_vram` を記録する（CPU へはみ出した量が時間を決める。26b の size は MoE のため小さく出るので比べない）
- 測っている間も `/api/ps` をときどき見て、**自分の num_ctx と違う設定で載っているモデル**があれば、札の外の誰かが使っている。記録に残す
- 統合テスト・単体テストは本物の Ollama へ送らない（作り物のAIで閉じる。0.89.18 で直した）
- 時間は参考。ほかの担当の CPU 負荷が乗るので、比べの主役は当たりと誤検出

## MCP サーバーを起こすとき

- 本体の `dist/mcp-server.mjs` を使う。**必ず環境変数 `NOVELAI_GLOBAL_STORAGE` を scratchpad の下のフォルダーに設定してから起こす。** 設定しないと、束の置き場（`dist/`）を保管庫とみなして `dist/local-ai/` に札の台帳を書き、**配布物に紛れる**（2026-09-26、0.89.14 の VSIX に入り、出口の許可リストが止めた）
- 起こす前に本体で `npm run build`、`mcp.version` で版を控える

## 台と正解

- 作品は**作者の作品の写し**（scratchpad の下）。作者の原稿（`Documents\novel\`）・確認用コピーは読むだけ。**仕込み（わざと入れる誤り・食い違い）は自分用の写しにだけ**
- **正解は Claude が本文を読んで作る。** 「確実」と「たぶん」を分ける。**作ってから測る**（測った答えを見て正解を動かさない。動かすなら理由を記録）
- 本文を含む中間生成物はリポジトリの外（scratchpad）へ

## 撃ち方（製品と同じ道）

- MCP の `novel.run`（runner ollama）で撃ち、**検算（validate）まで通す**。`prompt` だけ呼んで検算を通さない測り方は、製品に無い不具合を見つけたことになる（CLAUDE.md の失敗5）
- さくらは製品の `sakuraProvider` を通す（実接続の試験の形でもよい）。検算は製品のもの
- **Claude が内部AIを代わった場合**も並べる：runner claude で prompt を受け取り、答えを書いて `novel.validate` へ戻す
- 答えの控え（キャッシュ）が効いて撃たずに返らないよう、写しの `.aiwriter\cache` を消すか版で分ける

## 採点

- **見逃しと誤検出の両方**（片方だけでは何も指摘しない実装が満点になる。CLAUDE.md の失敗2）。画面に出る分（確信度で隠れるもの）も分ける。失敗した話・空の応答・形の崩れも数える
- **誤検出は1件ずつ見直す。** 本当は正しい指摘（正解の漏れ）なら正解へ足して採点し直す（理由を記録）。**わざとの表記**（口語・崩し・方言）は作者の意図なので誤検出。迷ったら Fable に根拠の本文を添えて訊く
- **検算が落とした当たり・検算が通した誤り**を数える（誤字脱字では、前後の句を抱えた案を落としていた・当てると本文が壊れる案を通していた）
- 同じ条件でも揺れる（さくらは温度0でも揺れる）。差が数件なら揺れの範囲と書く

## 頼み方の工夫を比べる

- 共同注意（先に照らす所を揃える段）・英語で考えさせる、などの工夫は、**gemma4:26b と さくら Kimi-K2.6 の2つで**、工夫なしと並べる。**製品へ入れるのは両方で良くなったときだけ**
- これまでの結果：共同注意は矛盾検知で効き、誤字脱字では両方で悪化（26b 12件→0件）。段を足すと答えの量を食い、形が崩れることがある
- 20B で頼み方を分ける仕組み（`useSmallModelTypoPrompt`・`contradictionSpeechCheck`）がある。分けるほうが良いと測れたら同じ形で分ける

## さくら

- 作者の許可は**月ごと**に数える（作者 2026-09-26「なお月間です」）。2026年9月は2,000回まで（09-25 に1,000回、09-26 に「あと1000回認めます」で1,000回足した）。翌月からの枠は、その月に作者へ確かめる。**リーダーが担当ごとに上限を指示に書く**。空の応答・失敗も1回と数える
- 鍵は環境変数 `SAKURA_AI_ACCOUNT_TOKEN` からだけ読み、値を表示・記録しない

## 見つけた不具合

- 製品の不具合（検算の穴・頼み方・答えの読み方）は、スキル `implement` の規則で直す（先に再現テスト。プロンプトを変えたら `_VERSION`）。**直したら同じ台で測り直して効き目を数える**
- 方針の判断が要るものは直さず報告（作者に諮る）
- **既定のモデル（`RECOMMENDED_CHAT_MODEL`）は変えない**（作者の裁定）。機能ごとの向くモデルの案内は、測った結果と日付に合わせて直してよい
