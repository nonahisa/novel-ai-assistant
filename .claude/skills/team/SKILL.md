# 役割分担

**リーダー（この会話を進めているモデル）が Fable でも Opus でも、分担は同じ。** 違うのは1点——**リーダーが自分で手を動かしてよい大きさ**。

| 役割 | 担当 | 具体的に |
|---|---|---|
| 全体計画・判断・**デバッグ**・作者とのやり取り | **リーダー** | 何を作るかの設計、作業の分割と順序、**作者への判断の依頼（選択肢で）**、**原因の分からない不具合の調査**、エージェントの結果の**最終確認** |
| **本流への合流・コミット・配布** | **リーダーだけ** | 担当の枝の取り込み（**競合はリーダーが解く**）、`main` へのコミットと push、版上げの采配、GitHub Release・Marketplace |
| 実装 | **implementer（Opus）** | 固まった計画のコード化。新規実装・修正・リファクタリング。**画面に出る文言の直しも実装**（文字列は `src/` にある）。**貼り込み係（別リポジトリ）のコードと README もここ**。実装で決まった細部を設計書の該当節へ追記するところまで |
| レビュー（バグ探し・簡素化） | **general-purpose を `model: "opus"` で** | 観点ごとに1エージェント。**`/code-review` スキルは使わない**——中の検出エージェントは Fable で動き、1回で200万トークン超を食う（2026-08-29に実測） |
| 走査・調査 | **Explore／general-purpose を `model: "sonnet"` で** | 文書の総点検、コードの横断検索、ログの読み取り。**`model` を省くとリーダーを継承する** |
| 文書の機械的な更新 | **light-tester（Sonnet）** | 版の揃え・CHANGELOG・引継ぎ書の記録・実機確認リストの項目・`handoverToc` の再生成。**リーダーは箇条書きの材料を渡し、最終確認だけ行う**。**`src/` と別リポジトリは触らない** |
| 軽いテスト | **light-tester（Sonnet）** | テストの実行と結果整理、期待値の更新、既存パターンを写した追加ケース、**実装の差分と報告の照合** |
| 使い終わったものの片づけ | **cleaner（Sonnet）** | 担当の作業場と枝（連結を外してから）、テスト用に足した右の枠の起動設定と一時の写し、残った試験用のブラウザ版・VS Code・MCP のプロセス。**取り込み・配布・測定が終わるたびに頼む**（作者の依頼、2026-09-25）。原稿・確認用コピー・保管庫は消さない |
| **AIの比べ（測定）** | **3つに分ける**（作者の裁定、2026-09-26） | ①**正解作り・誤検出の見直し**は implementer（Opus）かリーダー。②**台本を回す・札を待つ・採点**は light-tester（Sonnet）。③**見つけた不具合の直し**は implementer（Opus）。**1人に「測って、直して」を丸ごと任せない**（09-26 に4人へ丸ごと任せ、1人約50万トークン、札待ちの2時間も Opus が見張った）。手順はスキル `ai-bench` |
| **実機確認** | **ノートPCのセッション（別の Claude）** | 画面を押して確かめる（**確認用コピーの作品だけ**）。結果は `field-check-*` の枝で送り、リーダーが取り込む。**見つけた不具合は直さず**、再現手順・画面の文言・ログを揃えてリーダーへ渡す（メモ「実機確認の分業」） |

エージェントの定義は `.claude/agents/` にある。

## 振り分けの早見（2026-09-23 に食い違いが出たもの）

| 頼みたいこと | 担当 |
|---|---|
| 画面・通知・パネルの文言を直す | **implementer**（`src/` の文字列。light-tester には頼まない） |
| 貼り込み係のコード・README・画面の文言 | **implementer**（別リポジトリ。light-tester は触らない） |
| 版の揃え・CHANGELOG・引継ぎ書・実機確認リスト | light-tester |
| 担当の枝の取り込みと競合の解消 | **リーダー** |

## コミットの約束

- **`main` に書くのはリーダーだけ。** コミットは必ずパス指定（`git commit -m … -- <ファイル…>`）か、索引の中身を確かめたうえでの素の `git commit`（合流の確定・並行の担当の未ステージがあるとき）
- **implementer**：別の作業場（worktree）で動かすときは、**その枝にコミットしてよい**。`main` の作業木で動かすときはコミットしない（名指しでステージまで）
- **light-tester**：**指示にコミットするパスが書いてあるときだけ**、そのパスでコミット・push する。書いていなければステージもしない
- **作者が書き込み中のファイル**（例：`docs/メニュー名の短縮案.md` に○×を付けている間）は、誰もステージしない

## リーダーが自分でやってよい大きさ

| リーダー | 自分でやってよいもの | 理由 |
|---|---|---|
| **Fable** | 数行の修正、設定値、短い文書の編集、1〜2回の `grep`/`Read`。**それ以上は投げる** | **週の上限で Fable だけが偏る**（2026-08-29に79%）。Fable の値打ちは判断にあり、打鍵に使うと判断の分が減る |
| **Opus** | 上に加えて、**5ファイル未満・300行未満**の実装なら自分でよい | implementer も Opus なので、投げる理由は使用量ではなく**リーダーの文脈を守ること**（読む量が増えると判断が鈍る）と**並行できること** |

**どちらのリーダーでも投げるもの**：読む量の多い仕事（レビュー・走査・文書の総点検）、書く量の多い仕事（文書の機械的更新）、テストの往復。**分業は儀式ではない**——数行の修正をエージェント経由にすると、かえって高くつく。

## 投げ方

- **エージェントは会話の文脈を持たない。** 指示には「触るファイル・直し方・確かめ方・やらないこと」まで書く。「さっきの方針で」は通じない
- **implementer へ投げるのは方針が固まってから。** 原因調査の途中で投げると、エージェントが独自の推測で直し始める
- **implementer には「スキル `implement` を読んでから」と指示に書く。** CLAUDE.md には要点しか残していないので、全文はスキルでしか読めない
- **互いに独立な作業は並行して投げる。** ただし**同じファイルを触る作業は並行させない**（後勝ちで消える）。CLAUDE.md や引継ぎ書を2つのエージェントが同時に触らないよう、担当を分ける
- **並行させるときは、それぞれ別の作業場（`isolation: "worktree"`）で。** 作業場を分けても、**同じファイルを触れば取り込むときにぶつかる**（2026-09-23：確認画面の部品 `views/notify.ts` を2つの担当が別々に変え、4ファイルで競合した）。指示に「触ってよいファイル」と「ほかの担当が触っているので触らないファイル」を書き、重なるものは順番に回す
- **指示・報告・思考はすべて日本語**（担当にも「思考も報告も日本語で」と書く）。**画面に出す文言には開発中の内輪の呼び名（「母艦」など）を使わない**と書く
- **エージェントにも落とし穴を伝える**（スキル `shell-safety` の要点を指示に写す）。知らないと、日本語を `perl` に通して UTF-8 を壊す
- **手元の Ollama を使う担当を2人以上立てるときは、札の絶対パスを全員の指示に同じ1つで書く**（スキル `ai-bench`）。書かないと担当ごとに別の札を作り、同時に叩いて時間の数字が狂う（2026-09-25〜26 に2度）
- リーダーが待つだけの間は、次の作業へ進む（loop の待ち間隔は最大の60分にする）

## 検収

- 「できました」の報告を鵜呑みにしない。**検査の実行結果（件数）が報告に入っているか**を見る。入っていなければリーダーが走らせ直す
- implementer には**自己点検の要約と差分の要点**を報告させ、リーダーは要約と要所だけ読む
- 文書の移設・置換は、**落ちた行が無いことを機械で照合**させる（元の本文行が移した先に全部あるか）
- **版上げの采配とコミットはリーダーが行う**（文書の書き込みそのものは light-tester に渡してよい）。設計の判断（設計書の新節・方針の変更）はリーダーが書く

## 使用量の偏りを防ぐ

リーダーが自分で読む・書くのは「設計」「判断」「最終確認」「コミット」に絞る。**エージェントの結果を全部読み返さない**——要約と差分の要点で足りるように、報告の形を指示に書いておく。
