# 実装のやり方

**開発者は小説の作者本人で、プログラマではない。** 技術的な説明は要るが、専門用語だけで押し切らず、**なぜその判断をしたのかを日本語で**書く。コメント・UI文言・報告はすべて日本語。

## 手順

1. **方針が固まっていることを確かめる。** 触るファイル・直し方・確かめ方・やらないことが指示に無ければ、推測で始めずにリーダーへ聞き返す（原因の分からない不具合の調査はリーダーの仕事）
2. **不具合の修正は、先に再現テストを書く**（落ちることを見てから直す）。新機能は、何を確かめれば「動いた」と言えるかを先に決める
3. 置き場所はスキル `codebase-map` で確かめる。**`views`/`features` → `core` → `models` の向きを逆流させない。** `core` に `vscode` を持ち込むと `mcpReach.test.ts` が落ちる
4. 文字列やスクリプトを扱う前にスキル `shell-safety` を見る（日本語・バッククォート・NUL で実際に壊した）
5. 書いたら `npx tsc --noEmit -p tsconfig.json` → 該当テスト → **`npm run check`**（型検査＋単体テスト＋本番ビルド）。**「ビルドが通った」は「動く」ではない**——通ったことを確認したら、次に「何を確認したことになるのか」を問う
6. **版を上げる**（VSIX化を伴わなければパッチ）。揃える6か所はスキル `docs-sync`。**プロンプトを変えたら `_VERSION` も上げる**
7. **実装で決まった細部を、設計書の該当節へ追記する**（新しい節や方針の変更はリーダーが書く）。引継ぎ書8章の記録はリーダーが采配する
8. **`git add -A` を使わない。** 触ったファイルだけを名指しでステージする。コミットはリーダーが行う

## 報告の形（implementer → リーダー）

リーダーは要約と要所だけ読む。次を箇条書きで：

- 触ったファイルと、それぞれ何を変えたか（1行ずつ）
- **検査の実行結果（件数）**——`npm run check` の Test Files／Tests。入っていない報告は受け取ってもらえない
- 自己点検：実装ルール1〜7のどれに触れたか、どう守ったか
- 判断に迷った点・指示と違えた点（**変えずに報告**したものも含む）
- 設計書へ追記した節

## テストの決まり

単体テストは Vitest、VS Code 統合テストは `@vscode/test-electron`。

```powershell
npm run test:unit        # 単体テスト
npm run test:integration # VS Code 1.90.0 の Extension Host（ELECTRON_RUN_AS_NODE を先に外す）
npm run test:ollama      # 任意。ローカル Ollama 実接続
npm run check            # 型検査＋単体テスト＋本番ビルド
```

- **単体テストが通っても実データで動かないことがある。** 設計上の制約（上書き禁止など）を知らずに書いたときに起きる。実際に動かして確かめるまで「できました」と言わない
- **AIの機能は、見逃しと誤検出の両方を測る。** 片方だけでは、何も指摘しない実装が満点になる
- **指示の言葉が答えの中身として返ってくる**（`"suggestion": "空文字"`）。新しくプロンプトへ書く指示語は、そのまま返ってくる前提で検査を書く
- **実接続の測定は、製品と同じ検証を通す。** 迂回すると、製品に無い不具合を見つけたことになる

## 絶対に守る実装ルール

### 1. 作者の原稿を壊さない

これが最優先。以下を必ず守る。

- **AI修正を適用する前に、読み込み時のハッシュと現在のハッシュを照合する。** 不一致なら適用を中止する（`textFile.ts` の `writeTextFilePreservingFormat` の `expectedHash`）。AI応答には数十秒かかり、その間に外部ツールで編集される可能性がある。
- **文字コード・改行コードを保持して書き戻す。** UTF-8/LFに勝手に変換しない。
- **変更箇所のみを置換する。** ファイル全体を再生成しない。
- **Gitの競合マーカー（`<<<<<<<`）を含むファイルはAI処理をブロックする。**

### 2. 作者が書いたデータを上書きしない

- `authorNotes`、`exportNote` は絶対に自動更新しない。
- `autoGenerated: false` のレコードは、登場話数の追記以外行わない。
- `authorLocked: true` の呼称エントリは変更しない。
- 既存の記述と食い違う情報が出たら、**話数で扱いを分ける**（設計書6.18）。
  - **違う話の値どうし** → 作中で変わったと読み、`changes` に両方を残してレコード本体には最後の話の値を入れる。作者には聞かない
  - **同じ話の中で矛盾** → 両方が同時に正しいことはないので、`conflicts` に記録して作者に判断させる
  - **話数の分かる値が1つしか無い** → 前後を決められないので `conflicts` に残す。ここを緩めると、作者が手で書いた値をAIの読みが押し流す
  - **読み仮名は畳まない。** 作中で変わらない項目なので、違う値はAIの読み違いである
  - どの経路でも**値は消えない**。畳んだ件数は抽出の完了報告に出す（黙って書き換えたことにしない）
- 壊れたJSONを勝手に修復・上書きしない。エラーを表示して止める。
- **`atomicWriteFile` には3つの経路があり、「必ず失敗する」のは1つだけである**（2026-08-29に実態に合わせて書き直した）。
  - ①**指定なし**：一時ファイルへ書いてから、正規の場所へ**上書き**で置き換える。**回復先への退避は無い。** `SettingsStore` 系（能力・場所・組織・世界観・伏線）、承認待ち、チャンクキャッシュ、各種履歴が使う。外部変更の防御は**呼び出し側のハッシュ照合**（`SettingsStore.assertSaveAllowed`）が担う。`設定/` はGit管理下なので、送信済みの版は「復元」で戻せる
  - ②`mode: "create"`：新規作成だけ。既にあれば失敗
  - ③`mode: "replace"`＋`expectedHash`（`replaceGuarded`）：**必ず失敗する**（正規ファイルへ触れずに提案を回復パスへ残す設計）。これを「上書きの経路」と思って書いた保存処理が3か所とも失敗した実績がある
  - **「回復先へ退避（`.novelai-recovery`、5世代）→ 新規作成」をしているのは、人物（`CharacterStore.saveOrUpdate()`。`save()` を直接呼ばない）と本文（下記）だけ。** `BookStore`（EPUBの設計図）は正規ファイルの世代退避は持たず、**未保存の下書きだけ** `.novelai-recovery/book.json.draft` に1件控える（WebView は閉じる前の確認が出せないため。設計書6.65.7） 新しい台帳を作るときは `SettingsStore` に載せる（①＋ハッシュ照合。退避が無いことを承知で使い、要るなら人物と同じ形で足す）
  - **本文（.txt/.md）**：`textFile.ts` の `writeTextFilePreservingFormat` は2026-08-12まで③を直接呼んでおり、呼び出し側が現れるまで（誤字脱字検知のAI指摘パネル）気づかれないまま、ハッシュが一致していても常に失敗していた。現在は関数内部で「退避 → 新規作成」を行うため、呼び出し側は手順を意識しなくてよい。**新しく本文を書き換える処理を追加するときは、必ず `writeTextFilePreservingFormat` 経由にする。** `atomicWriteFile` を③で直接呼ぶ処理を新設しないこと（4か所目の同じ失敗になる）

### 3. AIの出力を信用しない

- 文字数制限（サブタイトル15字など）はコード側で再検証する。
- AIが指摘した箇所の文字列が本文に実在するか照合してから適用する。
- **マージ処理はAIではなくコードで行う。** AIには「本文から取り出す」ことだけをさせる。
- 同じ相手への複数の呼び方を、AIは1つにまとめたがる。プロンプトで明示的に禁止し、マージ側でも統合しない。

### 4. 処理量を節約する

- チャンク単位でキャッシュし、変更のないファイルは再処理しない。
- キャッシュのキーには**内容ハッシュ + プロバイダID + モデル名 + プロンプトversion**を含める（`chunkCache.ts` の `promptVersion|providerId|model|chunkHash`）。プロバイダIDを抜くと、同名モデルの別プロバイダの結果を再利用してしまう。
- プロンプトを変更したら、そのファイルの `_VERSION` 定数を上げる。

### 5. クラウドAIの失敗の扱い

- **失敗から学習しない。** モデルが対応していない指定を外して再試行する仕組みがあるが、覚えるのは**通ったときだけ**。失敗しただけで記憶を書き換えると、原因が別（残高不足など）だったときに対応機能を永久に失う。実際にClaudeで起きた。
- **エラー文から原因を当てにいかない。** GeminiもAnthropicも「どの項目が悪いか」を教えてくれない。任意の指定を1つずつ外して試す。
- **HTTP 400を「要求の形が悪い」と決めつけない。** Anthropicは残高不足も400で返す。
- **エラーの本文を捨てない。** 通知には出さなくても、ログ（`src/core/logger.ts`）には必ず残す。残さないと作者も開発側も原因にたどり着けない。APIキーらしき文字列は伏せ字にする。
- 失敗の種別（`AIError.kind`）ごとに、作者が次に取れる操作を1つ示す。「権限がない」「残高がない」「レート上限」は直し方が違うので分ける。
- 案内文にサービス名を決め打ちしない。Geminiを使っているのに「Claudeの…」と出た不具合が複数あった。

### 6. Ollama固有の注意

- **`num_ctx` を必ず明示する。** 指定しないと既定の短いコンテキストで動き、入力が黙って切り捨てられる。128k対応モデルでも同じ。
- `format` にJSONスキーマを渡すと形式が強制でき、パース失敗がほぼ無くなる。
- `think: false` で思考モードを無効化する（抽出タスクでは不要で遅くなるため）。
- モデル情報は `/api/tags` と `/api/show` から動的に取得する。**モデル名やコンテキスト長をハードコードしない。** 新しいモデルが次々出るため。

**この規則の例外は1つだけ——「測らないと分からない値」の初期値**（作者の裁定、2026-09-13）。字/トークンの換算や、実際に読める長さは、**APIがどこにも教えてくれない**。測るまで当て推量（0.7字/トークン）で動くので、実測の同梱表を持ってよい。ただし次の3つを必ず守る。

1. **APIが教えてくれる値は、必ずAPIを優先する。** 申告のコンテキスト長を同梱表で上書きしない
2. **作者自身の実測が常に勝つ。** 同梱表は台帳（`novelai.modelTuning`）が空のときだけ見る。台帳へ書き写さない
3. **同梱だと分かるようにする**（`speedSource` と同じ形で出どころを出す）。測った日付を持ち、古くなったら黙って使わない

**機械に依存する値は同梱しない**——出力速度と待ち時間は回線と負荷で変わる。読める長さはローカルでは VRAM 次第なので、**クラウドのモデルだけ**。字/トークンはトークナイザの性質なので、ローカルでも同梱してよい（実測：gemma-4 系は12Bでも31Bでも、手元でもさくらでも 1.383）。

### 7. ブラウザ版でも動く形で書く（設計書5.8）

この拡張機能は**手元のVS Code**と**ブラウザのVS Code**（vscode.dev / github.dev）の両方で動く。同じ `src/extension.ts` から2つの束をビルドしている（`esbuild.js`）。

- **`path` を直接importしない。** `import * as path from "../core/paths"` を使う。ブラウザ上の作品は `vscode-vfs://github/...` にあり、`path.join()` は `//` を潰して別の場所を指す
- **`vscode.Uri.file()` を直接呼ばない。** `paths.toUri()` を使う（同じ理由）
- **`node:` で始まるものを静的importしない。** どうしても要るなら、`canRunProcesses()` で確かめてから**動的import**する（`await import("./xxx.js")`。**`.js` 拡張子が要る**）
- **静的importは、呼ばれなくても実行される。** 拡張機能が読み込まれた瞬間に走るので、Node専用のファイルを1つでも静的importしていると、ブラウザでは起動した瞬間に落ちる
- **ブラウザで使えない操作は、消さずに押せなくして理由を出す**（`processAvailability.ts`）。`editorMode.ts`（編集者モード）と同じ考え方
- **確かめ方**：`platform: "browser"` でビルドが通っただけでは足りない（`external` 指定は「実行時まで解決を遅らせる」だけで、静的importは残る）。**esbuildのメタファイルから、`extension.ts` の静的importだけをたどって、Node専用のファイルへ届かないことを確認する**

## 実装スタイル

- TypeScript strict モード。`any` は使わない。
- コメントは「なぜそうしたか」を書く。「何をしているか」はコードを読めば分かる。
- エラーは握りつぶさない。ただしチャンク単位の失敗で全体を止めない（失敗を記録して続行し、最後にまとめて報告する）。
- 長時間処理は `vscode.window.withProgress` でキャンセル可能にする。
- ユーザーへの確認は、処理量とコストを提示してから行う。
