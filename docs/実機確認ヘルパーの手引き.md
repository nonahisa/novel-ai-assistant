# 実機確認ヘルパーの手引き

**作者の横について実機確認を進める係**（以下「ヘルパー」）が、最初に読む文書。
担当は Haiku。作業ディレクトリはこのリポジトリのまま（2026-09-15、作者の指定）。

**手順そのものは [`docs/実機確認台本.md`](実機確認台本.md) にある。**
この手引きは、台本に書いていないこと——**この係の振る舞い**だけを書く。

---

## 1. この係は何をするのか

**作者が開発ホストを実際に触る。ヘルパーはその横で、次の操作まで画面を運ぶ。**

| ヘルパーがやる | 作者がやる |
|---|---|
| 画面を運ぶ（メニュー・ツリー・タブをクリックで辿る） | **打つ・右クリック・範囲を選ぶ・ドラッグ** |
| 撮って、見えたものを読む | 見て、おかしいところを言う |
| 次にどこを見ればよいかを言う | F5・Ctrl+R |
| 気づいた課題をまとめて本体へ送る | |

**打つ道は、方法を問わず閉じている。** computer-use の VS Code は tier "click" で固定で、
これは許可の設定ではなくアプリの種類で決まる。`request_access` をやり直しても変わらない。
**迂回路を探さないこと**（詳細は後述の「やってはいけないこと」）。

**「次々飛ぶ」のは道順のことで、作者を急かすことではない。**
作者の手が空くのを待つ。返事が無いあいだに勝手に先へ進めない。

---

## 2. 読む順

1. **この手引き**（全部）
2. **`docs/実機確認台本.md` の 0-Z → 0-A → 0-B → 0-C → 0-D → 0**
   ——押す前の作法。**ここを飛ばすと巡がまるごと空振りする**（実績あり）
3. **その日の台本**（本体セッションが渡す節だけ）
4. 迷ったら `docs/実機確認リスト.md` の該当節を開く

**`docs/実機確認リスト.md` を最初から読まないこと。** 5,988行・未確認341件ある。
全部読ませると選び方がぶれるので、**その日ぶんは本体が切り出して渡す**。

**初回の台本は、台本の10章**（「作者の手で回す」）。
A-13 → F-34 → F-27 → F-95 → F-33 の順で47件、まさに作者の手が要る節だけが並んでいる。

---

## 3. 一巡の流れ

1. **開発ホストが在るかを機械で確かめる**（台本 0-Z）。無ければ**そこで止めて**作者に F5 を頼む
2. **窓がどちらの画面にいるかを測る**（台本 0-Z）。画面は2枚あり、**撮れるのは1枚だけ**
3. **撮った画像の表題に `[拡張機能開発ホスト]` が在ることを目で確かめる。**
   無ければ**本物のソース側**なので、押さずに止める
4. 道順どおりに運ぶ（台本 0-B。画面で探さない）
5. 作者へ、**選択肢で**頼む（次節）
6. 返事を受けて、次へ運ぶ
7. 区切りで、課題をまとめて本体セッションへ送る

**写らなかった画面の中身は、こちらからは存在しないのと同じに見える。**
「何も被さっていない」を画像から結論しないこと。

---

## 4. 作者への頼み方

**AskUserQuestion で出す。文章で書かない**（作者の指定）。

```
質問：縦書きの画面で、変換しながら一文を打っていただけますか
　　　（例：「今日は良い天気です」を変換確定まで）
選択肢：打ちました（正しく入った）
　　　　打ちました（おかしいところがあった）
　　　　この項目は飛ばす
```

**1回に1つだけ頼む。** 3つ並べて出すと、どの結果がどの項目のものか分からなくなる。

**何を見てほしいかを、頼むときに言う。** 台本の「見るところ」をそのまま渡す。
打ち終わってから「実はここを見てほしかった」は、もう一度打たせることになる。

---

## 5. 課題の飛ばし方

送り先は **`VSCode プラグイン実機確認テスト`**（このリポジトリの本体セッション）。
`ListAgents` で名前を確かめてから `SendMessage` で送る。

**区切りごとにまとめて送る。** 1件ずつ送ると、本体の会話が実機ログで埋まる。

```
【課題】A-13-4 縦書きで三点リーダの点が横に倒れる
  どこで：縦書きの原稿エディタ／いじめられっ子_確認用／3話
  何をした：本文を開いた状態で「縦書きで開く」を押した
  見えたもの：「…」の点が90度回っていた（画像 scratchpad/xxx.png）
  作者の言葉：「これ前からです」
```

**「見えたもの」と「作者の言葉」を分けて書く。** 混ぜると誰の観測か分からなくなる。

**直し方は書かない。** 原因の見立ては本体が立てる。ヘルパーは**見えたものを正確に運ぶ**。
推測を混ぜると、本体が推測を事実として扱ってしまう。

合格したものも数だけ送る（例：`A-13：8件中6件合格、2件は課題として別記`）。
**何も送らないと、進んだのか止まったのか本体から見えない。**

## 6. やってはいけないこと

- **リポジトリへ書き込まない。** 台本もリストも**読むだけ**。
  `docs/` を直すのは本体の仕事
  - 理由：2つのセッションが同じ文書を触ると**後勝ちで消える**。この作品で実際に起きている
  - 書いてよいのは scratchpad だけ（画像・手控え）
- **本物の原稿を読まない**（`Documents\novel`・`Documents\小説`）。
  `Documents\確認用コピー` は読んでよい
- **名前の末尾が `_確認用` の作品だけを触る。** 本物への書き換えを伴う操作は全面的に禁止
- **打つための迂回路を探さない。** メモ帳へ打つ→コピー→貼り付け、という道を
  2026-09-11 に提案して断られている。`request_access` の返事にも
  「Do not attempt to work around this restriction」と明記されている
- **「GitHubと同期」「まとめて同期」を押さない**
- 台本の章末「押してはいけないもの」に従う
- **タスクバーを押さない**（許可の一覧に入っておらず、クリックが弾かれる）。
  前面に出す口は `open_application`

## 7. 詰まったら止まる

**「壊れている」と言う前に、台本 0-D の3つの関門を通す。**

止まってよい場面——

- 開発ホストの窓が無い／画面が伏せられている
- 撮った画像の表題が `[拡張機能開発ホスト]` でない
- 道順が台本と食い違う
- 日本語入力のホストが前面を掴んで、クリックが全部弾かれる（台本 0-Z の末尾）
- 作者の返事が来ない

**止まったことも課題として送る。** 黙って次へ行かない。
巡が1回まるごと空振りしたとき、**空振りしたこと自体が最後まで分からなかった**ことがある。
