統合小説執筆環境のまわりに、創作者が集まる Discord サーバーを立ち上げるための計画。**まだ何も作っていない。**

**作者の裁定（2026-10-17）**

| 項目 | 決めたこと |
|---|---|
| 始め方 | **第1段（ボットの土台・作者タイプ・要望とエラーの受付・母艦への Issue）まで作ってから開く** |
| 稼働環境 | **母艦で動かす**（3章の案C）。夜や不在の間は Discord の AutoMod だけが守る |

| モデレーター | **当面は作者だけ** |

## 1. 狙いと序列

**主は創作者の交流、従が統合小説執筆環境のサポート。** サポート窓口に雑談部屋が付いているのではなく、創作者の集まりがあって、その人たちの声で道具が育っていく形にする。

そう見えるために、次の3つを守る。

1. **チャンネルの並びで序列を見せる。** 上に「創作者の部屋」、下に「環境を一緒に作る部屋」。使い方の質問は一番下
2. **要望が版になるまでを、見える一本の道にする。** 「機能の種」→「育てている種」→「次の版に入るもの」→「実った（配布済み）」。実ったら提案者の名前を出す（本人が同意したときだけ）
3. **AIは前に出ない。** 監視もファシリテーションも、まず人（モデレーター）に置いていく。編集部が本文を書き換えず提案として置く（設計書5.6）のと同じ構え

## 2. 全体の形

```
Discord サーバー
  ├─ Discord の標準機能（無料・コード不要）
  │    AutoMod（荒らしの一次防衛）／フォーラム／オンボーディング／サーバーガイド
  │
  └─ 自前のボット 1本（TypeScript・discord.js）
        稼働場所：母艦（3章。常駐マシンへ移せる書き方にする）
        AIの口：切り替え式。既定はさくら（無料枠）、Haiku 等も選べる（4章）
        記録：SQLite 1ファイル（停滞の時計・問診の結果・要望の状態）
        │
        └─ GitHub Issues（非公開の受付リポジトリ）
              └─ 母艦（開発担当セッション）が読む（8章）
```

**ボットのコードは別リポジトリにする**（`nonahisa/novel-ai-community-bot`、非公開。手元は `Documents/novel-ai-community-bot`。2026-10-17 作成）。投稿サイトのヘルパーと同じ扱いで、製品の VSIX に混ざらないようにするため。この文書だけ製品の `docs/` に置く。

## 3. 稼働環境の選択肢

| 案 | 月額 | 24時間 | 良い所 | 困る所 |
|---|---|---|---|---|
| A. Google Cloud e2-micro（起案時の推奨） | 0円 | ○ | 無期限の無料枠。メモリ1GBで discord.js のボット1本には足りる | 米国の3地域だけ無料。カード登録が要る。地域を間違えると即課金 |
| B. Oracle Cloud Always Free | 0円 | ○ | 性能が大きい（ARM） | 2026年6月に無料枠が半分に減ったとの報道があり、公式の表と食い違う。使われていないと判断されると回収されることがある。人気の地域は空きが出ない |
| **C. 母艦（作者のPC）＋手元の Ollama（採用）** | 0円 | × | AIまで無料。設定がいちばん楽 | **作者が寝る・離席すると止まる**（画面消し・スリープの運用がある）。荒らしは夜に来る。GPUを作者の作業と取り合う |
| D. 国内の格安 VPS（さくらのVPS 等） | 数百円〜 | ○ | 国内で完結。回収の心配がない | 有料 |
| E. Cloudflare Workers（HTTP で受ける方式） | 0円 | ○ | 常駐不要 | スラッシュコマンドとボタンしか受けられない。**発言を見られないので、荒らし監視と停滞検知ができない** |

起案時の推奨は A だった（監視と停滞検知はメッセージを見続ける接続＝Gateway が要り、無料で回収の心配が小さいため）。**作者の裁定で C（母艦）に決まった。**

**母艦で動かすときの約束**

- **止まっている間も Discord の AutoMod は動く**（Discord 側の機能なので母艦と関係ない）。夜の荒らしの一次防衛はここに任せる。だから AutoMod の設定を最初に厚くする
- ボットは**起動したとき、止まっていた間の発言をさかのぼって読む**（直近の件数まで）。止まっている間に立った質問・要望・不具合を取りこぼさない
- ボットの状態欄に「見習いは今お休み中です（夜は返事が遅れます）」と出す。会員が無視されたと思わないように
- 停滞の時計は、母艦が起きている時間だけ回す
- **ボットのコードは A・D でも同じに書く。** 人が増えて夜の監視が要るようになったら、設定を変えずに移せるように
- Ollama は作者の作業と取り合うので、母艦で動かす間のAIは原則クラウド側（4.1）。Ollama は試運転用

Discord 側の制約：ボットが発言の中身を読むには「Message Content Intent」を有効にする。参加サーバーが100未満のボットは審査なしで有効にできる。このボットは1サーバー専用なので問題にならない。

## 4. AI の口と処理量の節約

### 4.1 どこへ送るか（切り替え式）

**AIの口は設定で差し替えられるようにする**（作者の裁定）。用途ごとに口を選べる形にし、1つが落ちたら次へ回す。製品の口の作り（プロバイダIDとモデル名で選ぶ）に揃える。

| 口 | 費用 | 会員の発言を送ってよいか | 向いている用途 |
|---|---|---|---|
| **さくらのAI Engine** | 月3,000回まで無料、超えると従量 | ○（国内で完結） | 既定の口。監視の判定・要約・使い方の回答 |
| **Claude Haiku（Anthropic API）** | 従量課金（1回は安いが無料枠なし） | ○（API の入力は既定で学習に使われない。規約で要確認） | 使い方の回答・論点整理など、日本語の読み取りの質が要る所。さくらの枠を超えた月の受け皿 |
| Gemini（無料枠） | 0円 | **×**（無料枠の入力は Google の改善に使われ、人が読むこともある） | 会員の発言を含まない処理（話題の在庫づくり）だけ |
| Gemini・ChatGPT（有料） | 従量課金 | ○（規約で要確認） | 予備 |
| 手元の Ollama | 0円 | ○（外へ出ない） | 試運転。作者が作業していないとき |

- **Haiku は API キーで使う**（従量課金の正規の口）。Claude のサブスクリプションをボットの裏で使うことはしない
- 口ごとに**月の上限回数（または金額）**を設定に持ち、超えたら次の口へ。全部超えたら「AIなし」の動き（4.2の最後）に落ちる
- 会員の発言を「送ってよい口」だけに流す区別は**コードで止める**（設定の書き間違いで Gemini 無料枠へ流れないように）
- 失敗の扱いは製品の規則5と同じ（失敗から学習しない・エラー文から原因を当てない・鍵は伏せてログに残す）

**会員の発言をクラウドAIへ送ることは、サーバーのルールに書いて同意を取る**（オンボーディングで「読んだ」を押してもらう）。原稿の一部が混ざりうるため。

### 4.2 全部の発言にAIを当てない

月3,000回（1日100回）に収めるため、AIを呼ぶのは**コードで絞った後だけ**にする。

| 機能 | AIを呼ぶ条件 | 1日の目安 |
|---|---|---|
| 荒らし監視 | AutoMod とコードの規則（連投・新参の外部リンク・大量メンション）で引っかかった分と、会員が「モデレーターに知らせる」を押した分だけ | 0〜10回 |
| 話題の投下 | 週1回まとめて在庫を作る。投下は在庫から出すだけ | 週1回 |
| ファシリテーション | 予兆（後述）が出たときだけ | 0〜3回 |
| 作者タイプ | **呼ばない**（製品の判定をそのまま使う） | 0回 |
| 使い方の質問 | 質問1件につき1回。同じ質問は答えを使い回す | 5〜30回 |
| 要望・エラーの要約 | 1件につき1回 | 0〜10回 |

超えそうになったら、使い方の質問を「FAQ の該当箇所を貼るだけ」に落とし、監視の判定はモデレーターへ回す。**AIが使えなくても止まらない作り**にする。

## 5. 交流（主）の設計

### 5.1 チャンネル構成（案）

```
📖 はじめに
   ルール／自己紹介／作者タイプ（問診の結果を置く場所）
✍ 創作者の部屋                ← いちばん上
   雑談／お悩み相談（もと「詰まっている話」。「書いている話」は作品紹介と重なるので消した。話題が分散するとにぎやかさがなくなるため。作者の裁定 2026-10-18）／イベントの提案（フォーラム。「今日の一行」「お題」を消して置き換えた。作者の裁定 2026-10-18）
   作品紹介（フォーラム。自作の宣伝もここへ。宣伝だけの投稿は週1回まで。「作品の宣伝」の部屋は役割が重なるので消した。「読み合い」は相互に読む約束に見え、ランキングをゆがめると受け取られるおそれがあるので避けた。作者の裁定 2026-10-18）
   もくもく会（ボイス。黙って書く部屋）
🌱 環境を一緒に作る部屋
   機能の種（フォーラム。投票はリアクション）
   取り入れる予定（読み取り専用）／入った機能（入った機能のお知らせ）。もとは「次の版に入るもの」「実った」だったが、更新が少ないと空になり、「版」も分かりにくいので改めた（作者の裁定 2026-10-18）
   ベータを試す（希望者のロールだけ）
🛠 困ったとき
   使い方の質問（フォーラム）／不具合の報告（フォーラム）
🔒 モデレーター
   見張り番の報告（ボットが置く）／論点整理（ボットが置く）
```

### 5.2 荒らしの監視

3段で受ける。上の段ほど安い。

1. **Discord AutoMod**（無料・コード不要）：禁止語、大量メンション、怪しいリンク、スパムの疑い
2. **ボットの規則**（AI不要）：入って24時間以内の外部リンク、短時間の連投、同じ文の複数チャンネル投稿
3. **AIの判定**（1と2で引っかかった分と、会員の通報だけ）：荒らし／口論／問題なし の3択と理由1行

**AIは処分しない。** できるのは「メッセージを隠してモデレーターへ知らせる」まで。タイムアウトやキックは人が押す。AIの誤判定で常連を追い出すと、取り返しがつかないため。

### 5.3 話題の停滞

- **時計はコードが持つ。** 決めたチャンネルで、人の多い時間帯（例：20〜24時）に N時間（例：3時間）発言がなければ1つ投下。**1チャンネル1日1回まで**
- **中身は在庫から出す。** 週1回、AIに「創作の問い」を20件ほど作らせ、モデレーターが目を通してから在庫へ入れる。作者が自分で足してもよい
- 投下には問いを1つだけ書く。ボットが会話を続けない（人の会話が始まったら引っ込む）

### 5.4 もめそうなとき（ファシリテーター）

- **予兆はコードで拾う**：同じ2人の往復が短時間に続く、強い言葉の規則に当たる、会員の通報、モデレーターがメッセージに「論点整理」を押す
- AIは**モデレーター用チャンネルに**論点整理を置く。形は「Aさんの主張／Bさんの主張／一致している点／食い違っている点／事実の確認が要る点」。**どちらが正しいかは書かない**
- 人が読んで、使えると思ったら［この整理をスレッドに出す］を押す。**AIが本人たちの会話へ直接割り込むことはしない**（火に油になるため）

### 5.5 作者タイプの問診

**製品の「相談の助言方針」（設計書6.86）の9問と判定を、そのまま使う。** 製品と食い違うと、試した人が裏切られる（`記事のたね_タイプ分類.md`）。

- 判定は `src/core/advicePolicy.ts`（`ADVICE_QUESTIONS`・タイプの判定）と `threeAxis.ts`。VS Code に依存しない純粋関数なので、**写しを作らずボットから読み込む**（ボットのリポジトリから製品リポジトリを参照してビルド時にまとめる）
- `/作者タイプ` で9問をボタンで答える。**AIは使わない**（費用0、結果がぶれない）
- 結果は**本人にだけ**見える形で出し、［共有する］を押したら #作者タイプ に貼る。11タイプはロールにもでき、同じ型の人どうしで話せる
- 外へ共有：11タイプの紹介ページを GitHub Pages に置き（無料）、結果に URL を添える。X 等に貼ると絵つきで出る
- **守ること**：「診断」「あなたは〜が足りない」と言わない（「あなたにはこういうものが効く」）。受容度・自信度は出さない。質問の点数表は出さない
- 結果の最後に「統合小説執筆環境では、このタイプに合わせて相談の言い方が変わります」と1行。押し売りはしない

## 6. サポート（従）の設計

### 6.1 使い方の質問

- #使い方の質問（フォーラム）に新しい投稿が立ったら、ボットが1回だけ答える
- **RAG は作らない。** README と FAQ（新しく作る短いもの）を毎回まるごと渡す。答えには必ず「どこに書いてあるか」を添え、書いていないことは「分かりません、作者に回します」と答えさせる
- 答えの下に［解決した］［違う］ボタン。［違う］は作者への質問として 8章の道へ。解決した質問は FAQ の種になる

### 6.2 機能要望

- #機能の種（フォーラム）。立てるときにテンプレート（困っていること／こうなると嬉しい／いまの回避策）
- ボットは**似た種がないか**を探してリンクを添える（重複を減らす。まとめるのは人）
- 👍 の数と、モデレーターの［育てる］で 8章の道へ。**採用・不採用は作者が決め、理由を一言返す**

### 6.3 エラーの情報収集

- `/不具合を報告` で入力欄つきの窓が開く。Discord の窓は欄が5つまでなので：①環境（版・VS Code の版・OS・ブラウザ版か・AIの種類とモデル）②何をしたら ③期待した動き ④実際の動き ⑤記録（任意）。記録は .txt／.md の添付（1MB まで）でも受ける
- **記録（⑤と添付）は非公開の受付 Issue にだけ載せる。** 会員が読めるスレッドには①〜④だけ
- **製品の「障害報告用の記録」と揃える**（製品側と合意、作者の裁定 2026-10-17）：製品は `.aiwriter/reports/` に .md を1枚書き出す。前半は3,000字以内の要約（見出しは上の①〜④と同じ。①は製品が埋める）、全体で1MB以内。原稿の本文・AIの応答は 〈本文 123字〉 のように置き換え、**人物名と作品名は既定で 〈人物A〉〈作品〉 に伏せる**（作者が外せる）。絶対パスは相対か `~`。どの行にも日本語が120字を超えて続かない（ボットの原稿の疑い 200字に当たらない）。送るのは作者の手で貼るだけ（Webhook は使わない。製品は公開されていて、送り先を入れると誰でも投稿できるため）
- **報告ID** `NAI-YYYYMMDD-xxxx`（xxxx は英小文字と数字4字）で、スレッド・Issue・記録を結ぶ。ボットは本文から拾って Issue の題の先頭に入れる。見出しの正確な文字列は製品の設計書に書かれたらボットを合わせる
- **原稿本文は貼らせない。** 入口で注意を出し、ボットは長い日本語の段落を見つけたら「本文が入っているかもしれません、外してください」と止める
- **APIキーらしい文字列は伏せる**（製品の規則5と同じ）。伏せてから保存・転送する
- 同じ版・同じ症状をまとめて件数を数える

## 7. 「コミュニティが作っている」ための仕掛け

- **実った種に提案者の名前**：CHANGELOG と #入った機能 に「提案：〇〇さん」（同意した人だけ）
- **ベータ参加者のロール**：配布前の VSIX を試してもらう。実機確認の一部を手伝ってもらえる
- **月1回の「次の版の相談会」**：作者がボイスかテキストで、次に何を育てるかを話す。決めるのは作者
- **呼び名をそろえる**：要望は「種」、採用は「育てる」、配布は「実る」。創作者の言葉で開発を語る
- **ボットの名前と役**：店員ではなく「見習い」にする（例：編集部の見習い）。偉そうに見えないことが大事

- **非公開の受付リポジトリ**（`nonahisa/novel-ai-community-inbox`、無料。2026-10-17 作成。ラベル `未読`・`要望`・`不具合`・`質問の取りこぼし`）に Issue を立てる。製品リポジトリは公開なので、会員の発言をそのまま置かない

## 10. 進め方
