## 0-A. 画面を見る回数を減らす（作者の指定、2026-09-08）

**作者の指定「ファイル優先へ寄せる」。** 実機確認の費用のほとんどは**画面を撮ること**である。
1枚あたり千数百トークンで、1つの確認に5〜10往復かかる。
ログやファイルを読むのは数百トークンで、**桁が2つ違う**。

**画面でしか確かめられないのは2つだけ**である。

1. **組まれた見た目**——ルビが振り仮名になるか、黄色の帯が付くか、ボタンが枠に収まるか、色分け
2. **押して初めて起きること**——ダイアログの文言、選択肢の並び、通知

**これ以外は、必ずファイルかログで確かめる。**

| 確かめたいこと | ✗ 画面 | ○ ファイル・ログ |
|---|---|---|
| 処理が終わったか | 進捗を撮る | `.aiwriter/logs/actions.log` を `tail` |
| 何件できたか | 一覧を撮る | `ls 設定/characters/*.json | wc -l` |
| 中身が正しいか | パネルを撮る | JSON を `node -e` で数える |
| 本文が壊れていないか | エディタを撮る | 控えと `diff -rq` |
| 設定がどうなっているか | 設定画面を撮る | `settings.json` を読む |
| 機能が実装されているか | メニューを探す | `grep` でコマンドIDを引く |

**順序も効く。コードを先に読み、画面は裏取りに1回だけ使う。**
2026-09-08 の夜に見つけた不具合は、**どれもコードとファイルから出た**——
プレビューのルビ（VS Code 本体の `dist` を grep）、思考が流れない（ソース2行）、
傍点が字数に入る（`stripRuby` が2つある）、関係の重複48%（node スクリプト）。
画面はどれも「最後に1回」確かめるために使っただけである。

### 撮るときの作法

- **全画面を撮ってから拡大しない。** 見たい場所を最初から `zoom` で撮る
- 位置を探すだけなら `scale: 0.4` で足りる。読む必要があるときだけ `scale: 1`
- **座標は一度測ったら使い回す**（下の表）。同じ場所を何度も測り直さない
- `computer_batch` で押せるだけ押し、**撮るのは最後の1回**にする

### 印刷用HTML から分かること（`unzip` も要りません）

`.aiwriter/exports/印刷用 *.html` を開くと、**選んだ判型がそのまま入っています**。

```
@page { size: 105mm 148mm; margin: 15mm; }   ← A6判・余白15mm
writing-mode: vertical-rl                     ← 縦書き
```

ですから **F-25 の「用紙サイズ・余白は『既定』のまま」**という但し書きの理由は、
ファイル側で確かめられます——**判型は HTML の `@page` が持っており、
印刷ダイアログで指定するものではない**からです。
**実際に PDF ができるかどうか**は `Ctrl+P` を押す必要があるので、作者の手が要ります。

**この日、私は同じ形の誤報を3回出した。** どれも**手元の材料だけで結論を急いだ**のが共通で、
3回とも自分で取り消した。**次に同じ道を通らないための手順**をここへ置く。

| いつ | 何と言ったか | 実際は |
|---|---|---|
| 14:20 | 「原稿を読み上げる」が**押しても何も起きない** | **私の押し損ね**。作品選択の行の隙間を押していて、QuickPick が閉じただけ（取りやめの正しい振る舞い） |
| 18:50 | EPUB に**傍点が出ていない**（`text-emphasis` が0件） | **探し方が違った**。傍点は `class="emphasis"` で印を付け、`text-emphasis` は**CSSの側**にある |
| 21:30 | 変換のあと**本文が壊れる**（同じ語が二重・三重） | **作者が意図して繰り返し打った**もの。壊れた証拠ではない |

### 言う前に通す3つの関門

1. **「無い」と言う前に、中を見る。**
   grep で0件でも、**別の名前で入っている**ことがある（傍点＝`class="emphasis"`／
   関与度＝記録に持たず表示のときに計算／ルビ＝本文に記法が無いだけ）。
   **探し方を変えて2通り試すまで、「無い」と書かない。**
2. **「押しても起きない」と言う前に、押せたことを確かめる。**
   0.5倍の画面から換算した座標は**1行ぶん（約15px）ずれる**。
   **押し先が1行ずれると致命的な場面では、倍率1で撮る**（0-Bにも書いた）。
   QuickPick は行の隙間を押すと**閉じるだけ**で、それは正しい振る舞いである。
3. **痕跡を証拠に使う前に、誰がその痕跡を作ったのかを訊く。**
   ファイルに残った変な並びは、**作者の操作の跡**であることがある。
   **「何をどう打ったか」を聞いてから**、壊れたかどうかを言う。

**「自由に打ってみてください」では、あとから判定できない。** こう頼む。

## 0. 共通の約束（最初に1回読む）

- 起動：`code --extensionDevelopmentPath=<worktree> --folder-uri=file:///<作品フォルダー>`。
  `--new-window <パス>` はフォルダーが開かないことがある。起動後、制限モードのバナーで
  「管理」→「信頼する」を押す（信頼しないと拡張機能が有効化されない）。
- **作品登録は globalState にあり、コピーを開いても本物を指す。** コピー作品を試すときは
  「1. 作品登録 > フォルダから追加」で別作品として登録し直し、選択作品を明示的に
  コピー側（例：「いじめられっ子_確認用」）へ切り替える。切り替え忘れたまま操作しない。
- **作品一覧を展開するとメニュー全体が下へずれる。** クリック前に必ず `computer zoom` で
  いま見えている位置を確かめてから押す。ずれたまま座標で押すと別の項目に当たる。
- **トースト通知のボタンは座標が当たらないことがある。** 確認ダイアログ（「実行」等）は
  ステータスバー右端のベル（通知センター）を開き、そこに並ぶ大きなカードのボタンを押す。
- **ダイアログ（フォルダー選択）・InputBox は座標クリックで本物を触る危険がある。**
  フォルダー選択ダイアログの操作は作者に依頼し、予期せぬInputBox（新規話ファイル名・
  作品名など）が出たらEnterを押さず作者にEscでの取りやめを依頼する。
- **指摘の照合は必ず `computer zoom` で読む。** 0.6倍などの縮小スクショのまま行番号や
  文言を読み取らない（誤読の実績あり）。
- **本物の作品では押さないボタン**：適用／見送り／今後直さない／反映する／保存／書き出し
  （`設定/`や本文に書くもの）／Git操作（記録・送信・同期・書庫化）／クラウドAI（課金の
  確認が出る操作）。本物では「表示・実行して見るだけ」に留める。
- AIは **LM Studio（google/gemma-4-e4b）** を使う。12b（qat）は遅く300秒でtimeoutしやすい
  ので、AI機能を使う前に `lms ps` で12bが読み込まれていないか確認し、いれば
  `lms unload google/gemma-4-12b-qat` で外す。
- ツリーのグループ（「作品管理」など）は行クリックで展開しないことがある。展開しなければ
  矢印（`>`）をクリックする。「AIに相談」「詳細メニュー」のヘッダーを畳むと簡単ステップ
  メニューの表示領域が広がる。長い一覧を触るときは畳んでおく。
- **ボタンの座標は必ず等倍のスクリーンショットから読む。** 0.6倍などから換算すると
  10〜20px ずれて空振りする（実績あり）。とくに**カードに注記の行が増えるとボタン列が
  下へずれる**（「再チェック（時刻）：…」が付くと約16px）。押して反応が無いときは、
  まず等倍で撮り直して位置を取り直す（機能の不具合と決めつけない）。
- **クリックが全部弾かれたら、IME の常駐を疑う。** Windows の「入力エクスペリエンス」
  （`TextInputHost.exe`）が**画面に何も見えないまま前面を握る**ことがあり、
  「Textinputhost is not in the allowed applications」で止まる。作者にも見えないので
  聞いても解決しない。Bash から `Stop-Process -Name TextInputHost -Force` で止める
  （Windows が必要時に入れ直す）。`open_application` では戻らない。
- **通知は溜めない。** 節の区切りごとに通知センター（ステータスバー右端のベル）を開き、
  用の済んだ通知を「通知をすべてクリア」で消す。溜まると確認カード（「実行」ボタン）が
  下へ押し出されて埋もれ、古い通知を新しい結果と読み違える（実績あり）。
- **画面の使い勝手も見る**（作者の依頼、2026-09-06）。押しにくい（境界が分からない・
  小さい・隣と近い）、名称が分かりにくい・実物と違う、表示が崩れる／ダサい、と感じた点を
  気づいた範囲で記録する。判定は作者がするので、こちらは「どこで・何が・どう感じたか」を
  1行ずつ書けばよい。記録先は `実機確認メモ.md` の「デザインの気づき」節。
- 各節を終えたら `実機確認メモ.md` に「見出し・時刻・結果（合格／不具合／判断案件）」を
  1ブロック追記する形式で記録する（既存の記録の書き方を写す）。

## 8. 仕込み方式で「見逃し」を測る（2026-09-06 に確立）

**なぜ要るか**：これまでの実機確認は「誤った指摘が出ないか」（誤検出）に偏っていた。
AI機能は**見逃し**も測らないと、「何も指摘しない実装」が満点になる（CLAUDE.md の
繰り返した失敗2）。既知の誤りを本文へ仕込んで、拾えるかを見る。

**手順**（コピー作品でのみ行う。本物には仕込まない）
1. 対象ファイルを scratchpad へ退避（`cp`）
2. 誤りを仕込む。**改行コードを保つ**こと（`\r\n` を `split`/`join` で扱う。`file` で確認）
3. 検知を実行する。確認画面の「N チャンク中 M 件を処理します」で、**変えたチャンクだけが
   AIへ行く**ことも同時に確認できる
4. 結果を判定し、**退避から元へ戻す**。最後に作品全体のハッシュを控えと突き合わせて
   差分0を確かめる（`sha256sum` の一覧を `diff`）

**仕込む誤りの例と、2026-09-06 の結果**（LM Studio `gemma-4-e4b`）

| 仕込んだもの | 種類 | 結果 |
|---|---|---|
| 「かもしれ**あ**い」（な→あ） | かな1文字の置き換え | **拾った** |
| 「思わなかつた」（っ→つ） | 促音の誤り。日本語では典型 | **素通り** |
| 「目を覚まさ、」（覚まし→覚まさ） | 活用の誤り／脱字 | **素通り** |
| 「おばあさん」→「お婆さん」 | 漢字とかな | **拾わない**（仕様。固有名詞はカナの入れ替えのみ見る） |
| 「おばあさん」→「オバアサン」 | ひらがな⇄カタカナ | **拾った**（2組。うち1組は部分文字列で重なる） |

**1回では測れない（2026-09-06 に実測）**：同じ入力・同じモデル・temperature 0 でも、
拾える回と素通りの回がある（180字 1/1、1,018字 3/4、5,019字 1/1）。**「N回中M回」で書く。**
1回だけの結果から「拾えない」と断定しない。検証で捨てた件数と理由も必ず出す
（生の指摘が有って通した件数が0になることがある）。

**外から測るときは、拡張機能側でAI処理が走っていないことを確かめる（2026-09-06 に踏んだ）**：
API を直接叩くと、拡張機能の「実行の札」（AI処理を1つずつに絞る仕組み）が効かない。
同時に AIチューニングが走っていて 91,488字の要求でサーバーが埋まり、こちらの要求が
すべて `fetch failed` になった。それを「LM Studio が落ちた」と誤って報告した
（CLAUDE.md の繰り返した失敗5そのもの）。測る前に `lms ps` の状態と、
作品の `.aiwriter/logs/actions.log` の末尾を見る。

**判定のしかた**：拾えなかったものは、**プロンプトの問題かモデルの力か**を切り分けるため、
同じ本文を別のモデル（12b、さくらのAI 等）へ通して比べる。片方だけでは結論が出ない。

   > 書く面：打っている最中に色が一瞬消える程度で、ズレた色文字・浮いた用語が出ないか（スクロール直後・変換確定直後・面を切り替えた直後）
5. **やること**：実データ（コピー作品）の本文を一通り眺め、「彼《行くぞ》」のようにセリフの括弧がルビ記法と誤認されている箇所がないか探す。
   **見るところ**：組まれた画面で、会話の括弧部分が変な小さい文字（ルビ）になっていないか。
   **合格**：誤認箇所が無い（あれば場所を報告する）。
   > 会話の括弧（例：彼《行くぞ》）が誤ってルビに見える箇所が実データに無いか（既知の限界。あれば報告）

### 10-3 F-27 組んで書く（実験）——ルビが組まれたまま打てる面

道順：詳細メニュー →「執筆AI支援」→ 原稿づくり →「組んで書く（実験）」
使う作品：たゆたう鉛_確認用 または ハイエルフ未亡人のお気楽資産運用〜_確認用（10-2と同じコピーでよい）

1. **やること**：ルビ・傍点のある話をこの面で開き、縦書き・横書き両方で日本語を入力・変換する。
   **見るところ**：変換窓の位置がおかしくないか、確定した文字が取りこぼされないか。
   **合格**：縦横どちらでも問題なく日本語入力ができる。
   > 「組んで書く（実験）」で面が開き、ルビ・傍点が組まれた状態で日本語入力ができるか（縦書き・横書き両方。変換窓の位置・確定の取りこぼし）
2. **やること**：入力後保存し、通常の原稿エディタや素のテキストエディタで同じファイルを開く。
   **見るところ**：ルビ記法・空行・全角空白を含め、本文が壊れていないか。
   **合格**：どの見方でも本文が一致する。
   > 打った内容が保存され、他の面・素のエディタで見ても本文が1文字も壊れていないか（ルビ記法・空行・全角空白）
3. **やること**：文字を範囲選択して「ルビを振る」を実行し、その直後にCtrl+Zを押す。
   **見るところ**：ルビを付ける前の状態に戻るか。
   **合格**：正しく取り消される。
   > 取り消し（Ctrl+Z）が効くか。とくに「ルビを振る→Ctrl+Z」の往復
4. **やること**：Enterキーを連続して押したあと、Backspaceで連続して削除する。
   **見るところ**：意図した数と異なる空行が残らないか。
   **合格**：打った分・消した分だけ正確に増減する。
   > 改行を連打・削除して、空行が増減しないか
5. **やること**：ルビ・傍点が付いた語を、クリックや矢印キーで選択・削除してみる。
   **見るところ**：かたまり全体が1文字のように動くか、かたまりの途中にカーソルが止まらないか。
   **合格**：かたまりごと選択・削除でき、途中にカーソルが入らない。
   > ルビ・傍点のかたまりが1文字のように選べる・消せるか。かたまりの中にカーソルが入らないか
6. **やること**：改行がLFの原稿とCRLFの原稿の両方をこの面で開く。
   **見るところ**：LFでは用語に色が付き、CRLFでは色が付かない（仕様どおり）か。
   **合格**：LFで色が付き、CRLFで付かないことを確認する（CRLFで付かないのは不具合ではない）。
   > 用語の色付け（Custom Highlight API）が出るか。CRLFの原稿では色が出ないのが正しい挙動（既知の穴。設計書6.34.5）
7. **やること**：用語の上で右クリックして「設定資料を見る」を選ぶ。別に、用語の上にマウスを乗せたまま少し待つ。
   **見るところ**：右クリックで資料が開くか。ホバーでチップ（吹き出し）が出るか。縦書きで位置がずれないか。
   **合格**：どちらも正しい位置で機能する。
   > 右クリックで設定資料、ホバーでチップが出るか（縦書きでの位置ずれ）
8. **やること**：ふつうの文字範囲を選んで「ルビ」を実行する。別に、既にルビが付いているかたまりを含む範囲で同じ操作をする。
   **見るところ**：前者はルビが振れるか。後者は断り（エラー表示）が出るか。
   **合格**：普通の範囲は振れ、かたまりを含む範囲は断られる。
   > 範囲を選んで「ルビ」を押すと振れるか。かたまりを含む選択では断りが出るか
9. **やること**：ルビが組まれた文字列を選択してコピーし、素のテキストエディタ（メモ帳や別ファイル）に貼り付ける。
   **見るところ**：貼り付け結果が記法どおり（`{漢字|かんじ}`など）になっているか、読み仮名が本文に紛れ込んでいないか。
   **合格**：記法どおりに貼れる。
   > コピーして素のエディタへ貼ると記法（{漢字|かんじ}として）貼れるか（読み仮名が本文に混ざらないか）
10. **やること**：Webページから装飾付きの文章（太字やリンクなど）をコピーし、この面に貼り付ける。
    **見るところ**：貼り付け後、装飾が引き継がれず平文として入るか。
    **合格**：平文として崩れず入る。
    > 貼り付けが平文になるか（Webからの装飾つきコピーを貼っても崩れないか）
11. **やること**：4万字ある作品のコピーでこの面を開き、文字を打つ。
    **見るところ**：入力の反応が遅くならないか。
    **合格**：普通の速さで打てる。
    > 4万字級で打鍵が重くないか
12. **やること**：本文の途中にカーソルを置いた状態で別の面に切り替え、またこの面に戻る。
    **見るところ**：戻ったときカーソル位置がだいたい同じ場所にあるか。
    **合格**：位置が大きくずれない。
    > 面を出入りしてカーソル位置がおおむね保たれるか

### 10-5 F-33 実機報告の修正・続き

道順：詳細メニュー →「執筆AI支援」→ 原稿づくり →「組んで書く」（**必ず「作品一覧」の話の行から開く**。
　　　エクスプローラーから直接`.md`を開くと VS Code 1.131 の新しいMarkdown画面になり、
　　　原稿エディタが開けず「本文のファイルを開いてから実行してください」で止まる）
使う作品：いじめられっ子_確認用

1. **やること**：本文に「……」（三点リーダー2つ）がある場所を表示する。次に「…」の直後に文字を打つ。
   **見るところ**：点列の間が不自然に開いていないか。「…」の直後に文字を打った瞬間、点が横倒し（横書き向き）にならないか。
   **合格**：間が均一で、横倒しにならない（一瞬なっても直後に直れば「見た目が直った」と書けばよい。本文自体は壊れない）。
   > 組んで書く面で「……」の点列の間が開かないか（作りを読む面と同じ素のspanへ変えた）。「…」の直後に字を打って横倒しにならないか（伝染対策。なっても本文は無事・組み直しで直る）
2. **やること**：設定資料パネルを開いたまま、本文の別の用語の上で右クリックする。次に、パネルを閉じた状態で同じ操作をする。
   **見るところ**：パネルが開いている場合は右クリックした瞬間に該当項目へ切り替わるか。閉じている場合は切り替わらず、品書きの「設定資料を見る」で初めて開くか。
   **合格**：開いている時は自動で切り替わり、閉じている時は切り替わらない。
   > 用語の上で右クリックした瞬間に、開いている設定資料パネルが該当項目へ切り替わるか。閉じているときは切り替わらず、品書きの「設定資料を見る」で開くか
3. **やること**：上の2で切り替わらなかった場合、`.aiwriter/logs/actions.log` を開いて該当箇所を探す。
   **見るところ**：「原稿エディタ：…作品を見つけられませんでした」か「設定資料パネル：…画面へ送りました」のどちらかが記録されているか。
   **合格**：どちらかの文言が記録されている（記録が無ければそれも報告する）。
   > 切り替わらない場合：ログに「原稿エディタ：…作品を見つけられませんでした」か「設定資料パネル：…画面へ送りました」が出ているか（切り分けの材料。書庫では作品違いの2枚目が開く疑いあり）
4. **やること**：用語の上で右クリックする。
   **見るところ**：出てきた品書きの一番上の行に、用語名（例：「三門太志」）自体が表示されていないか。
   **合格**：一番上に用語名が出ない（「設定資料を見る」などの操作名から始まる）。
   > 右クリックの品書きの先頭に用語名の行が無いか
5. **やること**：原稿エディタ（組んで書く面）を開いて画面右下を見る。
   **見るところ**：「最新話を書く」ボタンが右下にあるか。以前あったはずの色の凡例が消えているか。
   **合格**：ボタンが右下にあり、色の凡例は表示されていない。
   > 「最新話を書く」が画面右下にあるか。色の凡例が消えているか
6. **やること**：設定資料パネルを開き、登場人物・能力・組織・場所の各タブを見る。できれば明るいテーマと暗いテーマの両方で見比べる。
   **見るところ**：各タブの色が本文中の同じ種類の用語の色と一致するか。両テーマで文字が読めるか。いま選ばれているタブ（下線＋太字）が分かるか。
   **合格**：色が一致し、両テーマで読め、選択中タブが分かる。
   > 設定資料パネルのタブ（登場人物・能力・組織・場所）が本文の用語と同じ色か。明・暗の両テーマで読めるか。選択中タブ（下線＋太字）が分かるか
7. **やること**：縦書きの「組んで書く」面を開き、日本語入力の変換中の状態を作る（文字を打って変換候補が出ている状態で止める）。
   **見るところ**：変換中を示す下線が、縦書きの文字の右側に出るか。
   **合格**：下線が右側に出る。
   > 縦書きの組んで書く面で、変換中の下線が右側に出るか（textarea側は既知の不可。組んで書く面は今回が初確認）

### 報告の形

節番号-項目番号ごとに1行、合格／不合格／判断待ちのいずれかと、見えたものを書けばよい。

```
A-13-3：合格
A-13-4：不合格。縦書きで「…」の点が横に倒れた（スクリーンショットあり）
A-13-5：判断待ち。～が見当たらなかった
```

### 押してはいけないもの

- **本物の作品**（名前の末尾に「_確認用」が付かないもの）に対する、書き換えを伴う操作全般
  （文字を打つ・保存する・ルビを振る・まとめる、など）。
- 「GitHubと同期」「まとめて同期」。作者の判断で押すのは構わないが、この台本ではお願いしない。
