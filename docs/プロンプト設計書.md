## 第1部　共通設計方針

### 1.1 プロンプト管理方式

プロンプトはコード内にハードコードせず、`prompts/` 配下に機能単位のファイルとして分離する。

```
prompts/
├─ _common/
│  ├─ base_system.md          ← 全機能共通のシステムプロンプト
│  ├─ output_rules.md         ← JSON出力ルール
│  └─ context_rules.md        ← 設定情報の参照ルール
├─ plot_advice.md             ← P-01
├─ plot_reverse.md            ← P-02
├─ world_extract.md           ← P-03a（Map）
├─ world_merge.md             ← P-03b（Reduce）
├─ character_extract.md       ← P-04a
├─ character_merge.md         ← P-04b
├─ location_extract.md        ← P-05a
├─ location_merge.md          ← P-05b
├─ synopsis_work.md           ← P-06
├─ synopsis_chapter.md        ← P-07
├─ catchphrase.md             ← P-08
├─ typo_check.md              ← P-09
├─ proofread.md               ← P-10
├─ deviation_check.md         ← P-11
├─ contradiction_check.md     ← P-12
├─ notation_check.md          ← P-13
├─ commit_message.md          ← P-14
├─ file_parse.md              ← P-15
├─ reading_estimate.md        ← P-16
└─ appearance_structure.md    ← P-17
```

各ファイルはYAMLフロントマターでメタ情報を持つ。

```markdown
---
id: P-04a
name: 登場人物抽出（チャンク単位）
version: 1.0
min_capability_tier: standard   # これ未満のティアでは警告を表示（実行は可能）
recommended_tier: high          # 併用時の最適配分の参考値。単一運用では無視される
has_light_variant: true         # typo_check.light.md 相当の簡易版を持つか
max_input_chars: 20000          # ティアに応じてAIRouterが自動縮小する
output_format: json
temperature: 0.2
---
（以下、プロンプト本文）
```

変数の埋め込みは `{{変数名}}` 形式とし、拡張機能側のテンプレートエンジンで置換する。

### 1.2 全機能共通のシステムプロンプト（`_common/base_system.md`）

```
あなたは日本語の小説執筆を支援する編集アシスタントです。

【絶対に守る原則】
1. 本文に書かれていない情報を推測で補って断定しないこと。根拠が本文にない場合は
   該当フィールドを null または空配列とし、確信度(confidence)を low とすること。
2. 作者の文体・表現の好みを尊重すること。あなたの好みで書き換えを提案しない。
3. 指摘や提案を行う際は、必ず本文中の該当箇所を特定できる情報
   （引用文・行番号）を添えること。
4. 出力は指定されたJSON形式のみとし、前置き・後書き・説明文・
   マークダウンのコードフェンスを一切含めないこと。
5. 作品世界の設定（造語、固有名詞、独自の言い回し）を誤字や誤りとして
   扱わないこと。判断に迷う場合は指摘せず、confidence を low にすること。
```

原則5は特に重要で、これがないと「魔導書庫」「リヴェルス」といった造語を片端から誤字指摘してくる。既存の登場人物一覧・場所一覧・世界観まとめを固有名詞辞書としてプロンプトへ注入し、既知語として保護する。

### 1.3 出力形式ルール（`_common/output_rules.md`）

- 全機能でJSON出力を強制する。GeminiとClaudeは構造化出力/JSONモードを使用。
- Ollamaは指示追従が不安定なため、以下の多段フォールバックを実装する。
  1. コードフェンス（```json）の除去
  2. 最初の `{` から最後の `}` までを抽出して再パース
  3. パース失敗時、「JSONのみを出力してください」という指示を添えて1回だけ再試行
  4. なお失敗する場合は、当該チャンクを「解析失敗」として記録し処理を継続（全体を止めない）
- 全JSONに共通フィールドとして以下を持たせる。

```json
{
  "schema_version": "1.0",
  "confidence": "high | medium | low",
  "notes": "AIからの補足（任意、空文字可）"
}
```

### 1.4 コンテキスト注入ルール（`_common/context_rules.md`）

1000万字規模を扱うため、「本文を全部渡す」ことは前提としない。各機能に渡す情報は以下の優先順位で構成し、トークン上限に応じて下位から削る。

| 優先 | 内容 | 備考 |
|---|---|---|
| 1 | 処理対象チャンク本文 | 必須 |
| 2 | 固有名詞辞書（人物名・場所名のみの軽量リスト） | 誤指摘防止に必須。名前だけなので軽い |
| 3 | プロット要約（ログライン・テーマ・人称・行動原理） | 500字程度に圧縮 |
| 4 | 直前チャンクの末尾（500字程度） | 文脈の連続性確保 |
| 5 | 関連する登場人物・場所の詳細 | チャンク内に登場する人物・場所のみに絞る |
| 6 | 世界観まとめ要約 | 矛盾検知時は優先度を2に引き上げ |

優先度5が重要な節約ポイントで、キャラクターが100人いても、当該チャンクに出てくる5人分だけを渡す。事前の固有名詞マッチングで絞り込む。

### 1.5 Map-Reduce型処理

一覧生成系（世界観・登場人物・場所）は2段構成とする。

```
[Map段階]  チャンク1 → 抽出プロンプト → 中間JSON1
           チャンク2 → 抽出プロンプト → 中間JSON2   ← 並列実行可
           チャンクN → 抽出プロンプト → 中間JSON N
                              ↓
[Reduce段階] 中間JSON群 + 既存の一覧 → 統合プロンプト → 更新後の一覧
```

- Map段階の中間JSONは `.aiwriter/cache/processed/` に保存する。次回実行時、ハッシュ一致のチャンクはMapをスキップしキャッシュを再利用する。
- Reduce段階は、変更のあった中間JSONと既存一覧のみを入力とする。全チャンクの中間JSONを再投入しない。
- 中間JSONが多すぎてReduce段階が入力上限を超える場合は、階層的Reduce（20件ずつ統合→さらに統合）を行う。

### 1.6 作者加筆の保護

自動生成のマージ時、以下は絶対に上書きしない。プロンプト側とコード側の二重で保護する。

- `author_notes` フィールド
- `auto_generated: false` が設定されたレコード・フィールド
- 作者が手動編集したことをハッシュ差分で検出したフィールド

プロンプトには「以下のフィールドは作者が記述したものです。内容を変更・削除・要約しないでください」と明示し、加えてマージ処理コード側でも該当フィールドを既存値で強制的に上書き復元する。AIの指示追従を信用しきらない設計とする。

### 1.7 プロバイダ選択への対応

**すべてのプロンプトは、単一プロバイダのみで全機能が動作することを前提に設計する。** 各機能の `recommended_provider` はあくまで推奨であり、必須要件ではない。設定で選ばれたプロバイダが何であれ、全機能が実行可能でなければならない。

そのため、プロンプトはプロバイダ名ではなく**能力ティア**（`capabilityTier`）に対して最適化する。プロバイダが変わってもティアが同じならプロンプトは変わらない。

```
prompts/
├─ typo_check.md            ← 標準版（high / standard ティア用）
└─ typo_check.light.md      ← 簡易版（light ティア用）
```

`.light.md` が存在しない機能では、light ティアでも標準版を使用する（要約系など、簡易化の必要がないもの）。

**簡易版プロンプトの作成方針**

| 項目 | 標準版 | 簡易版（light） |
|---|---|---|
| 指示の分量 | 詳細な条件・除外規則を列挙 | 核心的な指示のみに絞る |
| 出力スキーマ | ネスト構造・複数フィールド可 | フラット構造、フィールド数を最小化 |
| 一度の処理量 | チャンク全体 | さらに小さく分割 |
| 例示 | 不要 | 出力例を1つ明示（形式追従性が上がる） |

**推奨プロバイダの位置づけ**

以下は「複数を併用できる場合の最適配分」であり、単一運用時には無視してよい。設定画面でも、機能別割当モードを有効にした場合のみ参考情報として表示する。

| 機能 | 推奨 | 理由 |
|---|---|---|
| 誤字脱字・表記ゆれ・コミットメッセージ | light で十分 | 単純タスク。件数が多くコストがかさむ |
| 各話あらすじ | standard | 量が多く、要約は軽量でも成立する |
| 登場人物・場所抽出 | standard 以上 | 抽出漏れが後工程に響く |
| 矛盾検知・逸脱検知 | high 推奨 | 長文横断の論理的整合性判断が必要 |
| プロット助言・キャッチコピー | high 推奨 | 対話品質・表現の質が直接成果物になる |

### 1.7.1 単一プロバイダ運用時の注意

**Ollamaのみで運用する場合**、以下の機能は精度が落ちる。禁止はせず、実行前に一度だけ注意を表示したうえで使えるようにする。

- 矛盾検知（P-12）：長文横断の照合が必要なため、検出漏れが増える
- プロット逸脱検知（P-11）：抽象的な判断が必要なため、的外れな指摘が混じりやすい
- キャッチコピー（P-08）：日本語表現の質が下がりやすい

対策として、light ティアでは以下を自動適用する。

- 矛盾検知の検証項目を6項目から3項目（人物の一貫性・状態・時系列）へ絞り、1回のリクエストの負荷を下げる
- 逸脱検知は「間延び」を既定でOFFにし、より判定しやすい「プロット逸脱」のみを対象とする
- キャッチコピーは3案を1リクエストではなく、方向性ごとに3回に分けて生成する

**Geminiのみ・Claudeのみで運用する場合**は、全機能を標準版プロンプトで実行できる。ただし全処理が課金対象になるため、誤字脱字検知のような高頻度実行機能では、実行前のコスト見積もり表示（第3部3.3）が特に重要になる。

### 1.8 temperature 方針

| 用途 | temperature | 対象 |
|---|---|---|
| 検出・抽出系 | 0.0〜0.2 | 誤字、矛盾、人物抽出、場所抽出 |
| 要約系 | 0.3 | あらすじ、世界観まとめ |
| 創作・提案系 | 0.7〜0.9 | キャッチコピー、サブタイトル、プロット助言 |

### P-01　プロットモード助言

**目的**：新規作品のプロット作成を対話で支援する。
**推奨**：Claude / temperature 0.7 / ストリーミング表示

**入力**：現在の `plot.md` の記入状況（未記入項目を含む）、作者の直近の発言、対話履歴（直近10ターン）

**出力**：JSONではなく自然文（対話のため）。ただし末尾に構造化提案がある場合のみ、区切り記号 `---SUGGESTION---` 以降にJSONを付与する。

```
あなたは経験豊富な小説の編集者です。作者がプロットを組み立てるのを対話で支援します。

【現在のプロット記入状況】
{{plot_current}}

【未記入の項目】
{{plot_empty_fields}}

【作者の発言】
{{user_message}}

【あなたの振る舞い】
- 作者の作りたいものを引き出すことを最優先とし、あなたのアイデアで上書きしないこと。
- 一度に多くを聞かない。質問は1〜2個までとする。
- 未記入項目がある場合、次に考えるとよい項目を1つだけ提案する。
  推奨順序：ログライン → テーマ → 主人公の行動原理 → 舞台・世界観 →
  あらすじ → 主要登場人物 → モチーフ → 人称 → タイトル
- 作者の記述に曖昧さや矛盾がある場合は、否定せずに質問の形で確認する。
  例：「主人公の行動原理は『復讐』とありますが、あらすじの終盤で彼が敵を許すのは、
  どのような心境の変化によるものでしょうか」
- ログラインは「誰が」「どんな状況で」「何を目指し」「何が障害か」の4要素を
  満たしているか確認する。
- テーマとあらすじが噛み合っているかを常に意識し、ずれていれば指摘する。
- 「面白いですね」のような中身のない相槌を返さない。必ず具体的な内容に踏み込む。

【提案を確定できる場合】
作者の発言から特定の項目に書き込める内容が確定した場合、回答の末尾に
---SUGGESTION--- を出力し、その後に以下のJSONを出力する。
{"field": "対象項目名", "value": "書き込む内容"}
確定していない場合はJSONを出力しない。
```

**後処理**：`---SUGGESTION---` 以降を検出したら、該当項目への反映確認UIを表示する。作者が承認した場合のみ `plot.md` へ書き込む。

### P-02　プロット逆算生成（既存作から）

**目的**：既存の本文全体からプロットを推定生成する。
**推奨**：Gemini Pro（長文コンテキスト）/ temperature 0.3
**構成**：Map-Reduce

**Map段階（チャンクごと）**

```
以下は小説の一部です。プロット逆算のための要素を抽出してください。

【本文】
{{chunk_text}}

【抽出項目】
- この範囲で起きた出来事（時系列順、最大5件、各50字以内）
- 登場した人物名
- 登場した場所名
- 読み取れるテーマの手がかり（作品が問いかけている主題、あれば）
- 語りの人称（一人称／三人称一元／三人称多元／その他）と、
  一人称の場合は主人公の自称
- 主人公と思われる人物の、この範囲での行動の動機

【出力形式】JSONのみ
{
  "events": [{"order": 1, "summary": "..."}],
  "characters": ["..."],
  "locations": ["..."],
  "theme_hints": ["..."],
  "narrative_person": "...",
  "protagonist_motive": "...",
  "confidence": "high|medium|low"
}
```

**Reduce段階**

```
以下は、ある小説の全編から抽出した要素です。これらを統合し、
作品全体のプロットを再構成してください。

【抽出済み要素】
{{merged_extracts}}

【出力するプロット項目】
- title: 既存タイトル（{{existing_title}}）をそのまま使用
- logline: 作品全体を一文で表す（80字以内）
- theme: この作品が問いかけている主題（100字以内）
- motif: 繰り返し現れる象徴・題材（配列、最大5件）
- worldview: 世界の成り立ち・法則（200字以内）
- setting: 主な舞台（100字以内）
- narrative_person: 語りの人称
- protagonist_motive: 主人公の行動原理（100字以内）
- plot_outline: あらすじの箇条書き（配列、各60字以内、最大20件、時系列順）
- main_characters: 主要人物（配列、name と summary。summaryは60字以内）

【注意】
- 本文から読み取れないものは推測で埋めず、null または空配列とすること。
- 特にテーマとモチーフは、作者の意図を勝手に断定しないこと。
  複数の解釈が可能な場合は、最も本文の記述量が多いものを選び、
  notes に他の可能性を記載すること。

【出力形式】JSONのみ
```

**後処理**：生成結果を `plot.md` へ書き込む前に差分プレビューを表示する。既に作者記述がある項目は上書き候補として別枠に表示し、既定では上書きしない。

### P-03　世界観まとめ生成

**目的**：ジャンル、時代背景、世界の法則等をまとめる。
**推奨**：Gemini Pro / temperature 0.3

**Map段階**

```
以下の小説本文から、世界観に関わる記述のみを抽出してください。
物語の出来事そのものではなく、「その世界がどうなっているか」の情報を集めます。

【本文】
{{chunk_text}}

【既知の世界観設定】（重複記載を避けるため参照）
{{known_worldview_summary}}

【抽出対象】
- ジャンル的特徴（現代/異世界/SF/歴史 など、判断根拠となる記述）
- 時代背景（年代、文明水準、技術水準）
- 世界の法則（魔法・超能力・特殊技術の仕組み、その制約や代償）
- 社会構造（国家、身分制度、組織、経済、通貨）
- 文化・風習（宗教、言語、暦、儀礼）
- 地理（大陸、気候、地形の特徴）
- 固有の用語・造語とその意味

【重要】
既知の世界観設定に既に含まれる情報は出力しないこと。新規情報のみを抽出する。
本文中に明記されていない設定を補完・創作しないこと。

【出力形式】JSONのみ
{
  "items": [
    {
      "category": "genre|era|rule|society|culture|geography|term",
      "content": "...",
      "evidence": "根拠となる本文の引用（30字以内）",
      "confidence": "high|medium|low"
    }
  ]
}
```

**Reduce段階**では、抽出項目をカテゴリごとに統合し、`world.md` の見出し構造に沿ったMarkdownを生成する。作者が加筆した段落（`<!-- author -->` コメントで区切る）は保持する。

### P-04a　登場人物抽出（チャンク単位）

**version**：2.5（実装は `src/prompts/characterExtract.ts`。本文はそちらが正）
**目的**：各チャンクから、本文に根拠のある人物情報だけを抽出する。
**推奨**：Claude / temperature 0.2

**実装との差**：設計時は人物だけを抽出する想定だったが、実装では**人物・能力・場所を1回の呼び出しでまとめて抽出する**。種別ごとにAIを呼ぶと同じ本文を3回読ませることになり、時間もコストも3倍かかるため。定数名とファイル名が `character` のままなのは、キャッシュキーと既存のimportへの影響を抑えるため。

**Map段階**

```
以下の小説本文から、登場人物の情報を抽出してください。人物以外は出力しません。

【本文】（第{{chapter_numbers}}話）
{{chunk_text}}

【既知の登場人物】（同一人物の判定に使用）
{{known_character_names_with_aliases}}

【抽出ルール】
- 各候補を entityType: person / group / location / unknown に分類する。characters に
  出力してよいのは person だけであり、それ以外はレコードを作らない。
- 一人称・二人称などの代名詞、汎用的な役職語、家族関係語、集団、場所、組織、種族、
  生物種は人物として出力しない。本文で特定の名前を確認できない話者の名前を発明しない。
- 同一人物が別の呼称で登場する場合、本名／通称／あだ名を既知の登場人物と照合する。
  同一と判断できる場合は既知の名前を name、本文の別呼称を aliases に入れる。
- 各項目は、この本文範囲から読み取れる内容のみを書くこと。
  読み取れない項目は null とする。
- evidence は各人物に必須とし、本文からそのまま抜き出した短い逐語引用にする。説明・要約・
  推測を evidence に書かない。

【抽出項目】
- name: 主たる呼称
- entityType: person（人物だけを出力するため常に person）
- aliases: 別の呼び方（配列）
- reading: 読み仮名。**名前に漢字を含む場合だけ**書く。カタカナ・ひらがなだけの
  名前は null でよい（コード側で機械的に作るため）
- summary: 何者かが一目で分かる紹介（**50字以内**）。一覧で名前の下に並べる1行
- affiliation: 所属する組織・部署を本文の表記のまま。職業や身分は role へ
- gender: 性別。**本文から確認できる場合だけ**書く。
  ・男性なら "男性"、女性なら "女性"。本文が「男」「少年」でもこの2語に揃える
  ・どちらでもない場合だけ本文の記載に合わせる
  ・**名前の響きから推測しない。** 造語の名前は判断できないのが普通である
  ・一人称（俺／僕／私）だけを根拠にしない。使い分けは作品によって異なる
  ・根拠が無ければ null。空欄のほうが誤った断定より害が少ない
- role: 物語上の役割（主人公／主要人物／敵対者／脇役 等）
- personality: 性格。行動の動機を含めて記述（120字以内）
- appearance: 外見の描写（100字以内）
- firstPerson: 本人が使う一人称
- defaultSecondPerson: 特定の相手を持たない一般的な呼びかけ（例：君、お前、あなた）
- addressTerms: **この人物が他の人物をどう呼んでいるか**（後述の呼称抽出ルール参照）
- relations: 他の人物との関係（配列、{"name": "...", "relation": "..."}）
- evidence: 抽出根拠となる本文の引用（30字以内）

【呼称の抽出ルール】（重要）
呼称は「誰が誰をどう呼んだか」の方向を持つ情報です。以下に従って抽出してください。

1. 会話文・心内語の中で、ある人物が別の人物を呼んだ表現をすべて拾うこと。
   例：「白瀬さん、それは違う」→ 話者が白瀬を「白瀬さん」と呼んでいる
2. **同じ相手に複数の呼び方がある場合、すべて記録すること。**まとめたり
   代表的なもの1つに絞ったりしないこと。
   例：平時は「澪」、怒った時は「白瀬」、人前では「白瀬さん」→ 3件すべて記録
3. 使い分けの条件が本文から読み取れる場合は context に記述する。
   読み取れない場合は context を null とし、まとめないこと。
4. 話者が誰かを特定できない発話の呼称は抽出しないこと。
   推測で話者を決めつけないこと。
5. 呼称に含まれる敬称・接尾辞（さん、くん、様、ちゃん、先輩、殿）は
   省略せず、本文に出てきた形のまま記録すること。
6. category には以下のいずれかを設定する。
   姓+敬称／名+敬称／姓のみ／名のみ／フルネーム／あだ名／役職・続柄／
   蔑称／一般代名詞／その他
7. 地の文での呼び方は、一人称視点作品の場合のみ「語り手による呼称」として
   抽出してよい。三人称の地の文は作者の記述であり、呼称ではないため抽出しない。

【出力形式】JSONのみ
{
  "characters": [
    {
      "name": "...",
      "entityType": "person",
      "aliases": ["..."],
      "reading": "つきしまあかり",
      "summary": "...",
      "affiliation": "...",
      "gender": "女性",
      "role": "...",
      "personality": "...",
      "appearance": "...",
      "firstPerson": "僕",
      "defaultSecondPerson": "君",
      "addressTerms": [
        {
          "targetName": "白瀬 澪",
          "term": "白瀬さん",
          "category": "姓+敬称",
          "context": "使い分けの条件（不明なら null）",
          "evidence": "「白瀬さん、それは違う」"
        }
      ],
      "relations": [{"name": "...", "relation": "..."}],
      "evidence": "..."
    }
  ],
  "confidence": "high|medium|low"
}
```

**品質ゲート**：`test/fixtures/character-extraction/balanced.json` の固定応答を
`parseResult` → `validateCharacterExtractResult` → `mergeExtractedCharacters` に通す。
`npm run test:quality` は recall 1、falsePositives 0、falseMerges 0、
authorProtectionViolations 0 を必須しきい値とする。fixtureは姓名・名・敬称付き呼称の
同一identity、同じ名を持つ別identity、代名詞・役職・関係語・集団・場所・組織・種族、
`autoGenerated: false` とロック済み呼称、複数章の登場話数・呼称期間を含む。
誤検出は生成された全identityを期待identityと照合して数え、誤統合はidentity間の混同と
同一identityの分裂を数える。別名の欠落は誤統合へ含めず、独立した期待値で検証する。

{{new_extracts_json}}

2. 呼称の整合：ある人物が別の人物を呼ぶ呼び方が、確立された呼称と食い違わないか。
   特に、関係の変化に伴って呼び方が変わった後で、理由なく古い呼び方に
   戻っていないか。ただし喧嘩・他人行儀になる場面・第三者の目がある場面など、
   意図的に呼び方を変える演出は矛盾ではありません。判断がつかない場合は
   confidence を low とすること。
3. 人物の状態：既に死亡・離脱した人物が登場していないか、負傷や状態変化が
   引き継がれているか
4. 場所の整合：地理関係、移動距離と所要時間、場所の描写が設定と一致するか
5. 世界法則：魔法や技術の制約・代償が、確立されたルールを破っていないか
6. 時系列：季節、時刻、経過日数、人物の年齢が矛盾していないか
7. 既出情報：以前の話で描かれた事実と食い違う記述がないか
【判断の注意】
- 作中で意図的に描かれた変化（成長による口調の変化、設定の秘密が明かされる等）を
  矛盾と誤認しないこと。判断がつかない場合は confidence を low とし、
  「意図的な変化の可能性」を note に記載すること。
- 未回収の伏線は矛盾ではありません。
- 設定側が誤っている可能性も考慮し、指摘は断定形にしないこと。

【出力形式】JSONのみ
{
  "contradictions": [
    {
      "line": 42,
      "excerpt": "該当箇所の引用（40字以内）",
      "category": "人物|呼称|状態|場所|世界法則|時系列|既出情報",
      "setting_says": "設定ではどうなっているか",
      "text_says": "本文ではどうなっているか",
      "note": "補足（意図的な変化の可能性など）",
      "severity": "high|medium|low",
      "confidence": "high|medium|low"
    }
  ]
}
```

**後処理**：矛盾指摘には「本文を直す」「設定を直す」の2つの解決導線を用意する。設定側が古い場合があるため、本文修正だけを提示しない。

### P-16　読み仮名・ローマ字の推定（設定資料エクスポート用）

**目的**：人物名・場所名・造語の読みを推定する。映像化・翻訳向け資料では読み方が必須になるが、本文に読みが明示されていないことが多い。

```

【固有名詞一覧】
{{proper_nouns}}

{{usage_contexts}}

{{existing_ruby}}

【推定のルール】
- 本文中にルビ・ふりがな・読みの明示がある場合は、必ずそれに従うこと。
- 明示がない場合のみ推定し、confidence を medium 以下とすること。
- 人名は特に読みが一意に定まりません。複数の読み方が考えられる場合は
  alternatives に候補を列挙すること。
  例：「灯」→ あかり / ともり / ひ
- 作品の世界観（和風／西洋風／架空言語）を踏まえて推定すること。

【出力形式】JSONのみ
{

    {
      "term": "月島 灯",

### P-17　外見情報の構造化抽出（コミカライズ向け資料用）

**目的**：本文の描写から、作画に必要な外見情報を項目別に整理する。
**推奨**：standard 以上 / temperature 0.1

```
以下は、ある登場人物に関する本文中の描写を集めたものです。
作画資料として使えるよう、外見情報を項目別に整理してください。

【人物名】{{character_name}}
【本文中の描写】（登場箇所を抜粋）
{{appearance_excerpts}}

【整理する項目】
- age: 年齢（明示がなければ推定範囲。例「17歳前後」）
- height: 身長
- build: 体格
- hair: 髪（色、長さ、髪型）
- eyes: 瞳の色、目つき
- skin: 肌の色・特徴
- distinctive: 特徴的な要素（傷、痣、装身具など）
- clothing: 主な服装（場面によって異なる場合は場面ごとに）
- changes: 物語中で外見が変化する場合、その内容と話数

【重要】
- 本文に記述がない項目は必ず null とすること。推測で埋めないこと。
  作画資料では、書かれていない情報を「設定」として渡すと事故になります。
- 描写が話数によって食い違う場合は、統合せず両方を記載し、
  conflicts に記録すること。
- 各項目には根拠となる本文の引用と話数を添えること。

【出力形式】JSONのみ
{
  "physical": {
    "age": {"value": "...", "evidence": "...", "chapter": 1},
    "height": null
  },
  "changes": [{"chapter": 12, "content": "...", "evidence": "..."}],
  "conflicts": [{"item": "hair", "descriptions": ["...", "..."], "chapters": [3, 9]}],
  "confidence": "high|medium|low"
}
```

**後処理**：null の項目は資料上で「（描写なし）」と明記する。空欄にすると、受け取り側は「まだ決まっていない」のか「伝え忘れ」なのか判断できない。`conflicts` は矛盾検知パネルへも転送する。

### P-18　設定について相談する（設定資料パネル）

**version**：2.0（実装は `src/prompts/settingsChat.ts`）
**目的**：選んだ1件について、本文を根拠に作者と対話する。
**temperature**：0.5

設計時は「掘り下げ」と「質問」を別機能として構想していたが、実装では**1つにまとめた**。観点を渡して掘り下げさせるのと、質問して答えさせるのは、AIから見て同じ処理だったため。入力欄を空のまま実行すると、既定の観点（`DEFAULT_CHAT_TOPIC`）で全体を掘り下げる。

材料は、その設定が登場する場面の本文抜粋（`core/mentionExcerpts.ts`）と、現在の設定（`core/settingsSummary.ts`）。同じ材料をP-20でも使う。

**保存は承認制。** 返ってきた内容は画面に出すだけで、作者が「追記」を押したときだけ `aiNotes` に入る。掘り下げは本文の逐語照合ができない解釈であり、抽出結果と同じ扱いで自動保存すると、どこまでが本文に書いてあることなのか分からなくなる。

**既存の項目は書き換えない。** 追記されるのは `aiNotes` だけで、`role` や `personality` には触れない。

### P-20　設定項目の充実（設定資料パネル）

**version**：1.0（実装は `src/prompts/settingsEnrich.ts`）
**目的**：設定資料の**各項目に入れる値そのもの**を提案する。
**temperature**：0.3（設定として書くので、相談より控えめにする）

P-18が文章のメモを書くのに対し、こちらは項目を埋める。パネルのAI機能はこの2つだけで、両方とも同じ本文抜粋を材料にする。

提案する項目は種別ごとに決まっている（人物なら性別・紹介・所属・役割・性格・外見）。人物にはこれに加えて、**作者が定義した追加項目**（`設定/custom_fields.json`）が並ぶ。追加項目の説明文はそのままAIへ渡す。

**JSONスキーマでは全項目を必須にし、nullを許す。** 省略可能にすると、小さいモデルは面倒な項目を黙って落とす。nullを返させれば「読み取れなかった」と明示させられる。

**提案は保存しない。** 項目ごとに現在の値と並べて見せ、作者がチェックを入れたものだけを書き込む。既定でチェックが入るのは**空欄を埋める提案だけ**で、作者が書いた内容の置き換えは必ず自分で選ばせる。

**反映しても作者が確定させた記述としては扱わない**（`EditOptions.authorConfirmed`）。中身はAIが書いたものなので、以後の抽出で更新されてよい。作者確定にすると、その人物は以後の抽出から締め出され、書き進めても情報が増えなくなる。

**後処理**：AIは「不明」「なし」「N/A」を値として返してくることがあるので、空欄と同じ扱いにする。文字数制限のある項目（紹介の50字）はコード側で切り詰める。

## 第3部　運用設計

### 3.1 プロンプトのバージョン管理

- 各プロンプトファイルの `version` を、生成結果のキャッシュメタデータに記録する。
- プロンプトを更新した場合、旧バージョンで生成されたキャッシュは「再生成可能」とマークするが、自動では再実行しない（コスト保護）。作者が明示的に「再生成」を選んだ時のみ実行する。

### 3.2 品質評価の仕組み（提案）

プロンプトの改善には評価基準が必要になるため、以下を用意することを提案する。

- `tests/fixtures/` に評価用の短編サンプル（既知の誤字・矛盾を意図的に埋め込んだもの）を配置する。
- 各プロンプトについて「検出すべき箇所」を正解データとして定義し、検出率と誤検出率を計測するコマンドを用意する。
- プロバイダ・モデルを変えて同一テストを実行し、機能ごとの推奨モデルを実測で決める。

これがないと、プロンプトを改良したつもりが実は悪化していた、という事態を検知できない。

### 3.3 コスト見積もりの表示

AI機能の実行前に、以下を確認ダイアログで提示する。

- 処理対象チャンク数（うちキャッシュ済みでスキップされる数）
- 推定入力トークン数・出力トークン数
- 推定コスト（プロバイダの単価設定に基づく。Ollamaは0円と表示）

10万字を超える範囲を対象とする場合は、既定で確認を必須とする。

### 3.4 失敗時の扱い

- チャンク単位で失敗した場合、全体を中断せず、失敗チャンクを記録して続行する。
- 処理完了後に「N件のチャンクで解析に失敗しました」と報告し、再試行できるようにする。
- APIレート制限に達した場合は指数バックオフで待機し、上限回数を超えたら中断して途中結果を保存する。

## 第4部　未確定事項・要相談

1. **プロット逸脱検知の厳しさ**：どの程度の逸脱を指摘してほしいかは作者の好みが大きく分かれます。設定で「厳しめ／標準／緩め」を切り替えられるようにする案を提案します。
2. **推敲の範囲**：現状「明らかに読みにくい箇所のみ」に絞っていますが、実際に使ってみて物足りない場合は対象を広げます。まずは狭く始めることを推奨します。
3. **呼称抽出の前提となる話者推定**：呼称は「誰が誰を呼んだか」の情報であり、抽出には話者の特定が不可欠です。会話文が連続して地の文による話者明示がない箇所（「〜」「〜」と応酬が続く場面）では、話者の取り違えが起きやすくなります。

   対策として、以下の構成を提案します。精度が出ない場合はこちらへ切り替えます。
   - 話者推定を独立したプロンプト（P-16）として切り出し、会話文ごとに話者と確信度を判定させる
   - 話者が特定できた会話文のみを呼称抽出の入力とする
   - 一人称視点作品では語り手＝話者が確定するため、視点情報をプロンプトへ渡して精度を上げる

   なお現状のP-04では「話者を特定できない発話の呼称は抽出しない」と指示しており、取りこぼしはあっても誤登録は避ける方針としています。
4. **チャンク分割の単位**：既定は「1話単位、超過する場合は約2万字で分割」を想定していますが、シーン区切り（空行や記号による区切り）を優先する方式も検討可能です。
