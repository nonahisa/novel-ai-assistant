## この文書の読み方

**プロンプトの本文は、この文書ではなく `src/prompts/*.ts` にある。** 食い違ったら実装が正である。ここに載せるのは、そのプロンプトが**何を狙っていて、なぜその形なのか**である。

各 P-XX は次の順で書く。

| 順 | 中身 |
|---|---|
| 1 | **version・目的・推奨モデル・temperature**（versionは実装の `*_VERSION` 定数と揃える） |
| 2 | **入力・出力・プロンプト本文** |
| 3 | **後処理**（コード側で何を検証・修正するか） |
| 4 | **`#### P-XX の経過`**（読み飛ばして構わない） |

柵の中の `{{chunk_text}}` のような書き方は、**「ここに値が入る」ことを示す読み方の約束**である。実装がテンプレートエンジンを使っているという意味ではない（1.1）。

### 経過は末尾へ畳む。ただし消さない

**プロンプトの一行一行は、実データで失敗した記録である。** 理由を消すと、あとから読んだ人が「この指示は冗長だ」と判断して外し、同じ失敗が戻る。だから経過は残す。

ただし**プロンプト本文と混ぜない。** 以前はP-04aで、経過がコード柵（プロンプト本文を示す枠）の**中**に入っており、送っていない文章が送っているように読めた。**柵の中には、送っている文だけを置く**（`test/unit/promptDocShape.test.ts` が見ている）。

## 第1部　共通設計方針

### 1.1 プロンプト管理方式

**プロンプトは TypeScript として `src/prompts/` に置く。**

```
src/prompts/
├─ characterExtract.ts   P-04a（人物・能力・組織・場所・世界観を1回で。P-03を含む）
├─ plotReverse.ts        P-02
├─ blurb.ts              P-06
├─ synopsis.ts           P-07
├─ typoCheck.ts          P-09
├─ proofread.ts          P-10
├─ deviationCheck.ts     P-11
├─ contradictionCheck.ts P-12（裏取りは contradictionVerify.ts）
├─ settingsChat.ts       P-18
├─ settingsEnrich.ts     P-20
├─ workChat.ts           P-21
├─ searchTerms.ts        P-22
├─ recheck.ts            P-23
├─ openingCheck.ts       P-24
├─ foreshadowDetect.ts   P-25
├─ foreshadowResolve.ts  P-26
└─ nameSuggest.ts        P-29
```

**Markdownのファイルにも、YAMLフロントマターにも、テンプレートエンジンにもしなかった。**

- 埋め込む値は関数の引数で渡す（`buildCharacterExtractPrompt({ chunkText, chapterLabel, knownCharacterNames })`）。`{{変数名}}` の置換だと、**渡し忘れがそのまま `{{…}}` の文字列としてAIへ届く**。引数なら型検査で止まる
- 字数の上限などは、コード側の定数から埋め込む（紹介の80字は `core/summaryLimit.ts` の `SUMMARY_MAX_CHARS`）。**2か所に書くと必ずずれる**
- モデルによって送り方が違う部分（Ollamaの `format`、OpenAI互換の `response_format`、Anthropicの `tools`）は `ai/jsonSchema.ts` が吸収する

**版は `*_VERSION` 定数で持つ。**

```ts
export const CHARACTER_EXTRACT_VERSION = "5.1";
```

チャンクのキャッシュの鍵は **`promptVersion|providerId|model|chunkHash`**（`core/chunkCache.ts`。`providerId` は0.24.4の機能別割当で追加——設計書6.28.9）である。したがって、

- **プロンプトを変えたら、必ずこの定数を上げる。** 上げないと、古い指示で作られた応答がキャッシュから返り続ける
- **上げると、その機能のキャッシュは全部無効になる。** 作品によっては数十〜数百回のAI呼び出しが発生する（Ollamaなら無料だが数十分、クラウドAIでは課金される）。**字数を1つ変えるだけでも同じ**なので、版を上げる変更はまとめて入れる
- 逆に、同じプロバイダ・同じモデル・同じ版なら**AIは1回も呼ばれない**。設定資料の作り直しが安く済むのはこのため

**再生成は自動で行わない。** 版が上がってもキャッシュは「作り直せる」と印を付けるだけで、実行するのは作者が選んだときである（コスト保護）。


### 1.2 全機能共通のシステムプロンプト

実装は `src/prompts/characterExtract.ts` の `BASE_SYSTEM_PROMPT`。

```
あなたは日本語の小説執筆を支援する編集アシスタントです。

【絶対に守る原則】
1. 本文に書かれていない情報を推測で補って断定しないこと。根拠が本文にない場合は
   該当フィールドを null または空配列とし、確信度(confidence)を low とすること。
2. 作者の文体・表現の好みを尊重すること。あなたの好みで書き換えを提案しない。
3. 指摘や提案を行う際は、必ず本文中の該当箇所を特定できる情報
   （引用文・行番号）を添えること。
4. 出力は指定されたJSON形式のみとし、前置き・後書き・説明文・
   マークダウンのコードフェンスを一切含めないこと。
5. 作品世界の設定（造語、固有名詞、独自の言い回し）を誤字や誤りとして
   扱わないこと。判断に迷う場合は指摘せず、confidence を low にすること。
```

原則5は特に重要で、これがないと「魔導書庫」「リヴェルス」といった造語を片端から誤字指摘してくる。既存の登場人物一覧・場所一覧・世界観まとめを固有名詞辞書としてプロンプトへ注入し、既知語として保護する。

### 1.3 出力形式ルール

- 全機能でJSON出力を強制する。Gemini・ChatGPT・Claudeは構造化出力/JSONモードを使用し、Ollamaは `format` にJSONスキーマを渡す。**スキーマの書き方は各社で異なる**ため、設計書7.8節の変換層（`src/ai/jsonSchema.ts`）で送信直前に方言へ直す。プロンプト側は1つの書き方だけを持つ。
- Ollamaは指示追従が不安定なため、以下の多段フォールバックを実装する。
  1. コードフェンス（```json）の除去
  2. 最初の `{` から最後の `}` までを抽出して再パース
  3. パース失敗時、「JSONのみを出力してください」という指示を添えて1回だけ再試行
  4. なお失敗する場合は、当該チャンクを「解析失敗」として記録し処理を継続（全体を止めない）
- 全JSONに共通フィールドとして以下を持たせる。

```json
{
  "schema_version": "1.0",
  "confidence": "high | medium | low",
  "notes": "AIからの補足（任意、空文字可）"
}
```

### 1.4 コンテキスト注入ルール

1000万字規模を扱うため、「本文を全部渡す」ことは前提としない。各機能に渡す情報は以下の優先順位で構成し、トークン上限に応じて下位から削る。

| 優先 | 内容 | 備考 |
|---|---|---|
| 1 | 処理対象チャンク本文 | 必須 |
| 2 | 固有名詞辞書（人物名・場所名のみの軽量リスト） | 誤指摘防止に必須。名前だけなので軽い |
| 3 | プロット要約（ログライン・テーマ・人称・行動原理） | 500字程度に圧縮 |
| 4 | 直前チャンクの末尾（500字程度） | 文脈の連続性確保 |
| 5 | 関連する登場人物・場所の詳細 | チャンク内に登場する人物・場所のみに絞る |
| 6 | 世界観まとめ要約 | 矛盾検知時は優先度を2に引き上げ |

優先度5が重要な節約ポイントで、キャラクターが100人いても、当該チャンクに出てくる5人分だけを渡す。事前の固有名詞マッチングで絞り込む。

### 1.5 Map-Reduce型処理

一覧生成系（世界観・登場人物・場所）は2段構成とする。

```
[Map段階]  チャンク1 → 抽出プロンプト → 中間JSON1
           チャンク2 → 抽出プロンプト → 中間JSON2   ← 並列実行可
           チャンクN → 抽出プロンプト → 中間JSON N
                              ↓
[Reduce段階] 中間JSON群 + 既存の一覧 → 統合プロンプト → 更新後の一覧
```

- Map段階の中間JSONは `.aiwriter/cache/processed/` に保存する。次回実行時、ハッシュ一致のチャンクはMapをスキップしキャッシュを再利用する。
- Reduce段階は、変更のあった中間JSONと既存一覧のみを入力とする。全チャンクの中間JSONを再投入しない。
- 中間JSONが多すぎてReduce段階が入力上限を超える場合は、階層的Reduce（20件ずつ統合→さらに統合）を行う。

### 1.6 作者加筆の保護

自動生成のマージ時、以下は絶対に上書きしない。プロンプト側とコード側の二重で保護する。

- `author_notes` フィールド
- `auto_generated: false` が設定されたレコード・フィールド
- 作者が手動編集したことをハッシュ差分で検出したフィールド

プロンプトには「以下のフィールドは作者が記述したものです。内容を変更・削除・要約しないでください」と明示し、加えてマージ処理コード側でも該当フィールドを既存値で強制的に上書き復元する。AIの指示追従を信用しきらない設計とする。

### 1.7 プロバイダ選択への対応

**すべてのプロンプトは、単一プロバイダのみで全機能が動作することを前提に設計する。** 各機能の `recommended_provider` はあくまで推奨であり、必須要件ではない。設定で選ばれたプロバイダが何であれ、全機能が実行可能でなければならない。

そのため、プロンプトはプロバイダ名ではなく**能力ティア**（`capabilityTier`）に対して最適化する。プロバイダが変わってもティアが同じならプロンプトは変わらない。

ティア差の吸収は、プロンプトファイルを2本持つのではなく **`ai/capability.ts` の `capabilityProfile()` が返すフラグ**で行う（例：`narrowContradictionCategories`）。プロンプト本文は1本のまま、フラグに応じて指示や分類の幅を狭める。ファイルを分けると、直すとき必ず片方を忘れるため。

**簡易版プロンプトの作成方針**

| 項目 | 標準版 | 簡易版（light） |
|---|---|---|
| 指示の分量 | 詳細な条件・除外規則を列挙 | 核心的な指示のみに絞る |
| 出力スキーマ | ネスト構造・複数フィールド可 | フラット構造、フィールド数を最小化 |
| 一度の処理量 | チャンク全体 | さらに小さく分割 |
| 例示 | 不要 | 出力例を1つ明示（形式追従性が上がる） |

**推奨プロバイダの位置づけ**

以下は「複数を併用できる場合の最適配分」であり、単一運用時には無視してよい。機能別割当（0.24.4、設計書6.28.9）は**常時有効**で、「有効にするフラグ」は意図的に作っていない（キーが無ければ既定のAIを使う。フラグと中身の2か所が食い違うのを避けるため——`ai/registry.ts`）。割当キーは8つ：extract／typo／proofread／contradiction／deviation／foreshadow／generate／chat。割当画面への推奨ティアの参考表示は未実装。

| 機能（割当キー） | 推奨 | 理由 |
|---|---|---|
| 誤字脱字・表記ゆれ（typo）・コミットメッセージ | light で十分 | 単純タスク。件数が多くコストがかさむ |
| 各話あらすじ（generate） | standard | 量が多く、要約は軽量でも成立する |
| 登場人物・場所抽出（extract） | standard 以上 | 抽出漏れが後工程に響く |
| 矛盾検知（contradiction）・逸脱検知（deviation）・伏線検知（foreshadow） | high 推奨 | 長文横断の論理的整合性判断が必要 |
| 推敲（proofread）・プロット助言・キャッチコピー（generate）・相談（chat） | high 推奨 | 対話品質・表現の質が直接成果物になる |

### 1.7.1 単一プロバイダ運用時の注意

**Ollamaのみで運用する場合**、以下の機能は精度が落ちる。禁止はせず、実行前に一度だけ注意を表示したうえで使えるようにする。

- 矛盾検知（P-12）：長文横断の照合が必要なため、検出漏れが増える
- プロット逸脱検知（P-11）：抽象的な判断が必要なため、的外れな指摘が混じりやすい
- キャッチコピー（P-08）：日本語表現の質が下がりやすい

対策として、light ティアでは以下を自動適用する。

- 矛盾検知の検証項目を6項目から3項目（人物の一貫性・状態・時系列）へ絞り、1回のリクエストの負荷を下げる
- 逸脱検知は「間延び」を既定でOFFにし、より判定しやすい「プロット逸脱」のみを対象とする
- キャッチコピーは3案を1リクエストではなく、方向性ごとに3回に分けて生成する

**クラウドAI（Gemini・ChatGPT・Claude）のみで運用する場合**は、全機能を標準版プロンプトで実行できる。ただし全処理が課金対象になるため、誤字脱字検知のような高頻度実行機能では、実行前のコスト見積もり表示（第3部3.3）が特に重要になる。**Geminiの無料枠は毎分の呼び出し回数が少なく**、チャンク数の多い抽出系ではレート上限に当たる前提で待機込みの時間を見積もること（設計書7.8節）。

### 1.8 temperature 方針

| 用途 | temperature | 対象 |
|---|---|---|
| 検出・抽出系 | 0.0〜0.2 | 誤字、矛盾、人物抽出、場所抽出 |
| 要約系 | 0.3 | あらすじ、世界観まとめ |
| 創作・提案系 | 0.7〜0.9 | キャッチコピー、サブタイトル、プロット助言 |

### P-01　プロットモード助言

**実装状況**：**未実装。** プロットモード専用画面がまだ無い（引継ぎ書「未着手」）。以下は将来のための設計案である。

**目的**：新規作品のプロット作成を対話で支援する。
**推奨**：Claude / temperature 0.7 / ストリーミング表示

**入力**：現在の `plot.md` の記入状況（未記入項目を含む）、作者の直近の発言、対話履歴（直近10ターン）

**出力**：JSONではなく自然文（対話のため）。ただし末尾に構造化提案がある場合のみ、区切り記号 `---SUGGESTION---` 以降にJSONを付与する。

```
あなたは経験豊富な小説の編集者です。作者がプロットを組み立てるのを対話で支援します。

【現在のプロット記入状況】
{{plot_current}}

【未記入の項目】
{{plot_empty_fields}}

【作者の発言】
{{user_message}}

【あなたの振る舞い】
- 作者の作りたいものを引き出すことを最優先とし、あなたのアイデアで上書きしないこと。
- 一度に多くを聞かない。質問は1〜2個までとする。
- 未記入項目がある場合、次に考えるとよい項目を1つだけ提案する。
  推奨順序：ログライン → テーマ → 主人公の行動原理 → 舞台・世界観 →
  あらすじ → 主要登場人物 → モチーフ → 人称 → タイトル
- 作者の記述に曖昧さや矛盾がある場合は、否定せずに質問の形で確認する。
  例：「主人公の行動原理は『復讐』とありますが、あらすじの終盤で彼が敵を許すのは、
  どのような心境の変化によるものでしょうか」
- ログラインは「誰が」「どんな状況で」「何を目指し」「何が障害か」の4要素を
  満たしているか確認する。
- テーマとあらすじが噛み合っているかを常に意識し、ずれていれば指摘する。
- 「面白いですね」のような中身のない相槌を返さない。必ず具体的な内容に踏み込む。

【提案を確定できる場合】
作者の発言から特定の項目に書き込める内容が確定した場合、回答の末尾に
---SUGGESTION--- を出力し、その後に以下のJSONを出力する。
{"field": "対象項目名", "value": "書き込む内容"}
確定していない場合はJSONを出力しない。
```

**後処理**：`---SUGGESTION---` 以降を検出したら、該当項目への反映確認UIを表示する。作者が承認した場合のみ `plot.md` へ書き込む。

### P-02　プロット逆算生成（既存作から）

**version**：3.0（実装は `src/prompts/plotReverse.ts` の `PLOT_REVERSE_VERSION`）
**目的**：既存の本文全体からプロットを推定生成する。
**推奨**：Gemini Pro（長文コンテキスト）/ temperature 0.3
**構成**：Map-Reduce

**Map段階（チャンクごと）**

```
以下は小説の一部です。プロット逆算のための要素を抽出してください。

【本文】
{{chunk_text}}

【抽出項目】
- この範囲で起きた出来事（時系列順、最大5件、各50字以内）
- 登場した人物名
- 登場した場所名
- 読み取れるテーマの手がかり（作品が問いかけている主題、あれば）
- 語りの人称（一人称／三人称一元／三人称多元／その他）と、
  一人称の場合は主人公の自称
- 主人公と思われる人物の、この範囲での行動の動機

【出力形式】JSONのみ
{
  "events": [{"order": 1, "summary": "..."}],
  "characters": ["..."],
  "locations": ["..."],
  "theme_hints": ["..."],
  "narrative_person": "...",
  "protagonist_motive": "...",
  "confidence": "high|medium|low"
}
```

**Reduce段階**

```
以下は、ある小説の全編から抽出した要素です。これらを統合し、
作品全体のプロットを再構成してください。

【抽出済み要素】
{{merged_extracts}}

【出力するプロット項目】
- title: 既存タイトル（{{existing_title}}）をそのまま使用
- logline: 作品全体を一文で表す（80字以内）
- theme: この作品が問いかけている主題（100字以内）
- motif: 繰り返し現れる象徴・題材（配列、最大5件）
- worldview: 世界の成り立ち・法則（200字以内）
- setting: 主な舞台（100字以内）
- narrative_person: 語りの人称
- protagonist_motive: 主人公の行動原理（100字以内）
- plot_outline: あらすじの箇条書き（配列、各60字以内、最大20件、時系列順）
- main_characters: 主要人物（配列、name と summary。summaryは60字以内）

【注意】
- 本文から読み取れないものは推測で埋めず、null または空配列とすること。
- 特にテーマとモチーフは、作者の意図を勝手に断定しないこと。
  複数の解釈が可能な場合は、最も本文の記述量が多いものを選び、
  notes に他の可能性を記載すること。

【出力形式】JSONのみ
```

**後処理**：生成結果を `plot.md` へ書き込む前に差分プレビューを表示する。既に作者記述がある項目は上書き候補として別枠に表示し、既定では上書きしない。

### P-03　世界観まとめ生成

**目的**：ジャンル、時代背景、世界の法則等をまとめる。

**独立したAI呼び出しは行わない。** P-04a（`src/prompts/characterExtract.ts`）の
`worldview` として、人物・能力・組織・場所と同じ1回の応答で受け取る。
種別ごとに呼ぶと同じ本文を何度も読ませることになるため。**version・temperature・
推奨モデルはP-04aに従う。**

保存先は `設定/world/` のJSON（1件1ファイル）。マージはコードで行う（`mergeExtractedWorldItems`）。
`world.md` は純粋な生成物である。

- **`content` ではなく `name`（15字以内の見出し）＋ `description`。**
  見出しが無いと一覧・パネル・統合の手掛かりが無く、同じ事柄が
  毎チャンク別項目として増え続ける。
- **作者の加筆は `authorNotes` / `exportNote` に入れる**（AIは触らない）。
  `world.md` に `<!-- author -->` で作者加筆を混在させる案は採らなかった。
  作者が散文を書きながらコメント記法を保つのは無理があり、
  解析を誤れば作者の文章が消えるため。

**抽出対象**

- ジャンル的特徴（現代/異世界/SF/歴史 など、判断根拠となる記述）
- 時代背景（年代、文明水準、技術水準）
- 世界の法則（魔法・超能力・特殊技術の仕組み、その制約や代償）
- 社会構造（国家、身分制度、組織、経済、通貨）
- 文化・風習（宗教、言語、暦、儀礼）
- 地理（大陸、気候、地形の特徴）
- 固有の用語・造語とその意味

**世界観には物語の出来事を書かせない。** 「城が燃えた」は出来事、「城は木造で燃えやすい」が世界観である。既知の世界観設定に既に含まれる情報も出力させない（新規情報のみ）。

【呼称の抽出ルール】（重要）

1. 会話文・心内語の中で、ある人物が別の人物を呼んだ表現をすべて拾うこと。

相手との関係を relations に入れてください。

1. 本文で述べられている、または本文からはっきり読み取れる結びつきだけを書くこと。

3. name には相手の人物名を入れること。指示語や、人物名の分からない相手は書かない。

##### 〔2026-08-09〕組織の抽出を足した

- `parent` に上位組織を入れる（「冒険者ギルドの生活保護課」なら name は「生活保護課」、parent は「冒険者ギルド」）
- `category` は作品側の言い方をそのまま使う（「ギルド」「王国」「部署」）
- **人物の所属に入れた組織名は、組織としても出させる。** 説明が無ければ `description` を null にして名前だけでよい
- **場所と組織は分ける。** 「冒険者ギルド」は組織、「冒険者ギルドの受付」は場所
- その場限りの集まり（「野次馬」「通行人たち」）は組織ではない

##### 〔2026-08-10〕性格だけは推論を認めることにした

原則1は「本文に書かれていない情報を推測で補って断定しない」だが、`personality` はその例外とする。

小説では性格が地の文で説明されることは少なく、行動と台詞で示される。明記だけを採ると、この項目はほぼ常に空欄になる。実データでも「（本文から読み取れる性格に関する記述なし）」ばかりが並んだ。

システムプロンプトの原則1にも同じ例外を書いた。**本文側のルールだけを直すと指示が食い違い、モデルは厳しいほうを選んでしまう。**

##### 〔2026-08-11〕v3.0　組織でないものが混ざる

実データ（教科書チート・219話）で、組織11件のうち4件が組織ではなかった。**Claude / Gemini でも起きる。**

| 入っていたもの | 本来の置き場 |
|---|---|
| 王都・スカラ子爵領・魔境 | 場所 |
| 赤熊（魔物） | 出さない |
| 血の奔流（技） | 能力 |

プロンプトに**除外の例を具体的に並べ**、「そこに所属する人がいるか」で決めるよう書いた。「王国」は人が仕える組織だが「王都」はただの都市である、という対比まで書かないと区別されない。あわせて**同じ名前を場所と組織の両方に出すことを禁じた**（以前は「両方に出てよい」としていた）。

**コード側では弾けない。** 「説明が場所を指していたら弾く」を検討したが、正しい組織の「冒険者ギルド」の summary が「…介抱に関わった場所。情報伝達の拠点。」で、その判定に引っかかる。弾けるのは所属から作る経路だけである。

##### 〔2026-08-15〕v4.0　「書いていないことは書かない」は、要約まで禁じてはならない

作者の指摘「設定資料の抽出等、全体の方針として『書いていないことは書かない』は有効だと思うのですが、要約まで認めていないのではないでしょうか？」。**当たっていた。**

v3.0のプロンプトは、性格についてこう指示していた。

> ・**必ず「どう振る舞ったか」を添えること。性質だけを書いてはならない。**
> 　良い例：「命令口調で指示を出し、部下の反論を最後まで聞かない」
> 　悪い例：「傲慢」「勇敢」

根拠のないラベル貼りを防ぐ意図だったが、**性質を書くこと自体を禁じていた。** AIは指示どおりに動いており、実データの性格欄は「赤ら顔で愛想笑いを浮かべる。投げやりに言う」のような**所作の羅列**になっていた。外見も「右腕を掲げて見せる」と動作が混ざっていた。

v4.0では、禁止の対象を**事実の捏造だけ**に絞り、要約を明示的に求めた。

> **本文にある複数の記述をまとめて言い換えるのは要約であり、禁じている推測ではない。**
> 禁じているのは、本文に無い事実（出来事・関係・設定・経歴）を作ることである。
> 逐語で写すのは evidence だけである。

**実機のOllama（`gemma4:e4b`）で、同じ本文・同じモデルのままプロンプトだけを入れ替えて比較した。**

| | 修正前 | 修正後 |
|---|---|---|
| 性格 | 「『この腕じゃ…』と発言するなど、現状に落ち込みがち」 | 「落ちぶれた状況に自暴自棄になりがちだが、根はプライドが高い（引用）」 |
| 外見 | 「右腕を掲げて見せると手のひらに…」 | 「右腕の指を失い、手のひらに人差し指のみ残っている」 |

**この作品の設計は、逐語照合の対象を evidence に限っている。** 値そのものは照合していない。つまり要約を許しても、根拠の追跡可能性は失われない。「書いていないことは書かない」を値にまで適用するのは、仕組みの上でも過剰だった。

あわせて、コード側の不在文フィルタ（`isMeaningfulValue`）が実データを取りこぼしていたのを直した。「（本文から読み取れない）」は語の前に「本文から」が付くため、「記述は確認できない」は語の間に動詞が挟まるため、どちらも既存の正規表現に一致していなかった。結果、主人公の性格欄にその文言がそのまま載っていた。

##### 〔2026-08-15〕v5.0　関係の抽出を必須にした

作者から「幽霊の太志が文佳に憑依しているのに、AIがそう認識しない」という報告があった。
調べたところ、**`relations` はスキーマにあるのにプロンプトに説明が無く、`required`
にも入っていなかった**。「省略可能な項目は小さいモデルが黙って落とす」という、
`role` / `personality` / `appearance` を必須にしたときと同じ条件に当てはまっており、
実データでもほぼ常に空だった。

**憑依・入れ替わりは、名前も外見も相手のものになる。** `relations` に書けなければ、
その情報を残せる欄が他に無い。そこで説明を足し、`required` に入れた（空配列は許すので
「無かった」とは言える）。

**これは「AIに言い当てさせる」改造ではない。** 本文で述べられているのに書き留める場所が
無かった、という取りこぼしを塞ぐものである。明言されていない憑依を推論させることは
引き続き行わない（原則1「本文に書かれていない事実を作らない」を緩めると、
原稿にない設定を作り始める）。

### P-07　各話あらすじ生成＋サブタイトル提案＋感情値

```

{{chapter_text}}

【前話までのあらすじ】（文脈把握用）
{{previous_synopses}}

【登場人物】（当該話に登場する人物のみ）
{{relevant_characters}}

【作成方針】
- あらすじは150字以内。この話で「何が起きたか」を時系列で簡潔に。
- 主観的な評価（「感動的な」「衝撃の」等）を入れず、事実を記述する。
- 本文に書かれていない出来事を書かないこと。

{{#if needs_subtitle}}
【サブタイトル提案】
このファイルのファイル名は話数のみです。サブタイトルを3案提案してください。
- 各案15字以内（厳守。全角15字を超えたものは出力しない）

- 次を読みたくなる引きがあるとよいが、ネタバレしないこと

- intensity（盛り上がり）：0〜10の整数。静かな日常の場面が0〜2、対立や転機が5前後、
  最も張り詰めた場面が8〜10。**作品の中で相対的に**付けること。
- valence（明暗）：-5〜+5の整数。絶望・喪失が-5、救い・和解・勝利が+5、淡々としていれば0。
- dominant（主だった感情）：「喜」「怒」「哀」「楽」から1つ。決めがたければ null。

{

  "subtitles": [
    {"text": "...", "kind": "出来事型", "reason": "..."}

  "emotion": {
    "intensity": 7, "valence": -2, "dominant": "怒", "reason": "..."
  }
}
```

**後処理**：
- 文字数はAIの自己申告を信用せず、拡張機能側で数え直す。15字を超える案は自動的に除外し、残りが0件なら再生成する。

- 感情値は本文から測った数値であり作者が書いた文章ではないので、**作者が書き直したあらすじにも追随させる**。書き直した話だけ途切れると起伏の形が読めなくなる。

| 種類 | 書かせること | 例 |
|---|---|---|
| 冗長 | 重なっている2つの語 | 「『まず』と『最初に』が同じ意味です」 |
| 同語反復 | 繰り返されている語と回数 | 「『言った』が3文の中で3回出ています」 |
| 係り受け | どこに掛かると読めるのか2通り | 「『赤い』が『鞄』にも『少女』にも掛かって読めます」 |
| 長文 | 字数と読点の数 | 「120字・読点7個で、切れ目が分かりません」 |

**「冗長です」「読みにくいです」は悪い例として明示する。** 種類の名前を言い換えただけでは、作者はどこを見ればよいのか決められない。

**返って来なかったときの言葉は、コード側に持つ**（`core/proofreadValidation.ts` の `explainProofreadReason`）。「AIが説明を返さなかったから何も出ない」を作らない。

### P-18　設定について相談する（設定資料パネル）

**version**：3.0（実装は `src/prompts/settingsChat.ts` の `SETTINGS_CHAT_VERSION`）
**割当キー**：`extract`（設定資料の抽出と同じ仕事なので割当も抽出に揃える——`features/settingsPanel.ts`）
**目的**：選んだ1件について、本文を根拠に作者と対話する。
**temperature**：0.5

材料は、その設定が登場する場面の本文抜粋（`core/mentionExcerpts.ts`）と、現在の設定（`core/settingsSummary.ts`）。同じ材料をP-20でも使う。

**禁じるのではなく、区別させる。** 事実の問い（出来事・数値・固有名詞）は、本文に無ければ「見当たりません」と答えさせる。**考えるための問い**（テーマ・人物の捉え方・足りない設定）では突き放さず、推測と分かるように書いたうえで述べさせる。理由は「P-18 の経過」に測った数字を載せた。

**保存は承認制。** 返ってきた内容は画面に出すだけで、作者が「追記」を押したときだけ `aiNotes` に入る。掘り下げは本文の逐語照合ができない解釈であり、抽出結果と同じ扱いで自動保存すると、どこまでが本文に書いてあることなのか分からなくなる。

**既存の項目は書き換えない。** 追記されるのは `aiNotes` だけで、`role` や `personality` には触れない。

#### P-18 の経過

##### 〔2026-08-16〕相談では「禁じる」のではなく「区別させる」（v3.0。P-21も同時に3.0へ）

作者からの問い「ハルシネーションを防ぐという目的に、今のプロンプト等のやり方は適切でしょうか？ **何も制限がない時のほうが適切な回答を返すことがあります**」。

**実データで測った。** いじめられっ子（18話）で、指示の強さを3通り試した。**幻覚と空振りを同時に測る**（片方だけ見ると必ず間違える）。

| 指示 | 幻覚（答えの無い問い6件） | 空振り（答えのある問い6件） |
|---|---|---|
| A 強い禁止「根拠が無ければ必ず分かりませんとだけ答えよ」 | 0/6 | 0/6 |
| B 区別させる「答えられることは答える。ただし事実／解釈／不明を区別する」 | **0/6** | **0/6** |
| C 制限なし | 2/6 | 1/6 |

**禁止を強めても幻覚は減っていない。** AとBは同点で、Cだけが悪い。

**差が出たのは「考えるための問い」だった。** 同じ3通りで、正解が1つに決まらない問いを投げた。

| 指示 | 「この作品のテーマは何だと読めますか？」への答え |
|---|---|
| A 強い禁止 | **「分かりません」（6字）** |
| B 区別させる | 792字。本文を引用しつつ解釈を述べる |
| C 制限なし | 1667字。内容は濃いが世辞と冗長さが混じる |

「この作品で足りていない設定はありますか？」でも A は「分かりません」だった。**作者が相談したいのはまさにこの種の問いで、そこで最も役に立たない答えを返していた。**

**直し方：禁止の範囲を「事実」に限る。** 問題は禁止の強さではなく、**掛かる範囲**だった。「答えが無ければ分かりませんと言え」が、事実の問いにも解釈の問いにも同じ強さで掛かっていた。

- **出来事・数値・固有名詞**（本文を見れば決まること）→ 無ければ「見当たりません」。当てずっぽうは邪魔
- **テーマ・人物の捉え方・足りない設定**（考えるための問い）→ **突き放さない。** 推測と分かるように書いたうえで述べる

原則1（事実と推測を区別して書く）は元からあった。**それを活かせていなかったのは、原則4が無条件に「分かりません」へ倒していたため。**

直した実物のプロンプトで測り直した結果：**事実の誤り 0/3、幻覚 0/3、突き放し 0/2。** 三つが両立した。

**抽出（P-04a・P-20）は厳しいままにする。** 相談は読んで終わりだが、**抽出結果は設定資料として保存され、後の判断の土台になる。** 扱いを変える。ただし過去に「書いていないことは書かない」が要約まで禁じ、性格欄が本文の切り貼りになった事故がある（P-04a v4.0で「要約は推測ではない」を明示して修正）。**禁じる対象は「推測」であって「要約」ではない。**

### P-20　AIで再読込（設定資料パネル。旧「設定項目の充実」）

**version**：2.0（実装は `src/prompts/settingsEnrich.ts` の `SETTINGS_ENRICH_VERSION`）
**割当キー**：`extract`
**目的**：設定資料の**各項目に入れる値そのもの**を提案する。v2.0からは、**作者の留意点**（自由記載。例「他の登場人物〇〇の情報が混入しています。」）を添えて読み直させ、**混入と判断した記述は `misattributed` として分けて返させる**（設計書6.31）。
**temperature**：0.3（設定として書くので、相談より控えめにする）

P-18が文章のメモを書くのに対し、こちらは項目を埋める。パネルのAI機能はこの2つだけで、両方とも同じ本文抜粋を材料にする。

提案する項目は種別ごとに決まっている（人物なら性別・紹介・所属・役割・性格・外見）。人物にはこれに加えて、**作者が定義した追加項目**（`設定/custom_fields.json`）が並ぶ。追加項目の説明文はそのままAIへ渡す。

**JSONスキーマでは全項目を必須にし、nullを許す。** 省略可能にすると、小さいモデルは面倒な項目を黙って落とす。nullを返させれば「読み取れなかった」と明示させられる。

**紹介に書く変化は、関与度で決める**（設計書6.18）。変化の記録には「課長になった」も「髪を切った」も同じ形で並ぶので、そのまま渡すとAIは書きやすいほう（外見）から埋める。材料（`core/settingsSummary.ts`）の変化には、コードが計算した点を［関与度 65（高）］の形で添えてある。プロンプトでは**（高）だけを紹介へ書き添えさせる**。（中）は字数が余ったときだけ、（低）は書かせない。

**点はコードが決める。** AIに測らせると、同じ人物でも呼ぶたびに紹介が変わる。

**提案は保存しない。** 項目ごとに現在の値と並べて見せ、作者がチェックを入れたものだけを書き込む。既定でチェックが入るのは**空欄を埋める提案だけ**で、作者が書いた内容の置き換えは必ず自分で選ばせる。

**反映しても作者が確定させた記述としては扱わない**（`EditOptions.authorConfirmed`）。中身はAIが書いたものなので、以後の抽出で更新されてよい。作者確定にすると、その人物は以後の抽出から締め出され、書き進めても情報が増えなくなる。

**後処理**：AIは「不明」「なし」「N/A」を値として返してくることがあるので、空欄と同じ扱いにする。文字数制限のある項目（紹介の80字）はコード側で切り詰める。**［関与度 …］そのものが値に混ざっていたら落とす**（`stripInvolvementNote`）。指示語がそのまま答えの中身として返ってくるのは、この作品で繰り返し起きている。

#### P-20 の経過

- **v1.1（2026-08-26）紹介に書く変化を関与度で決めるようにした。** 紹介が60字から80字になり、作中での変化を書く余地ができたため（設計書6.18）
- **v2.0（2026-08-28）「AIで再読込」へ。** 留意点の注入と `misattributed`（混入と判断した記述の分離。belongsTo・field・value・evidence の全項目required）。evidence は本文抜粋と逐語照合し、通らないものは件数つきで報告（黙って捨てない）。はじいた記述の**行き先（既存レコードへ挿入・新規を起こす）はコードが照合して作者が押す**——AIの返した文字列が書き込み先に直結しない。話数の無い値の挿入は設計書6.18の規則どおり conflicts へ（changes に積むと、起きていない年表が資料に載る）

|---|---|---|
| `edit` | `{"target": "plot.theme", "content": "...", "label": "..."}` | 書き込みの提案。`target` に取れるのは `plot.<項目>` / `blurb` / `catchphrase` / `episode.<話数>`。**本文（原稿）は対象外**で、名指しされたら断る。設定資料（人物・場所など）への書き込みは**未実装**（対象の特定が要るため。設計書6.6.3） |
| `needFiles` | 作品フォルダーからの相対パス、最大3件 | 材料が足りないときに読みたいファイル。中身を渡して聞き直す。**往復は1回だけ** |
| `run` | `checkTypos` / `checkTyposForFile` / `checkNotation` の3つだけ | 専用機能の起動を提案する。**一覧に無いものは黙って捨てる**（AIの返した文字列がコマンド名になる余地を残さない） |
| `locate` | `{"path": "...", "text": "...", "label": "..."}` | 「そこを見せて」。`path` を省けばいま開いているファイルの中、`text` を省けばファイルを開くだけ |

`locate` の `text` には**本文にそのまま出てくる文字列を写させる**（言い換えさせない）。押されたときに実在を照合し、**見つからなければ光らせない**（`core/textLocate.ts`）。少し言い換えた引用に対して近い場所を光らせると、作者は「そこは何も問題ないが」と混乱する。誤字脱字検知の逐語照合と同じ考え方。

**毎回渡す材料**

- **拡張機能の操作の目次と、関係しそうな説明**（`features/featureGuide.ts` の `buildFeatureGuideForQuestion`。v3.4、設計書6.27.9）。詳細メニュー（旧・操作メニュー）の定義から組み立てる。**目次（全操作の名前＋「原稿は勝手に書き換えない」等の考え方）は毎回渡し、説明は質問に関係しそうな小分類の束だけ渡す**（選ぶのは `core/guideSelect.ts`。質問と直前の作者発言を文字2つ組みに割り、ひらがなだけの組みを捨てて束との一致数で選ぶ。当たる束が無ければ目次だけ——本文の相談も、「使い方を教えて」のような漠然とした質問も同じ）。名前が全部あるので「その機能はありません」と嘘を答える心配は残さず、送る量は機能数に比例しない。プロンプトでは①目次に無い機能は存在しない、②説明が無い操作は「無い」の意味ではなく、細部を聞かれたら場所を答えてホバー説明とマニュアルへ案内する、③作品の相談では目次に触れない、を明示し、目次は**本題より後ろ**に置く（長い一覧が先にあると、作品の話をしているのに機能の説明を始める）
  - **字数はここに書かない。** 機能を足すたびに自動で伸びるので、書くと必ず古くなる（実際に「約4,300字」のまま8,111字まで伸びていた）。目印（目次1,600字未満・束1,500字未満・本文の相談1,800字未満）は `test/unit/featureGuide.test.ts` が持つ
- **質問に近い場面**（設計書6.19）。作品全体から探して渡す。開いている画面の前後だけでは、大きい作品でほとんど答えられなかった（78.5万字の作品で実測3問中0問）。検索語はP-22で作る
  - 材料には**出どころを書く**（`《本文／第105話》`）。設定資料とあらすじは本文からAIが作ったもので、本文と対等な証言ではないため、**食い違うときは本文を優先するよう明示する**

**JSONとして読めなくても捨てない。** 相談は会話なので、形式が崩れても本文が読めるなら見せたほうがよい。読めなければ全文を返事として扱う（`parseWorkChatAnswer`）。

### P-22　質問を検索語に直す

**version**：1.0（実装は `src/prompts/searchTerms.ts`）
**目的**：作者の言い回しを、本文に書かれていそうな言葉へ直す。相談（P-18・P-21）の前段。
**temperature**：0.2（言い換えなので揺らさない）

**なぜこの段が要るか。** 実データ（78.5万字・219話）で、「妬ましさを感じる場面は？」と聞くと意味検索も語句一致も30位以内に入らなかった。**「嫉妬」と直接聞けば1〜2位で出る。** 足りないのは検索の力ではなく、作者の言葉を本文の言葉へ直す段だった。

AIに検索語を作らせたところ（嫉妬・羨む・劣等感…）、5問中1問しか当てられなかったものが**5問とも当たる**ようになった。

```
{"terms": ["嫉妬", "羨む", "劣等感", "視線", "対比"]}
```

**守らせること**：

- 質問に答えないこと（検索語だけを出す）
- 作者の言い回しではなく**本文に書かれていそうな言葉**へ直すこと
- 作品固有の名前（人物名・地名・造語）は**そのままの形で残す**こと。そのために作品の名前一覧を渡す
- 一語ずつにすること（文にしない）

**後処理**：

- **失敗しても例外にしない。** 検索語が作れなくても質問文そのままで検索すれば動く（今より悪くはならない）。ここで止めると相談そのものができなくなる
- 30字を超える語は落とす（文を返してきたとき）
- **検索には質問文も残す。** 検索語だけにすると、AIが的外れな語を出したときに手掛かりが無くなる

**費用**：相談1回につきAI呼び出しが1回増える。入力も出力も小さい（100トークン程度）が、有料AIでは料金がかかる。

### P-23　指摘の再チェック（提案パネル）

**version**：1.0（実装は `src/prompts/recheck.ts`）
**目的**：作者が本文を手で書き直したあと、**その指摘が解消したか**を1件だけ確かめる。誤字脱字（P-09）・推敲（P-10）・表記ゆれと、**矛盾（P-12）・プロット逸脱（P-11）の指摘**が対象（矛盾・逸脱は0.23.9で追加。プロンプトは変えず、指摘の中身「設定では：…／本文では：…」を理由の欄で渡す。**versionは1.0のまま**）。
**割当**：プロンプトは1本共通だが、どのAIで走るかは**指摘の分類に従う**（typo系の指摘は `typo` の割当、矛盾系は `contradiction` の割当。設計書6.28.9）。
**temperature**：0.0（判断であって創作ではない）

**矛盾で確かめられるのは、本文を直した場合だけである。** 設定資料のほうを直した場合、本文は変わっていないので引用照合が「本文が変わっていません」と返す。設定側の解決も見るには、いまの設定（`settingsSummary`）を添える改修＝プロンプト変更が要る（未実装。ボタンの説明文も「本文を書き直したあと」に限って書いてある）。

作者の依頼（2026-08-27）：「推敲について、なおし方を作者が決める系のものは『再チェック』ボタンを追加してください。なおして解消されたか確認したいです」「誤字脱字の提案パネルでも、違うそうじゃないという提案がきます。手書きで書き直して解消したか確認したいです」。

**なぜ検知のやり直しでは足りないか。** 誤字脱字も推敲も、作品まるごとを何十チャンクにも割って走らせる。**1件を確かめるために全部を走らせ直すのは高い**（クラウドAIではそのまま料金になる）。こちらは1件だけを見るので、渡すのは該当箇所の前後（前後4行・1,200字まで）と元の指摘だけで足りる。

**AIを呼ぶ前に、コードで済ませる段がある。** 作者が直し忘れていれば、指摘が引用した文はそのまま本文に残っている。これは照合で分かるので、**そのときはAIを呼ばない**（`features/recheckProposal.ts` の `isQuoteStillPresent`）。「まだ書き直されていません」と返すだけで、作者が知りたいことは足りている。

**入力**：指摘の種類・ファイル名・引用（`original`）・問題とされた部分（`target`）・理由・そのときの修正案（あれば）・いまの本文の抜粋（行番号付き）。

```
{"resolved": true, "reason": "「駆けた」に書き直され、促音の誤りは無くなっています"}
```

**守らせること**：

- **直し方が元の修正案と違っていても、問題が無くなっていれば解消とすること。** 作者は自分の言葉で書き直す。ここを外すと、別の言い方で直したものを毎回「まだ残っている」と言うだけの機能になる
- 抜粋に無いことを推測で補わないこと
- **新しい問題を報告しないこと。** 聞いているのはこの指摘1件のことだけである
- 該当箇所が本文に見当たらない（丸ごと書き直された・削られた）なら、その指摘はもう当てはまらないので解消とすること

**後処理**：

- **答えは真偽値で受ける。** 「解消」「未解消」のような日本語のラベルを値にすると、指示の言葉がそのまま返ってくる（この作品で繰り返し起きている）。真偽値なら表記ゆれを吸収せずに済む。ただし**スキーマを守らないモデルがある**ので、文字列で返った `"true"` `"解消"` などは読み替える
- **読めなかったものを「解消した」に丸めない。** 通信の失敗も応答の崩れも、本物の指摘を消してよい理由にはならない。指摘はそのまま残し、理由を作者へ伝える（P-12bと同じ考え方）
- 理由が「なし」「特になし」のような中身の無い言葉なら、理由として扱わない
- 解消と分かっても、**片付けるのはその1件だけ。** 似た指摘までまとめて消さない（同じ語でも話ごとに事情が違う）
- **本文には一切書き込まない。** 直したのは作者であり、拡張機能は確かめているだけである

**費用**：1件につきAI呼び出しが1回。ただし**本文が書き直されていなければ0回**である。入力は該当箇所の前後だけなので、検知1チャンクよりずっと小さい。

**費用の確認**：有料AIのときは、**パネルを開いている間に一度だけ**確認を取る（`confirmPaidUsage`）。1件ずつ押す操作なので、毎回モーダルが出ると確かめる気が失せる。

- **出力**：`{ name, reading（ひらがな）, origin（系統）, note（由来や響きの一言）}` を10件。スキーマ固定・全項目required
- **AIは候補を出すだけ。衝突の判定はコードで行う**（設計書6.37.1の規則）。プロンプトで「既存の名前と響きが近いものは避けて」と書いてはいるが、**守られない前提**で、当たる候補は理由つきで落として残りを見せる。落とした件数も画面に出す（黙って減らさない）
- **系統を混ぜない。** 「指定なし」のときは既存の名前から系統を1つ推定し、その系統だけで出させる。混ぜると世界観が崩れる
- **指示語のなぞり**（「候補1」「名前」「系統」等）は `isPlaceholderText` と、プロンプトの出力例の言い換えで弾く（失敗3の型）
- キャッシュしない（同じ入力でも毎回違う候補が欲しい場面である）
- **実モデル未計測**

#### P-29 の経過

- **v1.1（2026-08-29）プロンプトの例示名（ミナ・ミナモト・アリア・アリサ）を `NAME_SUGGEST_HINTS` に入れ、候補として返ってきたら落とす。** 指示に書いた具体名がそのまま答えに混ざる（失敗3の型）。Opusレビューの要確認から採用

## 第3部　運用設計

### 3.1 プロンプトのバージョン管理

**1.1に書いた。** 版は `*_VERSION` 定数で持ち、チャンクのキャッシュの鍵は `promptVersion|providerId|model|chunkHash` である。

再生成は自動で行わない。版が上がってもキャッシュは「作り直せる」と印を付けるだけで、実行するのは作者が選んだときである（コスト保護）。

### 3.2 品質評価の仕組み（提案）

プロンプトの改善には評価基準が必要になるため、以下を用意することを提案する。

- `tests/fixtures/` に評価用の短編サンプル（既知の誤字・矛盾を意図的に埋め込んだもの）を配置する。
- 各プロンプトについて「検出すべき箇所」を正解データとして定義し、検出率と誤検出率を計測するコマンドを用意する。
- プロバイダ・モデルを変えて同一テストを実行し、機能ごとの推奨モデルを実測で決める。

これがないと、プロンプトを改良したつもりが実は悪化していた、という事態を検知できない。

### 3.3 コスト見積もりの表示

AI機能の実行前に、以下を確認ダイアログで提示する。

- 処理対象チャンク数（うちキャッシュ済みでスキップされる数）
- 推定入力トークン数・出力トークン数
- 推定コスト（プロバイダの単価設定に基づく。Ollamaは0円と表示）

10万字を超える範囲を対象とする場合は、既定で確認を必須とする。

### 3.4 失敗時の扱い

- チャンク単位で失敗した場合、全体を中断せず、失敗チャンクを記録して続行する。
- 処理完了後に「N件のチャンクで解析に失敗しました」と報告し、再試行できるようにする。
- APIレート制限に達した場合は指数バックオフで待機し、上限回数を超えたら中断して途中結果を保存する。

## 第4部　未確定事項・要相談

1. **プロット逸脱検知の厳しさ**：どの程度の逸脱を指摘してほしいかは作者の好みが大きく分かれます。設定で「厳しめ／標準／緩め」を切り替えられるようにする案を提案します。
2. **推敲の範囲**：現状「明らかに読みにくい箇所のみ」に絞っていますが、実際に使ってみて物足りない場合は対象を広げます。まずは狭く始めることを推奨します。
3. **呼称抽出の前提となる話者推定**：呼称は「誰が誰を呼んだか」の情報であり、抽出には話者の特定が不可欠です。会話文が連続して地の文による話者明示がない箇所（「〜」「〜」と応酬が続く場面）では、話者の取り違えが起きやすくなります。

   対策として、以下の構成を提案します。精度が出ない場合はこちらへ切り替えます。
   - 話者推定を独立したプロンプトとして切り出し、会話文ごとに話者と確信度を判定させる
   - 話者が特定できた会話文のみを呼称抽出の入力とする
   - 一人称視点作品では語り手＝話者が確定するため、視点情報をプロンプトへ渡して精度を上げる

   なお現状のP-04では「話者を特定できない発話の呼称は抽出しない」と指示しており、取りこぼしはあっても誤登録は避ける方針としています。
4. **チャンク分割の単位**：既定は「1話単位、超過する場合は約2万字で分割」を想定していますが、シーン区切り（空行や記号による区切り）を優先する方式も検討可能です。
