## まとめ（作者向け）

**いまの拡張機能で、計算そのものに時間がかかっている所はほとんどありません。** 遅く感じるときの時間の大半は「待ち」です。

- 起動して作品一覧が全部そろうまで、実機では**中央値4.6秒**。そのうち本当に計算していたのは**約0.2秒**（字数を数える 0.14秒・解析 0.04秒）。残りは、拡張機能ホスト（VS Code の拡張機能がみな乗っている1本の流れ）の**順番待ち**とファイルの読みでした。同じ作品を、混んでいない所で動かすと**0.1秒弱**で終わります
- 起動時の「点検」（GitHub との同期の確かめ）は実機で**12〜20秒**。中身は git の呼び出しで、**同じ置き場（書庫）の作品でも作品の数だけ git を7回ずつ呼んでいます**。写し（10フォルダー・置き場1つ）では、今の呼び方で**1.7秒（git 90回）**、置き場ごとに1回なら**0.12秒（7回）**でした。GitHub との通信（fetch）は1回約1秒
- **作者の補足「メニューの表示、同期前のチェック等が遅い」**：メニューの形そのものは2ms未満で、遅れるのは末尾の印（未反映の件数など）を**全作品ぶん読み直す**所（写し7作品で93ms・ファイル431回）。同期前のチェックは**ほぼ全部が git の待ち**で、写しで確認の窓まで1.3秒（git 73回）。作者の環境（25作品）に当てはめると9〜10秒ほど。0.115.0 の編集部の取り込みは、今は1回0.2秒ほどで主因ではない（下の節）
- **CPU の複数のコアで分けても、縮むのは計算の部分（実機で約0.2秒）だけ**です。コアを増やす手は、この拡張機能では効き目が小さい
- ただし「別の流れへ逃がす」こと自体には別の効き目があります。**混んだ流れから外れるので、順番待ちが消えます**（下の手2）。コアの数ではなく、列から外れることが効く

## 見立ての確かめ：この拡張機能だけで起動すると（2026-10-30 0時台、作者の許可を得て母艦で）

作者が「先に見立てを確かめる」（選択肢B）を選んだ。確かめたかったのは、起動時の待ちの正体が「ほかの拡張機能と流れを取り合っていること」なのか、「この拡張機能自身の起動時の処理（点検の git など）」なのか。

**やり方**：画面の自動テストの部品（`test/e2e/support/vscodeApp.ts`）で、VS Code 1.141.0 を画面の外に起こした。拡張機能の置き場は空の一時フォルダーなので、**入っているのはこの拡張機能だけ**になる。起こす前に、登録簿（globalState の `novelai.works`）へ写しの7作品を置いた（部品の作品と合わせて8作品・277ファイル）。1回目の起動で作品一覧の列を開き（作者の普段の起動と同じく、列が開いた状態で起動させるため）、そのあと4回起動し直して、起動ログの「起動の所要時間」の行を取った。起動時の点検も、手元の送り先へ向けてそのまま走る（GitHub と AI は呼んでいない）。台本は一時のもので、作業場から消した（記録していない）。走らせたあと、試験用の VS Code が残っていないことを確かめた（0件）。

|---|---|---|

| 作品一覧の初回描画 | **429〜474ms** | **4.6秒** |

読み方：

- 作品とファイルの数は作者の環境の半分ほど（8作品・277ファイル 対 25作品・約600ファイル）。数に比例するとしても、この拡張機能だけなら初回描画は1秒前後のはずが、作者の環境では4.6秒かかっている。**残りの3秒以上は、同じ拡張機能ホストに乗っているほかの拡張機能との取り合いと見てよい**
- 「1回に詰まった最長」が0.1秒以下に収まった。**作者の環境の0.8秒の詰まりは、この拡張機能の外から来ている**（ここでも点検の git は同じ時間帯に走っていたので、点検が詰まりの元ではない）
- 作者の機械の VS Code のログ（`%APPDATA%\Code\logs\20261029T224425\window1\exthost\exthost.log`）では、この拡張機能の起動と同じ時間帯に GitHub Copilot Chat・Claude Code・TypeScript の言語機能が立ち上がり、Copilot Chat はそこから約6秒ログを書き続けていた。詰まりの相手の候補だが、どれが何秒を使ったかまでは、このログからは分からない
- **点検は、ほかの拡張機能がいなくても、通信が無くても4秒以上かかる。** これは自分の git の呼び方による遅さで、1位の直しがそのまま効く
- 違う条件：試験の VS Code は 1.141.0・まっさらな設定・画面の外。作品は写し（OS のファイルの控えが温まっている）。作者の作品の数・置き場の数とは違う

**結論**：

1. 起動時の作品一覧の遅さは、**主にほかの拡張機能との取り合い**（見立てのとおり）。2位（走査を別の流れへ移す）と、同じ効き目を設定だけで試す「この拡張機能を別の拡張機能ホストで動かす」（`extensions.experimental.affinity`）は、狙いとして正しい
2. 起動時の点検と同期前のチェックの遅さは、**自分の git の呼び方**による。ほかの拡張機能がいなくても遅いので、1位の直しが要る
3. 計算そのもの（数え・解析）は、この拡張機能だけでも0.1秒以下。**CPU を何コア使っても縮む所はほぼ無い**

## 効く手（順位つき）

「効き目」は測った数字からの見込み。「ブラウザ版への影響」は CLAUDE.md の実装ルール7（ブラウザの VS Code でも動く形で書く）について。

### 1位　同期の前後と起動時の点検の git を、置き場ごとに1回・まとめて呼ぶ（やり直さない作り）

作者の言う「同期前のチェック」の遅さは、ほぼこれ1つで説明がつく。同じ直し方が4か所に効く：全作品同期・保存・同期の状態調べ（`syncAllWorks.ts` の `collectStates`）、送ったあとの読み直し（`gitSync.ts` の `refreshAll`）、起動時の点検（`handoffSync.ts`）、GitHubと同期の選択肢の前（`showGitSyncActions`）。

- **同期前のチェックの見込み**：写し（7作品・置き場1つ）で確認の窓まで 1.3秒（git 73回）→ 置き場を先に決めて同じ置き場の作品を読まなければ約20回・約0.35秒。作者の環境（25作品・置き場4〜5か所）では、確認の窓まで9〜10秒ほど → **fetch を同時に回して2秒前後**、送ったあとの完了の知らせまでの約4秒 → 1秒弱（見込み・混んでいない場合）
- **GitHubと同期（1作品）**：選択肢を出す前の fetch（約1秒）は、前回読んだ状態で先に選択肢を出し、fetch は裏で済ませる形にもできる。ただし「取り込むものがあるか」が選択肢に反映されるのが遅れるので、作者の判断が要る
- **起動時の点検の何を変えるか**：点検の最初で、作品ごとではなく**置き場（書庫）ごとに1回**だけ状態を読む。状態を読む git（`readSyncStatus` の中で7回：置き場の根・送り先の有無・枝名・上流・ahead/behind など）のうち、枝名・上流・ahead/behind・変更の一覧は `git status --porcelain=v2 --branch` 1回で取れるので、**7回を2〜3回に減らす**（置き場の根 `--show-toplevel` と送り先の有無 `remote` は status に出ないので残る）。置き場ごとの GitHub との fetch を**同時に**走らせる。終わりの `refreshAll`（今は登録作品ごとに順に読み直す）は、点検で読んだ状態を使い回す
- **見込み**：写しでは状態読みが 1.7秒→0.12秒（10フォルダー・置き場1つ）、さらに回数を減らして 0.12秒→**0.05秒前後（見込み。測っていない）**。実機の点検 12〜20秒は、残りがほぼ fetch の時間になり、置き場が数個なら**2〜4秒ほど**（fetch 1回約1秒を同時に回すため）。作者から見えるのは「右下の未記録の印が出そろうまで」と「開いたときに取り込みが終わるまで」が早くなること
- **もう1つの効き目かもしれないもの**：点検は起動の95ms目に始まり、作品一覧の走査と**同じ時間帯に**走っている（起動ログ：点検 開始 95ms → 初回描画 4,555ms → 点検 未了 14,561ms）。25作品×7回＝約175回の git を起こし、その返事を受けるのも同じ流れである。直したあとの起動ログで「下ごしらえ」と「ループの遅れ」も縮めば、**待ちの一部は自分の点検だった**と分かる。つまり1位は、2位の見立て（待ちの正体）を確かめるいちばん安い実験を兼ねる
- **直す範囲**：`core/git.ts`（`readSyncStatus` の読み方）、`features/handoffSync.ts`（`collectTargets` と fetch の並べ方）、`features/syncAllWorks.ts`（`collectStates` の飛ばし方と fetch の並べ方）、`features/gitSync.ts`（`refreshAll`）。中くらい。git の出力の読み方を変えるので、既存の試験（分岐・競合・送り先なし）を全部通し直す要がある
- **ブラウザ版への影響**：無い。ブラウザ版は git を起こせないので点検そのものが走らない（`canRunProcesses()`）。変わるのは手元の VS Code だけ

### 1位の次（小さい手）　メニューの印を、変わった作品だけ数え直す（やり直さない作り）

- **何を変えるか**：`refreshActionBadges` は、簡単ステップで作品を選び直すだけでも全作品の資料を読み直している。作品ごとの件数を覚えておき、選び直したときは数え直さない・抽出や反映のあとはその作品だけ数え直す。「重複の候補」は人物の JSON が変わったときだけ数え直す
- **見込み**：写しで1回93ms・ファイル431回 → 選び直しでは0、1作品の数え直しは数ms〜25ms（教科書チートで23ms）。作者の環境で約0.3秒・約1,500回 → 数十回。メニューの形そのものは元から速いので、効くのは「印が出そろうまで」と、そのあいだ流れを取り合う分
- **直す範囲**：小さい。`src/extension.ts` の `refreshActionBadges` と `views/actionDecorations.ts`（作品ごとの覚えは既に `workCounts` がある）。呼び出し元（12か所ほど）のうち、どれが1作品だけでよいかを仕分ける

### 2位　作品の走査を別の流れ（デスクトップは `worker_threads`）へ移す——コアのためではなく、列から外すため

- **何を変えるか**：起動時の全作品の走査（作品一覧の初回描画）を、別の流れ（worker）で丸ごと行い、結果を1回で受け取る。worker は自分の流れを持つので、拡張機能ホストの順番待ちを受けない
- **見込み**：実機の初回描画 4.6秒（中央値）→ 写しで測った素の時間（全作品で0.1〜0.3秒）＋受け渡し1回。**ただし、この見込みは「待ちの正体が流れの混み」という見立ての上に立っている。** 最初に試作で確かめるのがよい（下の選択肢B）。前回の一覧の控えで行が先に出る仕組み（0.94.7）が既にあるので、作者の目に見える差は「数字と種類が控えから本物に替わるまで」が早くなる所

### 3位　保存のたびに作品を丸ごと読み直すのをやめ、変わった話だけ読み直す（やり直さない作り）
