## まとめ（作者向け）

**いまの拡張機能で、計算そのものに時間がかかっている所はほとんどありません。** 遅く感じるときの時間の大半は「待ち」です。

- 起動して作品一覧が全部そろうまで、実機では**中央値4.6秒**。そのうち本当に計算していたのは**約0.2秒**（字数を数える 0.14秒・解析 0.04秒）。残りは、拡張機能ホスト（VS Code の拡張機能がみな乗っている1本の流れ）の**順番待ち**とファイルの読みでした。同じ作品を、混んでいない所で動かすと**0.1秒弱**で終わります
- 起動時の「点検」（GitHub との同期の確かめ）は実機で**12〜20秒**。中身は git の呼び出しで、**同じ置き場（書庫）の作品でも作品の数だけ git を7回ずつ呼んでいます**。写し（10フォルダー・置き場1つ）では、今の呼び方で**1.7秒（git 90回）**、置き場ごとに1回なら**0.12秒（7回）**でした。GitHub との通信（fetch）は1回約1秒
- **CPU の複数のコアで分けても、縮むのは計算の部分（実機で約0.2秒）だけ**です。コアを増やす手は、この拡張機能では効き目が小さい
- ただし「別の流れへ逃がす」こと自体には別の効き目があります。**混んだ流れから外れるので、順番待ちが消えます**（下の手2）。コアの数ではなく、列から外れることが効く

## 効く手（順位つき）

「効き目」は測った数字からの見込み。「ブラウザ版への影響」は CLAUDE.md の実装ルール7（ブラウザの VS Code でも動く形で書く）について。

### 1位　起動時の点検の git を、置き場ごとに1回・まとめて呼ぶ（やり直さない作り）

- **何を変えるか**：点検の最初で、作品ごとではなく**置き場（書庫）ごとに1回**だけ状態を読む。状態を読む git（`readSyncStatus` の中で7回：置き場の根・送り先の有無・枝名・上流・ahead/behind など）のうち、枝名・上流・ahead/behind・変更の一覧は `git status --porcelain=v2 --branch` 1回で取れるので、**7回を2〜3回に減らす**（置き場の根 `--show-toplevel` と送り先の有無 `remote` は status に出ないので残る）。置き場ごとの GitHub との fetch を**同時に**走らせる。終わりの `refreshAll`（今は登録作品ごとに順に読み直す）は、点検で読んだ状態を使い回す
- **見込み**：写しでは状態読みが 1.7秒→0.12秒（10フォルダー・置き場1つ）、さらに回数を減らして 0.12秒→**0.05秒前後（見込み。測っていない）**。実機の点検 12〜20秒は、残りがほぼ fetch の時間になり、置き場が数個なら**2〜4秒ほど**（fetch 1回約1秒を同時に回すため）。作者から見えるのは「右下の未記録の印が出そろうまで」と「開いたときに取り込みが終わるまで」が早くなること
- **もう1つの効き目かもしれないもの**：点検は起動の95ms目に始まり、作品一覧の走査と**同じ時間帯に**走っている（起動ログ：点検 開始 95ms → 初回描画 4,555ms → 点検 未了 14,561ms）。25作品×7回＝約175回の git を起こし、その返事を受けるのも同じ流れである。直したあとの起動ログで「下ごしらえ」と「ループの遅れ」も縮めば、**待ちの一部は自分の点検だった**と分かる。つまり1位は、2位の見立て（待ちの正体）を確かめるいちばん安い実験を兼ねる
- **直す範囲**：`core/git.ts`（`readSyncStatus` の読み方）、`features/handoffSync.ts`（`collectTargets` と fetch の並べ方）、`features/gitSync.ts`（`refreshAll`）。中くらい。git の出力の読み方を変えるので、既存の試験（分岐・競合・送り先なし）を全部通し直す要がある
- **ブラウザ版への影響**：無い。ブラウザ版は git を起こせないので点検そのものが走らない（`canRunProcesses()`）。変わるのは手元の VS Code だけ

### 2位　作品の走査を別の流れ（デスクトップは `worker_threads`）へ移す——コアのためではなく、列から外すため

- **何を変えるか**：起動時の全作品の走査（作品一覧の初回描画）を、別の流れ（worker）で丸ごと行い、結果を1回で受け取る。worker は自分の流れを持つので、拡張機能ホストの順番待ちを受けない
- **見込み**：実機の初回描画 4.6秒（中央値）→ 写しで測った素の時間（全作品で0.1〜0.3秒）＋受け渡し1回。**ただし、この見込みは「待ちの正体が流れの混み」という見立ての上に立っている。** 最初に試作で確かめるのがよい（下の選択肢B）。前回の一覧の控えで行が先に出る仕組み（0.94.7）が既にあるので、作者の目に見える差は「数字と種類が控えから本物に替わるまで」が早くなる所
- **話ごとに複数コアで回す必要は無い**：計算は全部で0.2秒ほどなので、8コアに分けても縮むのは0.2秒のうちの一部。1本の worker で足りる
- **直す範囲**：大きめ。`core/scanner.ts` は `vscode` を読み込んでいるので、そのままでは worker で動かない。設定の読み・本文フォルダーの決め方・数え方を `vscode` に頼らない部品として切り出し、worker 用の束を `esbuild.js` に足す。保存のたびの読み直しも同じ道に載せるかは別に決める
- **ブラウザ版への影響**：大きい。ブラウザ版の作品は `vscode-vfs://github/...` にあり、Web Worker からは `vscode.workspace.fs` が使えない（本文を読めない）。**ブラウザ版は今の道のまま**にし、worker はデスクトップだけで動的 import する（規則7の「`node:` を静的 import しない」）。`browserReach.test.ts` の見張りを worker の束にも向ける要がある

### 3位　保存のたびに作品を丸ごと読み直すのをやめ、変わった話だけ読み直す（やり直さない作り）

- **何を変えるか**：いまは1話を保存すると、その作品の全話を読み直す（`extension.ts` の `onDidSaveTextDocument` → `refreshForFile` → 作品の走査）。保存した1話だけを読み直し、合計を差し替える
- **見込み**：教科書チート（219話）で 69ms→1ms未満（1話分）。少ない作品（数十話）では元から5ms程度で差は小さい。混んだ流れでは1位・2位と同じく何倍にも膨らむので、長い作品を書いているときの保存後のもたつきが減る
- **直す範囲**：中くらい。`views/workTree.ts` の覚え（作品ごとの走査結果）を話ごとに持ち、`core/scanner.ts` に1ファイル分の口を足す。改名・削除・競合の印・合本ファイルの扱いを取りこぼさない試験が要る
- **ブラウザ版への影響**：無い（同じ道を通る。読み口は今と同じ）

### 4位　表記ゆれの検知を、話ごとに控えておく（やり直さない）か worker へ逃がす

- **見込み**：71万字で0.29秒が、2回目からは変わった話の分だけ（控え）。worker にすれば、押している間も打鍵が止まらない。押したときだけの0.3秒なので、作者の体感への効き目は小さい
- **直す範囲**：小〜中。`core/notationVariants.ts` は `vscode` を読まない純粋な部品なので、worker へは移しやすい
- **ブラウザ版への影響**：控えなら無し。worker にするならブラウザ版は Web Worker の束が別に要る（Web Worker にも本文を渡せば動く。ファイルを読む必要は無い）

### 直さなくてよいもの（測って小さかった）

- 原稿エディターの打鍵1回ぶんの計算（1ms。4万字でも5ms。まとめ待ちの120msに比べて小さい）
- 用語の索引を作る・照合する（0.2ms／219話で20ms。作品ごとに覚えてある）
- 提案パネルの台帳を読む（0.5ms）
- 作品の登録（0.1ms）

### そのほか（コードを直さずに試せること）

- **流れを握っている相手を確かめる**：実機で1回に0.8秒（最長2.0秒）詰まっているのは、測った中のどの処理より長い。VS Code の「開発者: 実行中の拡張機能を表示」で、起動時に時間を使っている拡張機能を見られる。ほかの拡張機能が原因なら、こちらのコードをいくら速くしても待ちは消えない
- **この拡張機能だけを別の拡張機能ホストで動かす設定**（`extensions.experimental.affinity`。VS Code の実験的な設定）を試すと、ほかの拡張機能と流れを取り合わなくなる。実験的なので、効くかと今の VS Code に残っているかは試して確かめる要がある。試すなら起動ログの「初回描画」「下ごしらえ」「ループの遅れ」で比べる
