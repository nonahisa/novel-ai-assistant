# AIの出力を「縛って落としている所」の洗い出し（2026-09-24）

対象：`src/prompts/*.ts`（指示）と `src/core/*Validation.ts`・`characterMerge.ts`・`recordChanges.ts`（検算とマージ）。
実測：`docs/measurements/*.json` の `runs[].detail.rejectedReasons` と `runs[].raw`（落とした中身）を全件集計した。集計の台本は scratchpad の `agg.js`・`rej.js`・`contra.js`。

**読み方**：「疑い」は「正しい指摘・情報を落としている疑い」の強さ。直すかどうかの判断はしていない（候補を並べただけ）。

## 機能ごとの詳細

### 1. 人物抽出（P-04a `prompts/characterExtract.ts`・検算 `core/characterExtractionValidation.ts`・マージ `core/characterMerge.ts`・`core/recordChanges.ts`）

#### 1-1. 性格（personality）【重点】

**指示**（`characterExtract.ts` 175〜187行）：性格だけは言動からまとめてよい。「どういう人か」を言い切り、根拠を括弧で添える。名前の響き・性別・ジャンル・他作品から推論しない。相反する面は両方書く。
**検算**：性格の中身を落とす条件は `isMeaningfulValue`（「記述なし」「本文から読み取れない」などの不在文）だけ。**抽出の段では、性格を不当に落としてはいない。**

**縛りが効いているのはマージの段である。**

| 縛り | どこ | 何のためか | 疑い | 根拠 | 直し方の候補 |
|---|---|---|---|---|---|
| **性格を「1つの値」として持ち、違う話で違う値が来たら「作中の変化」として畳み、本体を後の話の値へ入れ替える** | `characterMerge.fillOrConflict`（836〜965行）、`recordChanges.isFoldableConflict`・`foldCharacterConflicts` | 外見・所属・役割のような「その時点で1つ」の項目で、第1話「黒髪」→第7話「銀髪」を変化として残すため（6.18） | **高** | 性格は**同時に何面も成り立つ**。抽出はチャンク（話）ごとに**その話で見えた面だけ**を書くので、第1話「無愛想だが面倒見はよい」、第5話「臆病で慎重」が来ると、本体は第5話の「臆病で慎重」に替わり、資料には「無愛想…（第1話）→ 臆病…（第5話）」と**起きていない性格の変化**が並ぶ。プロンプトの「相反する面は両方書け」は1チャンクの中でしか効かない。**話をまたいで面を積み上げる道がどこにも無い**。設計書7719行も「性格：AIの言い換えでも動きやすい」と認めている | 性格を「変わらない項目」と「上書きする項目」のどちらでもない**積み上げる項目**にする（面ごとに話数と根拠を持つ一覧）／畳むとき性格だけは変化にせず「別の面」として並べる／性格の変化は作者の確認を経たものだけにする |
| **同じ話の中で違う性格の値が2つ出ると「食い違い」として作者の判断待ちに回す** | `isFoldableConflict`（「同じ話に2つの値が出ている。作中の変化では説明できない」） | 外見の取り違え（同じ第7話で黒髪と銀髪）を作者へ回すため | **高** | 1話を2チャンクに分けた長い話や、複数話を1チャンクで送るときに起きる。「臆病」と「優しい」は同時に成り立つのに「両方が同時に正しいことはない」という外見用の前提が当てられる | 性格（と外見の別部位）には「矛盾」ではなく「追記」として足す |
| 包含関係のときだけ「詳しいほう」を採る | `fillOrConflict` 899行 `value.includes(current)` | 「黒髪」→「短く切った黒髪」を変化にしないため | 中 | 性格は言い換えが多く、文字列の包含はまず起きない。**言い換えは全部「変化」になる** | 性格は包含ではなく「同じ面の言い換えか」を別に見る（AIに判定させるなら検算付き） |
| 性格の「変化」に関与度35点。3段以上で+5〜10、2話以上続くと+10、最新話で+5 | `core/changeSignificance.ts` 63行、設計書「ストーリーへの関与度」 | 紹介に何を書くかをコードで決めるため | 中（落とすのではなく**誤って載せる**側） | 言い換えで段数が増えるほど点が上がり、60点を超えると**紹介（summary）に「性格が変わった」と書かれうる**。上の1行目の副作用 | 性格の段数加点を外す／性格の変化は作者が認めたものだけ加点 |
| 性格の根拠は照合しない（レコード単位の `evidence` だけ） | `characterExtract.ts` 409行（evidence はレコードに1つ）、`recordChanges.changeMovesBody` | 「その人物が本文にいる」ことの捏造防止 | 中 | 性格の括弧の中の引用（「舌打ちしつつ最後まで付き合う」）は本文と照合していない。一方で**レコードの引用がある＝根拠あり**として、性格の「変化」が本体を動かせる（`changeMovesBody`）。**性格の根拠ではない引用で、性格が入れ替わる** | 性格の括弧内の引用を本文と照合し、通ったものだけ「根拠あり」にする |
| 捨てた語り手の中身に性格を載せない | `characterExtractionValidation.narratorDetails`（1174行。紹介・役割・外見・性別だけ） | 報告を短くするため | 中 | 語り手はたいてい主人公で、性格がいちばん厚く読める人物。今日の0.85.8で「中身を見せる」ようにしたが、**性格と口調は見せる対象から外れている**ので、作者が拾い直すときに性格は手で書き直すことになる | 報告は短く保ち、操作ログ（全文）には性格も載せる |

**人物の性格についての見立て（まとめ）**：抽出の指示と検算は、性格に対しては**むしろ緩い**（推論を認め、落とすのは不在文だけ）。作者の「妙な縛り」の感触の正体は、**マージが性格を外見と同じ「上書き型の1つの値」として扱っていること**だと見る。話ごとに見えた別の面が「作中の変化」として積まれ、本体は最後の話の一面に置き換わり、同じ話の中で2つの面が出れば「食い違い」として止まる。**性格を積み上げる受け皿が無い**ことが、正しく読めた面を資料から押し流している。

**全体を通して見えた形**（直し方の候補を選ぶときの手がかり）
1. **指示と検算の食い違い**がいちばん多い。指示どおりに答えると検算で落ちる形で、次のものがこれに当たる。
   - 既知のフルネームを name に使う → `ungrounded`
   - original を短く写す → `not_long`・`not_repeated`
   - 空配列で答える → 公募の提案が失敗扱い
   - 「」で括る → 口述の清書で落ちる
   - 間延びにも根拠を書く → `plot_reference_not_found`
   - 家族関係語でレコードを作らない → 検算は「おばあさん」を残す
2. **否定・不在の言い回しの網**（矛盾検知の `self_denied`・`no_setting`、逸脱の `self_denied`、読者の声の `ADVICE_PATTERNS`）は、**疑問形・理由形・部分的な不在・逆接**まで否定と読む。言い回しの網は、実測で仕込みの正解を落としていることが確かめられた唯一の型である。
3. **受け皿が無いときに捨てる機能**（推敲・矛盾検知・単話プロット・逸脱・人物の entityType）と、**最寄りへ寄せて残す機能**（世界観の `toWorldCategory` → `term`）が混在している。後者の作法を前者へ広げるのが、いちばん安く効く見込み。
4. **落とした中身が残らない**機能が多い。誤字脱字の記録は修正案も抜粋も持たず、人物の `ungrounded` は名前だけ、キャッチコピーの字数超えはログにも出ない。**落としすぎを実測で確かめられない**のはこれが原因で、どの直し方を選ぶにしても、先に「落とした中身を記録に残す」を入れると、あとの判断が測定でできるようになる。
