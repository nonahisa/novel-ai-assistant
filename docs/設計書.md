## 1. 概要

### 1.1 目的
テキスト/Markdownで書かれた小説作品を対象に、VSCode上でAI（Gemini / Claude / Ollama）を活用した執筆支援を行う拡張機能を開発する。

### 1.2 対象ユーザー
- カクヨム・小説家になろう等からダウンロードした既存作、または新規作を管理する個人作家
- 複数作品を並行して管理したい作家

### 1.3 対応AI（マルチプロバイダ対応）
| プロバイダ | 用途 | 備考 |
|---|---|---|
| Google Gemini API | クラウドAI（デフォルト候補） | 長文コンテキストに強み |
| Anthropic Claude API | クラウドAI | 高品質な文章校正・分析 |
| Ollama（ローカル） | オフライン/無料運用 | ローカルLLM、API課金なし |

**3つすべてを用意する必要はない。1つだけを選んで運用できることを前提とする。**

利用形態は以下の2モードを用意し、初期状態は「単一プロバイダモード」とする。

| モード | 内容 | 想定ユーザー |
|---|---|---|
| **単一プロバイダモード（既定）** | 1つのプロバイダ・モデルを選び、全AI機能をそれで実行する | 大多数。Claudeだけ、Ollamaだけ、といった運用 |
| 機能別割当モード（任意） | 機能ごとに異なるプロバイダ・モデルを割り当てる | コスト最適化をしたい場合のみ |

機能別割当モードは設定画面の「詳細設定」内に隠し、明示的に有効化しない限りUIに現れないようにする。未設定のプロバイダは選択肢として表示しない（APIキー未登録のGeminiが選べてしまい、実行時にエラーになる、という事態を防ぐ）。

詳細は「6. AIプロバイダ選択・抽象化層」を参照。

### 1.4 管理対象ファイル
- `.txt`（本文、なろう/カクヨムのDL形式想定。話数分割済み or 複数話まとめの両パターンに対応）
- `.md`（本文。ルビ機能はMDファイルのみ対応）

### 2.2 技術スタック（提案）
- 言語：TypeScript
- ビルド：esbuild もしくは webpack（VSCode拡張標準構成）
- UI：VSCode標準API（TreeView / WebView） + WebView内はReact（軽量に留める）
- ローカルDB：JSONファイル群を基本とし、統計データ量が増えた場合のみ `sqlite3`（better-sqlite3）へ移行可能な設計にしておく
- 差分検出：ファイルハッシュ（SHA-256）+ 行/段落単位のdiff（`diff` npm パッケージ）
- Git連携：`simple-git` パッケージ、またはVSCode組込みGit拡張のAPIを利用
- Markdownルビ：独自記法をパースしてWebView/プレビューで表示（後述）

### 2.3 マルチディスプレイ対応方針（重要な制約の明記）

VSCode拡張は「1つのウィンドウ内で複数パネルを配置する」ことが基本であり、OSレベルで完全に独立した複数ウィンドウをVSCode拡張自身が自由に生成することはできません。そのため、以下の現実的な方式で対応します。

- 資料ウィンドウ（キャラ/場所の参照パネル）、AI指摘パネル、統計グラフパネルは、それぞれ独立した **WebViewPanel** として実装する。
- VSCode標準機能「エディターをウィンドウの外へドラッグ」「新しいウィンドウに移動」を利用し、ユーザーが各パネルを別ディスプレイに配置できるようにする（拡張側は「別ウィンドウでの表示」を前提にレイアウト崩れが起きないよう、各WebViewをレスポンシブに作る）。
- 本文編集エディターを1画面目、資料パネル・AI指摘パネル・統計パネルを2画面目、という運用を想定した「推奨レイアウト適用コマンド」を用意する（`エディターグループの分割`をコマンドから自動実行）。

### 3.3 大規模テキスト対応（最大1000万字）とキャッシュ設計

- 全AI処理は「チャンク分割 → 個別処理 → 統合」を基本アーキテクチャとする。チャンクサイズは各AIプロバイダのコンテキスト上限とコストを踏まえ、`config.json` で機能ごとに調整可能にする（デフォルトは章単位、または約2万字単位）。
- **差分処理（節約設計）**：各ファイル・各チャンクごとにSHA-256ハッシュを `.aiwriter/cache/file_hashes.json` に記録。次回実行時、ハッシュが一致するチャンクはAI再処理をスキップし、キャッシュ済みの生成結果（人物一覧・世界観・あらすじ等への反映分）を再利用する。
- キャラクター一覧・場所一覧・世界観まとめ等の「全文横断で生成する」機能は、**差分チャンクのみを再解析し、既存の一覧に追記/更新マージ**する方式とする（全文の毎回全再生成は行わない）。
- 作者による手動編集（`author_notes`、加筆済みキャラクター情報等）は自動生成マージ時に **上書きしない** ことをデータモデル上のルール（`auto_generated: false` のフィールドは保護）とする。

### 3.4 外部ツールとの共存（重要な前提）

本文ファイルは、本拡張機能以外のツールでも編集される可能性がある。想定される例は以下の通り。

- 別のテキストエディタ（秀丸、サクラエディタ、Word等）
- 執筆専用ソフト（Nola、TATEditor 等）
- 投稿サイトからの再ダウンロードによる上書き
- スマートフォンでの編集とクラウド同期
- Git経由で別PCから同期

この前提は、単に「変更を検知して再読み込みする」だけでは済まない。**外部編集を考慮しないと、作者の原稿を破壊する事故が起きうる**。以下、危険度の高い順に対策を定める。

#### 3.4.1 上書き事故の防止（最優先）

AIによる修正（誤字修正、推敲適用、ファイルリネーム）を適用する際、**読み込み時点と適用時点でファイルが変わっていないことを必ず検証する**。

```
1. AI処理のためにファイルを読む   → その時点のハッシュを記録
2. AIが応答を返す（数十秒〜数分）  ← この間に外部編集が起きうる
3. 作者が修正を承認
4. 適用直前に再度ハッシュを計算
5. 記録したハッシュと一致するか検証
   - 一致   → 適用する
   - 不一致 → 適用を中止し、「他のツールで変更されています」と警告
```

不一致の場合、選択肢を提示する。

- 再読み込みしてAI処理をやり直す（推奨）
- 差分を表示して手動で判断する
- 強制的に適用する（既定では選ばせない）

この検証を省くと、AIが応答を返す間に外部で加筆された内容を、古い本文で上書きして消してしまう。**AI処理は応答待ち時間が長いため、この危険が現実的に発生する。**

#### 3.4.2 文字コード・改行コードの保持

外部ツールはUTF-8とは限らず、Shift_JISやCRLFで保存することがある。読み込み時に検出した以下の情報を保持し、**書き戻すときは元の形式を維持する**。

| 項目 | 保持する値 |
|---|---|
| 文字コード | UTF-8 / UTF-8(BOM付) / Shift_JIS |
| 改行コード | LF / CRLF / CR |
| 末尾改行 | 有無 |

これを怠ると、AIで誤字を1文字直しただけで全行が変更扱いになり、Gitの差分が壊れる。外部ツール側で文字化けが起きることもある。

書き戻し時は、**変更箇所のみを置換し、ファイル全体を再生成しない**。行全体・ファイル全体の置き換えは行わない。

#### 3.4.3 外部変更の検知と追従

- `vscode.FileSystemWatcher` で本文フォルダを監視し、作成・変更・削除を検知する。
- 変更検知時は、該当ファイルのキャッシュを破棄して再計測する。全ファイルの再走査は行わない。
- 大量のファイルが一度に変更された場合（Git pull、フォルダ同期など）は、個別処理せず一定時間まとめてから一括で再走査する（デバウンス）。
- VSCodeが起動していない間の変更も拾う必要があるため、**起動時に全ファイルのハッシュを照合**し、変化したものだけキャッシュを破棄する。

#### 3.4.4 AI指摘の陳腐化

AI指摘パネルに表示中の指摘は、本文が外部編集されると位置がずれて無効になる。

- 指摘は行番号だけでなく、**該当箇所の引用テキストを併せて保持**する（プロンプト設計で `original` / `excerpt` を必須にしているのはこのため）。
- 適用時は行番号を信用せず、引用テキストで再検索して位置を特定する。
- 見つからない場合、その指摘を「本文が変更されたため無効」として灰色表示にし、適用不可とする。
- ファイル全体のハッシュが変わった場合、そのファイルの指摘一覧にまとめて「本文が変更されています。再チェックを推奨します」と表示する。

#### 3.4.5 ファイル構成の変化への追従

外部でファイルが追加・削除・リネームされた場合、生成済みデータとの整合が崩れる。

- `characters.json` の `appeared_chapters` などが、存在しない話数を参照する状態になりうる。
- 対策として、参照は**話数（数値）ではなくファイルの安定IDで持たず、話数で持ちつつ、走査時に実在チェックを行う**。実在しない話数への参照が見つかった場合、データからは削除せず「参照先が見つかりません」と警告表示する（作者が一時的にファイルを移動しただけの可能性があるため、勝手に消さない）。
- 話数の重複・欠番も検出して一覧に表示する。外部ツールでのリネーム時に起きやすいため。

#### 3.4.6 編集中バッファの扱い

VSCodeで開いている未保存のファイルと、ディスク上の内容は異なる。

- 文字数計測は、エディタで開いている場合は**未保存の内容（`TextDocument`）を優先**する。ディスクを読むと、書いている途中の文字が反映されない。
- 逆にAI処理は、**未保存の変更がある場合は保存を促す**。ディスクとバッファが食い違う状態で修正を適用すると競合するため。

#### 3.4.7 拡張機能専用領域の明示

- `.aiwriter/` 配下は本拡張機能の管理領域であり、外部ツールが編集することは想定しない。破損時は再生成できる設計とする（キャッシュは再計算可能、統計は失われると痛いためバックアップを持つ）。
- `設定/` 配下（characters.json 等）は作者が手動編集する可能性があるため、**外部編集を許容する**。読み込み時にJSONのパースエラーを検知したら、上書きせずエラーを表示して作者に修正を促す。壊れたJSONを勝手に修復・上書きしない。

#### 3.4.8 排他制御の方針

複数プロセスからの同時書き込みを完全に防ぐことはできないため、以下の実務的な方針とする。

- 拡張機能がファイルを保持し続けない（読む・書くを短時間で終える）。
- 書き込みは3.4.1のハッシュ検証とセットで行う。
- ロックファイルは作らない。異常終了時に残ると作者が対処できなくなるため。

### 3.5 GitHub同期を前提としたデータ設計

本文だけでなく、**GitHub経由で別の環境から更新される**ことを前提とする。

**利用形態の前提：編集するのは同一人物であり、複数の環境を渡り歩いて執筆する。**

- 自宅のデスクトップで執筆 → push
- 外出先のノートPCで続きを書く
- スマートフォンのGitクライアントやGitHubのWeb UIから修正

この前提は設計方針を大きく左右する。複数人の共同編集であれば「他者の意図を尊重してマージする」必要があるが、同一人物であれば**競合は本質的に事故**である。「二人の意見がぶつかった」のではなく「同期を忘れて二重に書いてしまった」だけであり、正しい対応は解決ではなく**予防**となる。

したがって以下の順で対策を組む。

1. そもそも競合させない（3.5.1）
2. 起きたら確実に気づかせる（3.5.2、3.5.3）
3. 解決は本人が選ぶ（3.5.4）

#### 3.5.1 予防：書き始める前に気づかせる

競合が起きる流れは決まっている。

```
デスクトップで第8話を執筆 → pushし忘れ
　　↓
ノートPCで作業開始（pullしていない）→ 第8話を別内容で執筆
　　↓
両方に異なる第8話が存在 → 競合
```

**分岐が起きるのは「pullせずに書き始めた瞬間」であり、競合が表面化するのはその後。** 書いた後に警告しても手遅れなので、書き始める前に止める。

- **VSCode起動時、および作品を開いた時に自動でfetchする**（fetchは取得のみでローカルを変更しないため安全）。
- リモートが先行している場合、本文ファイルを開く前に通知する。

  > 別の環境での変更が未取得です（3件）。取り込んでから執筆することを推奨します。
  > ［取り込む］［このまま開く］

- 未取得の変更がある状態で編集を始めたら、**エディタ上部に警告バーを常時表示する**。通知は消えてしまうが、警告バーは残り続けるため気づける。
- 逆に、ローカルに未pushのコミットがある場合も表示する。「この環境の変更が未送信です（2件）」。**別の環境へ移る前に気づけるかどうかが分かれ目**になる。

#### 3.5.2 検知：最終編集環境の記録

同一人物であるため強制ロックは不要だが、「直前にどの環境で書いていたか」が分かると事故を防げる。

`.aiwriter/session.json`（同期対象）に記録する。

```json
{
  "lastEditedBy": "desktop-a1b2",
  "lastEditedAt": "2026-08-04T22:15:03+09:00",
  "lastEditedFile": "本文/008.txt"
}
```

別の環境で開いた際、この記録が自分以外かつ新しければ「デスクトップで3時間前に第8話を編集しています」と表示する。ロックはせず情報提示にとどめるため、異常終了してもロックが残って詰まることがない。

#### 3.5.3 競合マーカーの混入検知（最優先）

Gitの競合が解決されないまま残ると、本文に以下が混入する。

```
<<<<<<< HEAD
　灯は歩き出した。
=======
　灯はゆっくりと歩き出した。
>>>>>>> origin/main
```

この状態のファイルをAIに渡すと、競合マーカーごと解析され、修正適用で原稿が破壊される。

- **全ファイルの読み込み時に競合マーカーを検出する。** 検出したファイルは文字数計測の対象外とし、ツリー上で警告アイコンを表示する。
- 競合マーカーを含むファイルに対しては、**AI処理を実行させない**（実行前にブロックする）。
- 「未解決の競合が N 件あります」と通知し、解決を促す。

#### 3.5.4 解決：本人が選べる形で提示する

同一人物であるため、「どちらが正しいか」は本人が見れば分かる。機械的なマージを試みるより、**両方を並べて選ばせる方が速く確実**である。

競合発生時、専用のWebViewパネルで以下を提示する。

| 項目 | 表示内容 |
|---|---|
| この環境の版 | 本文、文字数、最終更新時刻 |
| 別環境の版 | 本文、文字数、最終更新時刻、どの環境か |
| 差分 | 行単位の差分表示 |

選択肢は「こちらを採用」「別環境のものを採用」「両方を残す」の3つ。

**「両方を残す」を必ず用意する。** 判断に迷う場合、片方を消すより `008.txt` と `008.conflict-laptop.txt` として両方残す方が安全である。原稿は失われた時の損害が大きく、あとから統合する手間の方がはるかに軽い。

自動マージ（両方の変更を機械的に統合する）は行わない。文章は行単位で機械結合すると意味が壊れるため。

#### 3.5.5 設定ファイルの分割（競合を減らす構造）

`characters.json` のような大きな1ファイルは、2つの環境で別々の人物を追記しただけでも競合する。JSONは行単位マージと相性が悪く、自動解決が失敗しやすい。

そこで、**1エンティティ1ファイル**に分割する。

```
設定/
├─ characters/
│  ├─ char_001_月島灯.json
│  ├─ char_002_白瀬澪.json
│  └─ _index.json          ← 表示順など、一覧固有の情報のみ
├─ locations/
│  ├─ loc_001_図書塔.json
│  └─ _index.json
└─ terms/
   └─ term_001_魔導書庫.json
```

これにより、別の環境で別々の人物を追記した場合は競合しない（別ファイルのため）。同じ人物を両環境で編集した場合のみ競合するが、その頻度は大きく下がる。

ファイル名に人物名を含めるのは、GitHubの差分画面やスマートフォンから見たときに、何の変更か分かるようにするため。IDだけだと `char_007.json` が誰なのか判別できない。**出先で確認する場面を想定すると、ファイル名の可読性は実用上の差になる。**

`_index.json` には表示順やグループ分けのみを持たせ、人物の実データは含めない。中身が薄いほど競合しにくい。

#### 3.5.6 統計データの端末分離

執筆量統計は、同じ日に2台で書くと必ず競合する。「今日3000字」と「今日2500字」がぶつかり、どちらかが失われる。同一人物が環境を移動しながら書く以上、これは日常的に発生する。

対策として、**端末ごとにファイルを分け、表示時に合算する**。

```
.aiwriter/stats/
├─ daily.desktop-a1b2.json     ← 端末Aの記録
├─ daily.laptop-c3d4.json      ← 端末Bの記録
└─ ...
```

端末IDは初回起動時に生成してローカル設定に保持する。合算は読み込み時に行い、書き込みは自分の端末のファイルにのみ行うため、構造上競合しない。

同一人物の記録である以上、合算値こそが本人の総執筆量になる。したがって統計は既定で**同期対象に含める**。端末別の内訳も表示できるようにしておくと、「自宅では書けているが外では進まない」といった傾向が見える。

#### 3.5.7 キャッシュの共有

`.aiwriter/cache/` は既定でGit同期対象外としている。しかし別PCで作業を始めると、全チャンクをAIで再処理することになり、1000万字規模ではコストと時間が無視できない。

そこで、**キャッシュを同期対象に含めるオプション**を用意する。

| 設定 | 挙動 | 向いているケース |
|---|---|---|
| 同期しない | 端末ごとに再処理 | 1台のみで執筆 |
| 同期する（複数環境なら推奨） | 処理結果を共有し再処理を回避 | 複数環境を渡り歩く場合 |

キャッシュはハッシュをキーとした処理結果のため、内容が同じなら結果も再利用できる。ただしプロンプトのバージョンやモデルが異なると結果の一貫性が崩れるため、**キャッシュのキーにプロンプトversionとモデル名を含める**（3.3節の設計を拡張）。異なるモデルで生成された結果は再利用せず、再処理する。

#### 3.5.8 pull後の再走査

pullで大量のファイルが一度に変わるため、3.4.3のデバウンスに加えて以下を行う。

- Gitの操作（pull / checkout / merge）を検知したら、**全ファイルのハッシュを照合**し、変化したものだけキャッシュを破棄する。
- 変化したファイル数が多い場合、「N件のファイルが更新されました。設定一覧の再生成を推奨します」と通知する。自動でAI処理は実行しない（コストが発生するため作者に選ばせる）。
- 削除されたファイルへの参照は3.4.5の方針どおり、勝手に消さず警告表示にとどめる。

## 5. 各機能の詳細設計

### 5.1 作品管理・複数作品対応
- サイドバーに「作品ランチャー」TreeViewを新設。登録済み作品フォルダの一覧、各作品の総文字数・最終更新日を表示。
- 作品追加は「フォルダを選択して登録」または「新規作品作成（テンプレフォルダ生成）」の2方式。
- 作品切替時、対象作品の `.aiwriter/config.json` を読み込み、以降の全AI処理・表示はその設定に従う。

### 5.2 ファイル管理
- 「本文/」フォルダを右クリック→「新規話数ファイル追加」。既存ファイルの最大話数を自動検出し `+1` した番号（例 `007.txt`）を初期ファイル名として生成。
- 話数分割ファイル・合本ファイルは、ファイル名の数値パターン（`001`, `003-005` 等）をパースするルールベース解析＋AI補助解析（パターン不一致時）で話数レンジを認識する。

### 5.3 文字数計測・統計
- ファイル保存時、または明示的な「文字数再計測」コマンドで、ファイル単位・フォルダ単位（合計）の文字数を算出（日本語想定のため改行・記号除いた純文字数、および総文字数の2種を表示）。

#### 5.3.1 原稿用紙換算は割り算で求めてはならない

**文字数を400で割っても原稿用紙の枚数にはならない。** 原稿用紙は20字×20行であり、1行20字で折り返すため、段落の最終行には余白が残る。21字の段落は2行を占め、残り19マスは空白になる。空行も1行分の場所を取る。小説は会話文や短い段落が多いため、この余白が積み上がる。

実データでの差は大きい。

| 作品 | 純文字数 | 割り算 | 行数から算出 | 差 |
|---|---|---|---|---|
| 19話・4.3万字 | 43,755字 | 110枚 | **190枚** | +73% |
| 1ファイル・73万字 | 732,774字 | 1,832枚 | **3,118枚** | +70% |

**正しい算出方法**（`countManuscriptLines`）：

```
各行が占める原稿用紙の行数 = ceil(その行の文字数 / 20)   ※空行は1行
枚数 = ceil(総行数 / 20)
```

字下げの全角スペースも1マスを使うため、空白を除いた純文字数ではなく、**行ごとの見た目の文字数**で数える。ルビは投稿サイトの扱いに合わせて字数に含めない。

**集計は枚数ではなく行数で合算する。** ファイルごとに枚数を出して足すと、各ファイルの端数が切り上がって誤差が積み上がる。`CharCounts.manuscriptLines` として行数を保持し、合算後に枚数へ変換する。

**禁則処理は考慮しない。** 行頭の句読点を前行へ送る（ぶら下げ）などは組版側の裁量で変わるため実装しない。実際の印刷枚数は数%前後するので、UI表記は「約N枚」とする。
- 統計は `stats/daily.json` 等に加算記録し、TreeView右上のボタンから「執筆量グラフ」WebViewパネルを開く（**日次・週次・月次・年次**の4粒度を切替表示、Chart.js等で描画）。
- 月次は「当月の日別推移」と「過去12ヶ月の月別合計」の2ビューを持ち、月間目標字数に対する達成率も併せて表示する。集計の基準となる日付境界（日付変更時刻、週の開始曜日）は `config.json` で設定可能とする。

### 5.4 プロットモード
- コマンド「新規作品を始める（プロットモード）」実行で、`plot.md` の初期テンプレート（タイトル/ログライン/テーマ/モチーフ/世界観/舞台/人称/行動原理/あらすじ箇条書き/主要登場人物概要）を生成し、専用WebViewエディタを開く。
- 各項目入力欄の横にAIチャット形式の助言パネルを併設し、入力内容に対して「ここが曖昧です」「テーマとログラインの整合性は？」等の助言を返す（対話はストリーミング表示）。
- 既存作からの逆算生成コマンドも用意（本文全チャンク解析→プロット項目を推定生成→作者が加筆修正）。
- `plot.md` 保存時、内容差分を検出し、`characters.json`（主要登場人物欄）、`world.md`、`locations.json` 等へ自動反映（差分マージ、作者加筆分は保護）。

### 5.5 世界観・登場人物・場所のAI自動生成
- いずれも「全文差分チャンク解析→既存JSON/MDへのマージ更新」で実装（3.3節の差分設計に準拠）。
- 登場人物：本文からの言及箇所を集約し、性格・行動動機・外観・一人称/呼称・登場話数を生成。未登場人物（設定のみ存在するキャラ）は `status: "未登場"` として同一UIで管理。

#### 5.5.1 呼称（一人称・二人称）の管理

二人称は「その人物が使う言葉」ではなく「誰が誰をどう呼ぶか」という**方向を持つ関係データ**として管理する。単一フィールドでは以下が表現できないため、構造を分ける。

- AがBを「白瀬さん」と呼び、BがAを「灯」と呼ぶ（非対称）
- 同じ相手でも場面によって呼び方が変わる（平時／怒った時／人前／二人きり）
- 関係の変化に伴って呼び方が変わる（第7話まで「白瀬さん」、第8話から「澪」）
- 相手が不特定の場合の既定の二人称（「君」「お前」）

**データ構造の方針**

| 項目 | 格納先 | 内容 |
|---|---|---|
| 一人称 | `first_person` | 既定形＋場面別の変化形（`variants`） |
| 既定の二人称 | `default_second_person` | 特定の相手を持たない一般的な呼びかけ |
| 相手別の呼称 | `address_terms` | 呼ぶ側の人物レコードに、相手ごと・呼び方ごとに配列で保持 |

`address_terms` は**呼ぶ側のレコードに格納する**（方向が明確になるため）。AがBを呼ぶ呼称はAのレコード、BがAを呼ぶ呼称はBのレコードにある。相互の呼称を並べて見たい場合は、後述のマトリクス表示で解決する。

`status` は `current`（現在使用中）と `past`（過去に使っていた）を持つ。過去の呼称を削除せず残すことで、「第5話を書き直す時に、当時の呼び方を確認する」という用途に対応する。ここが単純な上書き方式との大きな違いになる。

**UI：呼称マトリクス**

キャラクター一覧の1タブとして、全登場人物の呼び合いを一覧できる表を用意する。

```
        →呼ばれる人
呼ぶ人↓   月島 灯        白瀬 澪        黒木 玲司
月島 灯    —             澪(現)         黒木さん
                         白瀬さん(〜7話)
白瀬 澪    灯くん         —             先輩
黒木 玲司  月島          白瀬            —
```

セルをクリックすると呼称の詳細（場面別の使い分け、登場話数、根拠となる本文）を編集できる。空欄のセルは「まだ会話していない、または未抽出」を意味し、作者が手動で埋めることもできる（未登場人物との関係も設定可能）。

**呼称の変化タイムライン**

呼び方の変化は関係性の変化を示すため、物語上の重要な情報になる。人物詳細画面に、呼称が切り替わった話数を時系列で表示する。

```
第1話  白瀬さん   （初対面）
第8話  澪         ← 呼び方が変化
```

**矛盾検知との連携**

呼称データは矛盾検知（P-12）の入力として使う。「第10話で急に『白瀬さん』に戻っている」といった不整合を検出できる。ただし、意図的に呼び方を戻す演出（喧嘩、他人行儀になる場面）もあるため、指摘は断定形にせず `confidence` を添える。

**用語ハイライトとの連携**

呼称のうち、固有名詞を含むもの（「澪」「白瀬さん」「灯くん」）はハイライト対象の別名（`aliases`）として自動登録し、本文中で青字表示＋ホバー参照ができるようにする。一方、「君」「お前」「あなた」のような一般語はハイライト対象から除外する（本文が青字だらけになるため）。除外語リストは編集可能とする。

**作者による保護**

`author_locked: true` を設定した呼称エントリは、AI再抽出時に上書き・削除しない。作者が意図して設定した呼び方（まだ本文に登場していない未来の呼称など）を保護するため。
- **顔アイコン管理**：現時点では外部で用意した画像ファイルの割当てに対応する。`設定/icons/` フォルダに画像（png / jpg / webp）を置くか、キャラクター詳細UIから「画像を選択」またはドラッグ＆ドロップで登録すると、拡張機能が同フォルダへコピーし `icon` フィールドへパスを記録する。表示用サムネイル（推奨128×128px程度）は自動リサイズして生成する。
- アイコンのAI自動生成は**将来の追加機能として予約**する。そのため、データモデルに `icon_source`（external / generated / none）と `icon_prompt` を先行して定義し、AI画像生成を後付けしても既存の外部画像運用と共存できる構造にしておく。生成画像も同じ `設定/icons/` に保存され、外部画像と同一の参照経路で扱えるようにする。
- 場所：地域（大分類）ごとにグルーピングして表示。未登場場所も同様に管理。

#### 5.5.2 モブキャラ（集団名詞・汎用役職名）の分離管理

登場人物抽出は、名前を持つ人物だけでなく「取調官たち」「金貸したち」のような複数人をまとめた表現や、「冒険者」のように特定の一人に固定できない汎用的な役割語まで、個々の人物レコードとして生成してしまう問題が実データ検証で確認された。ネームドキャラと同じ一覧に並ぶと、名前のある登場人物を探す妨げになる。

**判定基準**

| 分類 | `is_mob` | 例 |
|---|---|---|
| 複数人をまとめた表現（「〜たち」） | true | 取調官たち、金貸したち |
| 個人ではなく属性・集団として使われる汎用語 | true | 冒険者、村人 |
| 無名でも本文中で一貫して特定の一人を指す描写 | false（個人として扱う） | 老いた門番 |

**データ構造の方針**

人物レコードに `is_mob: boolean` を追加する。既存の「未登場人物」（`status: "未登場"`）と同様、削除ではなくフラグで区別する方式を採る。誤判定時に作者が手動でフラグを戻せるようにし、AIの判定はあくまで初期値とする。

**UI**

キャラクター一覧では `is_mob: true` のレコードをネームドキャラと区別し、既定では折りたたみ／別セクション表示とする（一覧から完全に除外はしない。作者が「集団として書いた存在」を後から個人として書き分けたくなるケースがあるため）。

**精度に関する注記**

この判定は「本文中の当該箇所だけで完結する局所的な判断」であり、5.5.1節の呼称抽出のように話数をまたいだ一貫性の維持を要求しない。そのため実装難度は比較的低いと見込むが、実際の判定精度（境界例：物語後半で集団の一員が個別のキャラクターとして書き分けられる場合など）は実データ検証で確認する。

#### 5.5.3 能力（魔法・超能力・スキル）の抽出と一覧化

ジャンルによって呼び名は変わるが（ファンタジーなら魔法、伝奇なら超能力、現代ものなら得意なスキル）、「誰が何をできるのか」という情報は作品を通じて一貫性を保つ必要がある点で共通する。矛盾検知の対象としても価値が高いため、人物設定に含めたうえで、独立した一覧としても管理する。

**総称はジャンルに合わせて可変とする**

`ability_system.genre_label` に作品側の総称（「魔法」「超能力」「スキル」「異能」等）を持たせ、UI文言や生成プロンプトで使う。作者が現代ものを書いているのに「魔法一覧」と表示されるのを避けるためである。初回抽出時にAIへ本文から推定させ、作者が変更できるようにする。

**定義と保有状況を分離する**

能力の定義（効果・制約・代償）は `abilities.json` に、人物ごとの保有状況（習得済みか・いつ使ったか）は人物レコードの `abilities[]` に置く。同じ能力を複数人が使う場合に定義が重複すると、設定変更のたびに全員分を直す必要が生じ、食い違いの温床になるためである。

**抽出時の方針**

- 本文中で実際に使用・言及された能力のみを対象とし、AIに能力体系を創作させない。
- 効果や制約は本文から読み取れる範囲のみを書く。「〜だろう」「おそらく」といった推測は入れない。
- 能力名は本文の表記をそのまま使う。ルビがある場合は `reading` に格納する。
- 同一能力の別表記（「灯火」と「ともしび」）は登場人物の別名と同じ方式で `aliases` に集約する。

**能力体系の無い作品では何も出さない**

すべての作品に能力体系があるわけではない。実データ検証（「こちら冒険者ギルド生活保護課!!」）では、能力体系を持たない作品に対してAIが次のような候補を返した。

```
左手だけでなんとかできる      ← 説明文であって能力名ではない
左手一本で扱う短剣だけ        ← 同上
魔力 / スキル / 戦闘能力      ← 総称であって個別の能力ではない
冒険者ギルドの保険制度        ← 制度であって能力ではない
```

**無いものを探させると、AIは何かしら埋めようとする。** プロンプトに「該当がなければ空配列」と書いても8Bモデルには効かなかったため、コード側で弾く（`isSpecificAbilityName`）。判定は3つ。

- 総称そのもの（「魔法」「スキル」「能力」等）および確定済みの `genreLabel` と一致するもの
- 説明文になっているもの（「〜できる」「〜だけ」のように活用語尾で終わる）
- 制度・組織を指すもの（「〜制度」「〜ギルド」等）

**境界事例の扱い（実データ検証で決定）**

「教科書チート」（73万字・能力体系あり）での検証で、判断に迷う3種類が出た。方針を分けて決めた。

| 事例 | 方針 | 根拠 |
|---|---|---|
| 「剣術」「槍術」「弓術」 | **残す** | 一般的な武術に見えるが、本文で「希望者に剣術、槍術、弓術、神術といった…」と神術・仙術と並列に列挙されており、この作品では正式な能力である |
| 「聖紋神術の同時発動」 | **統合候補として提示** | 「聖紋神術」の使い方であって別能力ではない。ただし「炎槍」と「大炎槍」のように別能力のこともあるため自動統合はしない |
| 「石造りの建物」 | **弾く** | 本文2箇所とも情景描写であり、特定の場所を指していない |

**何を能力とするかは作品が決める。** 「剣術」は多くの作品では一般的な技量だが、この作品では能力体系の一部である。コード側でこれを判定することはできないため、一般的な語であることを理由に弾いてはならない。

判断の基準は「**削除は作者に見えない損失、残存は見える手間**」という非対称性である。落とした能力は作者から見えない（存在したことすら分からない）が、余分に残った能力は一覧を見れば消せる。したがって迷う場合は残す側に倒す。これは「モブは消さずフラグで区別する」「省略形は自動統合しない」と同じ考え方である。

弾いてよいのは「特定の対象を指していないことが確実」な場合に限る。情景描写の判定（`isDescriptivePlace`）は、普通名詞で終わり・素材や形状の修飾語で始まり・固有名詞を含まない、の3条件すべてを満たすものだけを対象とする。「冒険者ギルドの二階の事務室」のように説明的でも特定の場所を指す名前を巻き込まないためである。

**一覧生成**

コマンド「能力一覧を生成」で、`abilities.json` からMarkdownの一覧を `設定/abilities.md` へ出力する。カテゴリ別に見出しを立て、各能力に効果・制約・使用者・登場話数を並べる。設定資料としてそのまま渡せる形を目指す。

ただし**能力が1件も抽出されなかった作品では、`abilities.md` を生成せず、UIにも能力の項目を表示しない**。能力体系の無い作品に空の「能力一覧」が並ぶのは、作者にとって意味のない項目が増えるだけで害があるためである。場所・登場人物も同様に、該当が無ければ出さない。

**矛盾検知との連携（将来）**

「第3話で失った能力を第10話で使っている」のような不整合は、`abilities[].mastery` の遷移と `appeared_chapters` を突き合わせれば機械的に検出できる。5.10節の矛盾検知に組み込む。

### 5.6 作品紹介文・あらすじ生成、サブタイトル提案、キャッチコピー提案
- 「作品紹介文」はsynopsis.mdへ、章あらすじは chapter_synopses.json へ格納。

**キャッチコピー提案機能**
- コマンド「キャッチコピー案を生成」で、プロット（ログライン・テーマ・主人公の行動原理）と作品紹介文、および冒頭数話の本文を入力として、**読者が読みたくなる短いキャッチコピーを3案**生成する。
- 3案は互いに方向性を変えて提案させる（例：①謎・引きで惹く型、②感情・関係性を打ち出す型、③世界観・設定のスケールで惹く型）。方向性の内訳は `config.json` で変更可能とする。
- 各案は目安30字以内。提案時には案ごとに「狙い（なぜ読者の興味を引くか）」を一行添えて表示し、作者が判断しやすいようにする。
- 選択UIはWebViewで表示し、作者は「採用」「再生成」「手直しして採用」を選べる。採用された案は `synopsis.md` の冒頭へキャッチコピーとして書き込まれる。
- 過去に生成・却下した案も `.aiwriter/cache/` に履歴保持し、再生成時に同じ案の重複提示を避ける。
- あらすじ生成実行時、対象ファイル名が初期形式（数字のみ、例 `007.txt`）であれば、AIに「15字以内のサブタイトル案」を追加生成させ、確認ダイアログ（WebViewまたはQuickPick）で提示。
- 作者が承認した場合のみ、`話数_サブタイトル.拡張子`（例 `007_湖畔の誓い.txt`）へリネームを実行し、リネーム履歴を `.aiwriter/logs/ai_actions.log` に記録。

### 5.7 用語ハイライト（種類別の色分け＋ホバー資料表示）

**種類ごとに色を変える**

当初は一律の青字装飾としていたが、種類ごとに色を分ける。地の文で「図書塔」と「灯」が並んだとき、同じ色ではどちらが人物か分からないためである。

| 種類 | ライト | ダーク | 理由 |
|---|---|---|---|
| 登場人物 | `#1a5fb4` | `#7cb7ff` | 最も数が多く、既定色として馴染みがある |
| 場所 | `#1c7c3c` | `#7ee08a` | 人名と混ざらない色相 |
| 能力 | `#7a3ea3` | `#d3a4f5` | 地の文で目立ちすぎない明度 |

ライト・ダークの両テーマで読める明度を選ぶ。

**モブは装飾しない**

`isMob: true` の人物は数が多く、「兵士たち」「冒険者」のように地の文の普通名詞と重なりやすい。装飾すると本文が色だらけになって読めなくなるため対象外とする。

**ホバー**

該当語にカーソルを合わせると、その種類に応じた要点を表示する。別名で一致した場合は「「白瀬さん」として登場」のようにどの呼び方で当たったかを示す。`conflicts`（作者の判断待ち）もホバーに出し、本文を書いている最中に食い違いへ気づけるようにする。

本文由来の文字列をそのまま出すため、Markdown記法はエスケープする。設定に「\*強調\*」のような表記が入っていても、装飾として解釈させず読めるべきである。

**性能：走査は本文1回、装飾は表示範囲のみ**

用語ごとに本文を走査する方式は、設定が増えるほど遅くなる。本文を1回だけ走査して全用語を同時に照合する（Aho-Corasick法、`termIndex.ts`）。

さらに、装飾の対象は**画面に表示されている範囲**に限る。73万字の作品全体を毎回走査するとスクロールが引っかかるためである。前後50行の余白を取り、スクロール直後の未装飾を減らす。入力のたびに走らせないよう150msまとめてから処理する。

**重なりの解消**

「灯」と「灯火」が両方登録されている場合、「灯火」の一部を「灯」として二重に装飾しない。前から順に見て、同じ位置から始まる場合は長い方を採る（最左最長）。

採用済みの装飾を毎回見比べる実装は、用語が数万回出現する作品で編集のたびに約8秒かかっていた（性能テストで検出、走査1回の方式へ変更して41msに短縮）。

### 5.8 誤字脱字検知・修正
- 対象範囲（現在ファイル／フォルダ全体／差分のみ）を選択して実行。AI検知結果を「AI指摘パネル」に一覧表示（該当箇所・指摘理由・修正案）。
- 各指摘に「適用」「無視」ボタンを配置し、作者が個別承認した箇所のみ本文を書き換える（一括適用オプションも用意するが既定はOFF）。

### 5.9 推敲支援（シンプル方針）
- 要求どおり「できるだけシンプル」を優先し、文体の大幅改変は行わず、以下に限定した提案とする：冗長表現の簡潔化、係り受けの分かりにくさ、同語反復の解消。
- 誤字脱字と同様、AI指摘パネルでの提示→個別承認フローに統一する。

### 5.10 プロット逸脱・間延び指摘／矛盾検知
- プロット逸脱・間延び：`plot.md`（特にあらすじ箇条書き）と該当話の本文を比較し、「プロットに記載のない展開」「テンポが停滞していると推定される箇所」を指摘。
- 矛盾検知：登場人物一覧・場所一覧・世界観まとめ（＝これまでの生成済み設定）と本文の記述を突合し、設定と矛盾する記述を検出。差分処理の仕組み上、チェック範囲は「新規/変更チャンク」を基本とし、必要に応じて「全文チェック」も選択可能にする。
- いずれも結果は5.8と同じ「AI指摘パネル」に統合表示するが、指摘カテゴリ（誤字脱字／推敲／逸脱・間延び／矛盾）でタブ分けする。

### 5.11 AI指摘パネル（共通UI）
- 独立したWebViewPanelとして実装し、別ディスプレイへ配置可能にする（2.3節参照）。
- 指摘一覧は「該当ファイル・行範囲へのジャンプリンク」「指摘理由」「AIによる修正案（該当機能のみ）」「承認／却下ボタン」を持つ。
- 承認済み・却下済みの履歴は `.aiwriter/logs/ai_actions.log` に保存し、あとから見返せるようにする。

### 5.12 MDファイルのルビ機能
- 独自記法 `{漢字|かんじ}` を採用（Markdown拡張として一般的な形式）。
- VSCode上ではプレビュー（既存Markdownプレビュー拡張、または独自WebViewプレビュー）で `<ruby>漢字<rt>かんじ</rt></ruby>` としてレンダリング。
- txtファイルはルビ機能対象外（要求仕様どおり）。
- 提案：カクヨム記法（`｜漢字《かんじ》`）、なろう記法との相互変換コマンドを用意し、投稿サイトへのコピペを容易にする。

### 5.14 設定資料エクスポート（外部提供用）

コミカライズ・映像化・アンソロジー等で、制作関係者へ設定資料を渡す必要がある。内部データ（JSON）はそのままでは読めないため、**人間が読むための文書**として書き出す機能を独立して用意する。

#### 5.14.1 出力可能な資料の種類

| 資料 | 内容 | 主な用途 |
|---|---|---|
| キャラクター設定資料 | 人物ごとに1〜2ページ。アイコン、読み仮名、役割、外見、性格、行動原理、一人称、口調、登場話数 | 作画・キャスティング |
| 呼称表 | 誰が誰をどう呼ぶかのマトリクス＋変化タイムライン | **演技・脚本で特に重要** |
| 人物相関図 | 関係性を図示（Mermaid / SVG） | 全体把握 |
| 世界観設定資料 | ジャンル、時代、世界法則、社会構造、文化、地理 | 美術・設定考証 |
| 場所・舞台設定資料 | 地域別の場所一覧、描写、登場話数 | 背景作画・ロケーション |
| 用語集 | 作品固有の造語・専門用語と読み仮名、意味 | 全体（表記統一） |
| 年表・時系列表 | 作中の出来事を時系列で整理 | 脚本・構成 |
| あらすじ集 | 全話あらすじの一覧 | 全体把握 |
| プロット資料 | ログライン、テーマ、モチーフ、主人公の行動原理 | 企画・脚本 |

#### 5.14.2 出力形式

| 形式 | 用途 |
|---|---|
| **Word（.docx）** | 最も要望が多い想定。関係者が編集・コメントを入れられる |
| **PDF** | 版を固定して配布する場合 |
| Markdown | 社内Wiki等へ転記する場合 |
| HTML（画像埋め込み単一ファイル） | ブラウザで閲覧、リンク共有 |
| CSV / Excel | キャラクター一覧、呼称表など表形式データの二次利用 |

Wordは画像（キャラクターアイコン）と表を含められ、受け取り側が最も扱いやすいため既定とする。

#### 5.14.3 対象者別プリセット

渡す相手によって必要な情報が異なるため、プリセットを用意する。

| プリセット | 含める内容 | 除外する内容 |
|---|---|---|
| **コミカライズ向け** | 外見描写、アイコン、場所の視覚的描写、相関図、年齢・体格 | 内面の細かい設定、未公開の伏線 |
| **映像化向け** | 読み仮名、一人称、二人称・呼称表、口調、性格、相関図 | 背景美術の細部 |
| **翻訳者向け** | 固有名詞の読み仮名とローマ字表記、用語集、呼称表、敬称の使い分け | 制作進行情報 |
| **全体資料（社内用）** | すべて | 作者メモのみ除外 |
| カスタム | 資料単位・項目単位で任意選択 | — |

呼称表を映像化向けに必須としているのは、日本語作品では呼び方が関係性を直接示すためで、脚本や演技指示に直結する。翻訳者向けでも同様に重要になる。

#### 5.14.4 ネタバレ範囲の制御（重要）

連載中の作品を渡す場合、**先の展開を伏せた資料**が必要になる。

- 出力時に「第N話時点の設定」を指定できる。指定すると、`first_chapter > N` の情報（未登場人物、未使用の呼称、後から明かされる設定）を除外する。
- 各データに `spoiler_level`（`public` / `staff_only` / `author_only`）を付与できるようにし、プリセットごとに出力範囲を決める。
- `author_only` に指定された情報（結末、真犯人、キャラクターの正体など）は、明示的に解除しない限りどの出力にも含めない。
- 除外が発生した場合、資料の末尾に「一部の設定は本資料の対象範囲外です」と注記を入れる（受け取り側が「情報が足りない」のか「意図的に伏せている」のか判断できるように）。

#### 5.14.5 データモデルへの追加

外部提供のために、以下のフィールドを追加する。

```json
{
  "name": "月島 灯",
  "reading": "つきしま あかり",          // 読み仮名（映像化・翻訳で必須）
  "romaji": "Tsukishima Akari",         // 翻訳者向け
  "physical": {                          // コミカライズ向け。任意項目
    "age": "17",
    "height": "168cm",
    "build": "痩せ型",
    "hair": "黒・ショート",
    "eyes": "暗褐色",
    "distinctive": "左目に古傷"
  },
  "speech_style": "丁寧語が基本。動揺すると素が出て砕ける",
  "spoiler_level": "public",
  "export_note": "作画時、左目の傷は前髪で隠れる場面が多い"  // 資料にのみ出力
}
```

- `reading` は名前だけでなく、場所名・用語にも持たせる。読み方が分からない造語は、制作現場で確実に問題になる。
- `export_note` は本文執筆には不要だが、外部に伝えたい補足を書く欄。内部UIでは折りたたみ表示とする。
- `physical` は任意。空欄でも出力は成立させ、AIによる自動補完（本文の描写からの抽出）も可能とする。

#### 5.14.6 版管理と差分出力

設定資料は一度渡して終わりではなく、連載進行に伴って更新される。受け取り側が「どこが変わったか」を追えるようにする。

- 出力時に版番号（`v1.0`, `v1.1`...）と出力日を自動付与し、表紙・ヘッダーに記載する。
- 出力時のデータスナップショットを `.aiwriter/exports/` に保存する。
- 次回出力時、前回版との**差分レポート**を併せて生成できる（「新規追加：3名／変更：5件／削除：0件」＋変更箇所の一覧）。
- 差分レポートは単独でも出力でき、「前回お渡しした資料からの変更点」として送付できる。

これがないと、関係者は毎回100ページの資料を読み直すことになる。

#### 5.14.7 出力の実行

- コマンド「設定資料を書き出す」でウィザードを起動する。
  1. プリセット選択（またはカスタム）
  2. 含める資料の選択（チェックボックス）
  3. ネタバレ範囲の指定（第N話時点 / 全編）
  4. 出力形式の選択
  5. プレビュー確認 → 出力
- 出力先は既定で `作品フォルダ/exports/`。Git同期対象からは除外する（成果物であり、容量も大きくなるため）。
- 表紙には作品タイトル、資料種別、版番号、出力日、作者名、「取扱注意」等の注記を入れる。注記文面はテンプレートで編集可能とする。

#### 5.14.8 テンプレート

**現時点で提供先・指定フォーマットは未定である。** そのため、テンプレートの作り込みは行わず、以下の方針とする。

- 初期実装では**汎用テンプレート1種のみ**を同梱する。項目を見出しと表で素直に並べた、可読性優先のレイアウトとする。
- 対象者別プリセット（5.14.3）は「どの項目を含めるか」の選択フィルタとしてのみ実装する。レイアウトはプリセット間で共通とする。
- 出力レイアウトはテンプレートファイル（Markdown + 変数展開、Word出力時はdocxテンプレート）で定義し、後から追加・差し替えできる構造にしておく。
- 指定フォーマットが判明した時点で、そのテンプレートを追加する。**この時、データ側の変更は不要**であることを設計上の要件とする。

つまり、いま作り込むべきはテンプレートではなく**データの網羅性**である。読み仮名、外見の構造化項目、呼称、`spoiler_level` といったフィールドを最初から持たせておけば、どんなフォーマットが来ても再抽出せずに出力できる。逆に、これらのデータを持たずに執筆を進めると、提供が決まった時点で全話を読み直すことになる。

#### 5.14.9 未定事項への対応方針

| 項目 | 現時点の扱い | 判明後の対応 |
|---|---|---|
| 提供先 | 未定 | プリセットの項目選択を調整するのみ |
| 指定フォーマット | なし | テンプレートを追加。データ変更は不要 |
| 出力形式の優先度 | Word を既定、他は同時実装 | 不要な形式があれば削らず残す（コストが低いため） |
| ネタバレ範囲 | 全編出力を既定 | 提供時に第N話時点を指定 |

エクスポート機能は開発フェーズ5に配置しており、実際に必要になるまで着手を遅らせられる。ただし**データモデル側（5.14.5）はフェーズ1のキャラクター管理実装時に含める**。後付けすると既存作品の再解析が必要になるため。

### 5.15 Git自動同期

**前提**：リモート（GitHub）側が別環境から更新されている可能性が常にある（3.5節）。したがって「コミットして push するだけ」では成立しない。

#### 同期の手順

```
1. ローカルの未保存ファイルを確認     → あれば保存を促す
2. 競合マーカーの残存を確認          → あれば同期を中止（3.5.1）
3. リモートの更新を取得（fetch）
4. リモートが進んでいるか判定
   - 進んでいない → 6へ
   - 進んでいる   → 5へ
5. pull（既定は --rebase なしのmerge）
   - 競合なし → 変更ファイルを再走査（3.5.5）して6へ
   - 競合あり → 同期を中止し、作者に通知。自動解決はしない
6. 変更内容からコミットメッセージを生成してコミット
7. push
   - 失敗（non-fast-forward）→ 3へ戻る（最大2回まで）。
     それでも失敗したら中止して通知
```

**自動での競合解決は行わない。** 原稿の競合をツールが機械的に解決すると、どちらの文章が消えたか作者が気づけない。競合が起きた時点で手を止め、作者に判断してもらう。

#### 自動同期の既定

- `git.autoSync` がtrueの場合も、**pushは即時ではなく一定間隔でまとめて実行**する（既定5分、または明示的な同期コマンド実行時）。保存のたびにpushすると、リモートとの往復が頻発して競合の機会が増えるため。
- 執筆中（直近30秒以内に編集がある）は同期を延期する。作業を中断させないため。
- falseの場合はローカルコミットのみに留め、pushは手動コマンドで実行。

#### 同期対象の整理

| 対象 | 既定 | 理由 |
|---|---|---|
| 本文ファイル | 同期する | 主目的 |
| `設定/` 配下 | 同期する | 1エンティティ1ファイルに分割済み（3.5.2） |
| `.aiwriter/config.json` | 同期する | 作品設定。APIキーは含まない |
| `.aiwriter/stats/` | 同期する | 端末ごとにファイル分離済み（3.5.3） |
| `.aiwriter/cache/` | 選択制 | 複数PC運用なら同期すると再処理を省ける（3.5.4） |
| `.aiwriter/logs/` | 同期しない | ローカルの作業記録 |
| `exports/` | 同期しない | 再生成可能な成果物 |
- `.aiwriter/`配下（キャッシュ・ログ）はデフォルトで `.gitignore` 対象とし、設定・本文・生成済み設定一覧のみを同期対象とする（キャッシュはローカル最適化用のため）。
- `exports/`（設定資料の出力先）も既定で同期対象外とする。生成物であり再出力可能なため。ただし「関係者へ渡した版を記録として残したい」需要もあるため、設定で同期対象に含められるようにする。
- 除外設定はプロジェクトごとにカスタマイズ可能にする。

## 6. AIプロバイダ選択・抽象化層

### 6.1 設計方針

**「1つだけ使う」を標準ケースとして設計する。** 3種類の併用は最適化オプションであり、前提条件ではない。この方針から以下が導かれる。

- 未設定のプロバイダは、UI上の選択肢に一切現れない
- 1つも設定されていない状態でAI機能を呼び出した場合、エラーではなくセットアップ画面へ誘導する
- 機能別割当は既定でOFF。設定画面の初期表示は「使用するAI」の1項目のみ
- プロバイダを後から追加・変更しても、生成済みデータは引き続き利用できる（プロバイダ非依存のデータ形式）

### 6.2 設定の階層

設定は2階層とし、作品ごとの独立性を保ちつつ、毎回設定し直す手間をなくす。

```
グローバル設定（VSCode settings / SecretStorage）
  ├─ 登録済みプロバイダとAPIキー          ← 全作品で共有
  └─ 既定のプロバイダ・モデル              ← 新規作品作成時の初期値
        ↓ 継承
作品ごとの設定（.aiwriter/config.json）
  └─ この作品で使うプロバイダ・モデル       ← 未指定ならグローバル既定を継承
```

作品Aは無料のOllama、作品B（本命作）はClaude、といった使い分けが可能。作品側で何も指定しなければグローバル既定に従う。

### 6.3 初回セットアップウィザード

拡張機能の初回起動時、または未設定でAI機能を呼び出した際に表示する。

```
ステップ1：使用するAIを選んでください（1つで構いません）
  ○ Claude（Anthropic）      … 文章の分析・校正の精度が高い。API課金あり
  ○ Gemini（Google）         … 長文の一括処理に強い。無料枠あり
  ○ Ollama（ローカル実行）    … 無料・オフライン可。要ローカル環境

ステップ2：接続情報の入力
  - Claude / Gemini … APIキーを入力（SecretStorageへ暗号化保存）
  - Ollama          … エンドポイントURL（既定 http://localhost:11434）

ステップ3：接続テスト
  - 実際に短いリクエストを送信し、疎通と応答を確認
  - Ollamaの場合は導入済みモデル一覧を取得して選択肢に表示

ステップ4：モデル選択
  - プロバイダごとの利用可能モデルから選択（既定値を推奨として提示）

  ［後で他のAIを追加することもできます］
```

### 6.4 プロバイダ抽象化インターフェース

```typescript
type ProviderId = "gemini" | "claude" | "ollama";

interface AIProvider {
  id: ProviderId;
  /** APIキー等が設定済みで、実際に呼び出せる状態か */
  isConfigured(): Promise<boolean>;
  /** 疎通確認。セットアップウィザードと設定変更時に使用 */
  testConnection(): Promise<{ ok: boolean; message: string }>;
  /** 利用可能なモデル一覧。Ollamaは導入済みモデルを動的取得 */
  listModels(): Promise<ModelInfo[]>;
  generate(params: GenerateParams): Promise<GenerateResult>;
}

interface ModelInfo {
  id: string;
  displayName: string;
  contextWindow: number;      // チャンクサイズ自動決定に使用
  capabilityTier: "high" | "standard" | "light";
  supportsJsonMode: boolean;  // 構造化出力の可否
  costPer1MTokens?: { input: number; output: number }; // Ollamaはundefined
}

interface GenerateParams {
  systemPrompt: string;
  userPrompt: string;
  model: string;
  temperature: number;
  maxTokens?: number;
  jsonMode?: boolean;
  signal?: AbortSignal;       // 処理中断用
}

interface GenerateResult {
  text: string;
  usage?: { inputTokens: number; outputTokens: number };
  finishReason: "stop" | "length" | "error";
}
```

呼び出し側（各AI機能）はプロバイダを意識しない。`AIRouter` が設定を解決して適切なAdapterへ振り分ける。

```typescript
class AIRouter {
  /** 機能IDから、実際に使用するプロバイダとモデルを解決する */
  async resolve(featureId: string): Promise<{ provider: AIProvider; model: string }> {
    // 1. mode === "per-feature" かつ overrides に該当機能があればそれを使用
    // 2. なければ作品設定の default を使用
    // 3. 作品設定がなければグローバル既定を使用
    // 4. 解決したプロバイダが未設定ならフォールバック（6.5）
  }
}
```

### 6.5 フォールバックと設定不整合の扱い

想定される不整合と対応を定義しておく。

| 状況 | 挙動 |
|---|---|
| 機能別割当で指定したプロバイダが未設定 | 既定プロバイダで実行し、実行後に「○○が未設定のため△△で実行しました」と通知 |
| 既定プロバイダも未設定 | 処理を中断し、セットアップウィザードへ誘導 |
| APIキーが無効・期限切れ | 明確なエラーメッセージを表示し、設定画面への導線を出す。処理途中の場合は中間結果を保存 |
| Ollamaが起動していない | 「Ollamaが応答しません。起動を確認してください」と表示。ポーリング再試行はしない |
| 指定モデルが存在しない（Ollamaでpull未実施等） | 利用可能モデル一覧を提示して選択を促す |

**自動フォールバックは既定でOFF**とする。Ollamaのつもりが勝手にClaudeで実行されて課金される、という事態を避けるため。有効化する場合も、課金の発生しないプロバイダへのフォールバックのみを許可する設定を用意する。

### 6.6 モデル能力に応じた自動調整

単一プロバイダ運用では、選んだAIの能力に全機能が依存する。特にOllamaの軽量モデルのみを使う場合、そのままでは高度な機能（矛盾検知など）が実用に耐えない。そこで `capabilityTier` に応じて処理側を自動調整する。

| 調整項目 | high（Claude / Gemini Pro） | standard | light（Ollama軽量モデル） |
|---|---|---|---|
| プロンプト版 | 標準版 | 標準版 | 簡易版（短く、出力スキーマも浅く） |
| チャンクサイズ | 約2万字 | 約1万字 | 約4千字 |
| 出力形式の強制 | JSONモード使用 | JSONモード使用 | プレーン＋多段パース |
| 一度に扱う指摘件数 | 制限なし | 制限なし | 上限を設けて分割実行 |

加えて、light ティアでは矛盾検知・プロット逸脱検知の実行前に「このモデルでは精度が limited です」という注意を1度だけ表示する（毎回は出さない）。機能自体は禁止せず、期待値を伝えたうえで使えるようにする。

### 6.7 共通ミドルウェア

- プロンプトテンプレートは `prompts/` 配下で一元管理し、モデルを差し替えても同一テンプレートを再利用する（プロンプト設計書 第1部参照）
- レート制御、指数バックオフによるリトライ、タイムアウト、AbortSignalによる中断を全プロバイダ共通で実装
- トークン使用量とコストを記録し、統計パネルで可視化（Ollamaは0円と表示）

## 7. セキュリティ・APIキー管理
- Gemini/Claude APIキーは、平文の設定ファイルには保存せず、VSCodeの `SecretStorage` APIを利用して暗号化保存する。
- Ollamaはローカル通信のみのためキー管理不要。使用しないプロバイダのキーは登録不要で、未登録のまま全機能が動作する。
- `.aiwriter/config.json` にはプロバイダ・モデル名のみを保持し、キー自体は別管理とする。config.jsonはGit同期対象となるため、キーが混入しない構造にしておくことが重要。
- APIキーはグローバル（全作品共通）で保持する。作品ごとに登録し直す必要はない。

## 9. 既知の制約・要検討事項
- VSCode拡張の性質上、真の意味での「独立した複数ウィンドウ生成」はできず、WebViewパネルをユーザー操作で別ウィンドウへ移動する運用になります（2.3節）。
- 1000万字規模のリポジトリはGit運用上も肥大化しやすいため、Git LFSの利用検討、または `.aiwriter/cache` を除外する現行方針の徹底が重要です。
- キャラクターアイコンのAI自動生成（画像生成）は**将来の追加機能**として位置づけ、初期リリースでは外部画像ファイルの登録のみ対応します。データモデル上は将来の生成機能を見越したフィールドを先行定義済みです（5.5節）。
- Ollamaのモデル性能はクラウドAIに比べ変動が大きいため、矛盾検知・逸脱検知等の高度な分析はClaude/Geminiを既定推奨とし、Ollamaは誤字脱字検知等の軽量タスク向け既定とする想定です。
