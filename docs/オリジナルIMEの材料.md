# オリジナルIMEの材料

作者の依頼（2026-10-25 未明）「IMEの性能に満足がいかない場合は記録してください。後のオリジナルIME開発で使います」で作った欄。既存の日本語入力（MS-IME など）を使っていて、**小説を書く道具として不満が出た所**を、見た日・入力の種類・起きたこと・製品の側でどう逃げたかの順に1件ずつ置く。

- 置くのは、実機で見たもの・記録に残っているものだけ（推測は「見立て」と書き分ける）
- 製品の側で逃げ道を作れたものも残す（オリジナルIMEなら逃げ道が要らなくなる、という材料になる）
- 新しいものを下に足す

---

## 1. 名前を姓と名で分けて確定すると、まとまった名前として外へ知らせない（MS-IME、2026-10-24〜25）

- 作者の打ち方は「しらかば」→白樺で確定、「あかり」→灯で確定、と**姓と名を分けて確定する**。IME から拡張機能へ届くのは「しらかば→白樺」「あかり→灯」の2回の確定で、「白樺灯＝しらかばあかり」というまとまりはどこにも無い
- 製品の逃げ道：直前の確定のすぐ後ろへ続けて打った確定を、拡張機能の側でつないで名前と照らす（0.111.6〜0.111.7、設計書6.42.2）。位置と15秒の間で「続けて打ったか」を推し量っている
- オリジナルIMEなら：変換の区切り（文節）と読みを、確定のたびに外へそのまま渡せば、つなぐ推し量りが要らない

## 2. 確定の知らせの瞬間のカーソルが、IME の置いた形のまま（Windows の TSF、2026-10-24）

- 確定の知らせ（compositionend）の瞬間に選択範囲を読むと、確定した字が選ばれたまま・カーソルが行の要素の上、などの形で、字の直後に落ち着いていないことがある。画面の外の Chromium で偽の IME 入力を流すと再現しない（本物の TSF でだけ起きる）
- 同じ系統の記録（2026-08-24、引継ぎ書8章 その42、0.19.4）：Windows の日本語入力では、確定の知らせ（compositionend）が先に来て、確定した字の入力（input）があとから届く組み合わせがある。知らせの時点で本文を読むと、まだ確定前の中身になる
- 製品の逃げ道：位置は次の変換の始まり（compositionstart）で1回だけ読む（0.111.7）。直したかどうかは作者の打鍵でしか確かめられない
- オリジナルIMEなら：確定のあとにカーソルを字の直後へ置き終えてから知らせる、を約束できる

## 3. 打ち直しのあと、つながらないことがある（MS-IME、2026-10-25 未明）

- 作者が一度打ち直した回に、「灯」の直前の確定として、本文に残っていない「蓮」が届いていた（記録：前=蓮・始まりの直前の字は「　白樺」）。消した確定は IME からは「取り消し」として知らされないので、拡張機能は直前の確定を「蓮」のまま覚えていて、白樺と灯をつながなかった
- 同じ日の 23:49 には、作者が「すぐに灯で確定した」のに白樺と灯がつながらなかった回が1回ある（このときは診断の記録が無く、原因は分からない）
- 製品の側：誤ってつなぐより、つながない側に倒している（消した字はつながない）
- オリジナルIMEなら：確定した字が消されたことも知らせれば、ひとつ前の確定へ戻ってつなげる

## 4. 学習すると区切りが変わる（MS-IME、2026-10-25 未明）

- 「しらかばあかり」を何度か打つと、4回目には1回の変換で「白樺灯」と確定した（記録：かな=しらかばあかり 字=白樺灯）。同じ作者・同じ名前でも、日によって確定の回数が違う
- 製品の側：1回でまとまったときも、分けて確定したときも拾えるようにした
- オリジナルIMEなら：作品の設定資料にある名前と読みを辞書として最初から持てば、学習を待たずに1回で出る（いまは製品から MS-IME の辞書へ書き出す道がある。設計書6.13）
- 学習の向きは外から変えられない（設計書6.13.5）：ユーザー辞書は候補を増やせるが、「堅い／硬い／固い」のどれを先に出すかは指示できない。並べ替えは IME の学習の担当で、拡張機能からは届かない

## 5. 予測変換で選ぶと、読みが途中で切れる（入力の種類を問わない、2026-10-24）

- 「かん」まで打って候補から「漢字」を選ぶと、ページへ届くかなは「かん」まで。読みの全体は外へ出てこない（2026-10-24 の会話で整理した落とし穴。実機ではまだ見ていない）
- 1字の名前はとくに抜けやすい：「あ」と打って「灯」を選ぶと、「灯＝あ」の形になる（引継ぎ書8章 2026-10-24 夕【実装】0.111.4 の残る懸念）
- 製品の逃げ道：名前と完全に一致し、読みの字数が名前の形に合うときだけ採る。同じ名前に別の読みが来たら回数の多いほうを主にする（設計書6.42.2）。1字の名前は回数の多数決しか守りが無い
- オリジナルIMEなら：候補を選んだときも、その語の読み（辞書に載っている読み）をそのまま外へ渡せる

## 6. 変換を確定する Enter が、確定のあとにふつうの Enter として届く（Windows の日本語入力、2026-10-19）

- 作者の実機（2026-10-19 夜、0.110.0 の開発ホスト）：プロットモードの会話の欄で、変換を確定する Enter を1回押しただけで AI への送信が始まった（usage.md に plot_advice が3回、23:19:26・23:20:07・23:20:22）
- 確定の知らせ（compositionend）のあとに、「変換中ではない」「キーは Enter」の印で確定の Enter が届く。変換中かどうかの印（isComposing、keyCode 229）だけでは見分けられない
- 製品の逃げ道：確定の知らせのあと、Enter のキーが離れるのを見るまで（最長500ms）は Enter を受けない（`views/imeEnterGuardScript.ts`、設計書6.4.10。2026-10-21 作者と画面で確かめた）
- オリジナルIMEなら：確定に使ったキーを、確定のあとでアプリへ流さない

## 7. 変換中は、ファンクションキーと Ctrl+T を IME が使う（MS-IME、2026-10-03）

- 作者の実機（2026-10-03）：変換中に Ctrl+Alt+T を押すと「日本語がアルファベットになった」。MS-IME では変換中の Ctrl+T は「半角英数に変換」（F10 と同じ）。変換中の F8 も半角カナへの変換になり、メモへは飛ばなかった（引継ぎ書2章）
- 製品の逃げ道：F6・F7・F9・F10 は使わない。変換中の F8 は製品へ渡さない（設計書6.25 の F8 の項、`keyHoldImeF8`）
- オリジナルIMEなら：執筆の道具と取り合わないキーの割り当てを、最初から決められる

## 8. 縦書きの変換中の線が、行の左に出る（Chromium、2026-09-21〜10-19）

- 作者の報告（2026-09-21）「変換中左側に線がでます」。縦書きの傍線は行の右に引くのが決まりだが、CSS の指定（`text-underline-position: right`）は効かない（設計書6.25.2、0.19.4 で実機で確かめた）
- 2026-09-23 に作者が Chrome で4通りの枠（lang="ja"・lang="zh"・右の指定・textarea）を試し、4つとも左だった。変換中の字はページの中に直接出ていて、線を描いているのはブラウザ部品の側と見た（引継ぎ書8章。それより前の 6.25.2 は「日本語入力の層」と書いていた）
- 製品の逃げ道：変換中の字に背景色を置いた（0.74.10）が、横書きで色が字とずれ、作者「入力の反応がわずかに悪い気がするので、文字の変換時の色替えはいらない。やめましょう」（2026-09-24）で外した。作者は線の位置を許容している（2026-10-19「右に線を表示できたことはないと思います。許容しています」）
- 見立て：オリジナルIMEでも、ページの中に出る変換中の字の線はブラウザが描くので、IME の側から右へ動かせるかは分からない

## 9. VS Code の標準エディターでは、変換中の字も打鍵のたびに本文へ入る（MS-IME、2026-09-23）

- 作者の報告（2026-09-23）「VS Code の標準エディター、日本語IMEと相性が悪いかもしれません。変換時に入力が飛ぶ現象があります」。標準エディターでは変換中の字も打鍵ごとに本文の変更として届き、拡張機能の色付け（150ms 後に付け直し）が変換の途中に割り込んでいた（設計書の用語ハイライトの「打鍵と日本語入力」）
- 製品の逃げ道：打鍵が800ms 止まってから、変わったときだけ付け直す（0.76.2）
- オリジナルIMEなら：変換中の字を本文へ入れずに IME の側で持つか、アプリへ「いま変換中」を確かに知らせる

## 10. 選んだ文字の再変換が、ブラウザの上では使えない（Chromium、2026-08-27）

- 作者の依頼（2026-08-27）「文章範囲選択して再変換の機能も欲しいです」
- Windows の再変換（選んだ文字をもう一度変換する）は、Chromium がその仕組み（`ITfReconversion`）に対応していない。VS Code 本体の編集画面でも同じで、拡張機能から足せない（設計書6.25.6）
- 製品の側：代わりの案（AI に直させる・打ち直しの手数を減らす・IME 辞書）を並べたが、どれも再変換とは別物で、作っていない
- オリジナルIMEなら：確定した字と読みを IME の側で覚えておけば、アプリの対応を待たずに選び直せる（見立て）

## 記録で確かめた、既存のIMEの辞書と拡張機能の限り

出どころは設計書6.13（2026-08-15 の実データ5作品での実測を含む）と6.42.2。

- **拡張機能から変換中の字は見えない**：VS Code の API に変換中の字を扱う口が無い（型定義に `composition`・`preedit` 系が0件）。拾えるのは製品が自前で持つ原稿エディター（WebView）の中だけで、標準エディターでは拾えない（6.13.1・6.42.2）
- **ページに届く知らせ**：compositionstart／compositionupdate／compositionend は MS-IME・Google 日本語入力・ATOK のどれでも同じ道で届く、という前提で作った（6.42.2）。本物で見たのは MS-IME だけ（2026-10-24〜25）
- **読みはひらがなでないと取り込めない**（6.13.3）。カタカナの読みの行は弾かれ、作者からは「入れた語が出ない」としか見えない
- **形式**：MS-IME は UTF-16 LE（BOM 付き）・3列、Google 日本語入力は UTF-8・4列（4列目にコメント）、ATOK は Shift_JIS・3列で**未検証**（文字コード・品詞名・4列目の3点）。どれもタブ区切り・CRLF・末尾にも改行（6.13.4）
- **Shift_JIS で表せない字**：実測で「𠮷野」が落ち、`――`・`｜《》`・`……` は通った（6.13.4）
- **品詞**：組織の品詞が無く、組織・能力・造語はすべて「名詞」になる（6.13.2）
- **取り込みは作者の手作業**：MS-IME・Google 日本語入力・ATOK のどれも、外から辞書を流し込む正式な仕組みを公開していない（6.13.5）
- **作品ごとの辞書の切り替えはしない**：MS-IME の辞書一覧はレジストリ（`HKCU\Software\Microsoft\IME\15.0\IMEJP\Dictionaries`）に連番と有効・無効の旗があるが、公開されていない形式で、失敗すれば作者の日常の入力を壊す。実データでは作品をまたいで同じ読みが別の表記になる組は164読み中0件だった（6.13.5）
- **ふつうの日本語を辞書に入れると入力が悪くなる**：読みが無くて辞書に入らない語は506語中335語で、大半は「廊下」「学校」「父上」のようなふつうの語。人名・地名として登録すると普段の変換が悪くなるので入れない（6.13.2）
- **記号の辞書（品詞「短縮よみ」）は未検証**：短縮よみが通るか・記号を表記にできるか・表記の長さの上限・MS-IME で4列目が通るかを確かめる「段階0」が残っている（引継ぎ書8章「IME辞書の強化」）

## 会話で整理した既存のIMEの仕組み（2026-10-24。未検証）

母艦の会話で、作者の問いに答えて整理したもの。資料や実機で確かめてはいない。

- **IME の側で単独で分かること**：前面のアプリ（Code.exe など）と窓の題名（VS Code ならファイル名とフォルダー名）は分かる。入力欄の種類（InputScope）は VS Code の原稿では「ふつうの文」としか出ない。カーソルの前後の字は、VS Code の標準エディターでは今の行の近く数十字ほど。どの作品・何話・登場人物かは IME からは分からない
- **読みを取る道**：自前の Windows アプリなら IMM32 の `GCS_RESULTREADSTR`（確定した字の読み）や TSF の読みの属性（GUID_PROP_READING）で取れる。ただしアプリの中で呼ぶ必要があり、拡張機能からは届かない。ブラウザの中なら compositionupdate で「漢字に変わる直前のかな」を控えれば推せる（これを 6.42.2 で作った）。スマホのアプリには確定した字しか渡らない
- **推すときの落とし穴**：予測変換（5. の件）・文節の区切り直し（どの漢字がどの読みかは自分で推す）・再変換（かなの段を通らないことがある）。かな入力でもかなの段は届く。IME の種類で「いつ途中の字を送るか」が少しずつ違う
- **辞書の切り替え**：標準の MS-IME には作品やアプリごとの切り替えが無い（ユーザー辞書は1つ。IFEDictionary で単語の登録・削除はできる）。ATOK は辞書セットを持ててキーで切り替えられるが、「アプリに合わせて自動で切り替えられるかは、私には確かな情報がありません」と答えている。Google 日本語入力はユーザー辞書を複数持てるが、どれも同時に効く
- **連携の道の案**：①窓の題名で辞書を切り替える ②決まった場所のファイルで「いまの作品・話・辞書」を渡す ③辞書の書き出し（いまの製品の形） ④常駐のプロセスを1つ置き、名前付きパイプでつなぐ（本命の形） ⑤常駐役が MCP の客になって作品の材料を問い合わせる ⑥IME が「よく選び直す変換」を溜め、製品が作者に「辞書に足しますか」と聞く。IME の部品は各アプリの中で動き、打つたびに速く返す必要があるので、通信や AI はその中に置けない、という見立て
- **気をつけること**：IME はすべての打鍵を見るので、学習は手元で行いクラウドへ送らない。ブラウザ版（vscode.dev）では②④が使えない。Android の IME はアプリの名前とカーソルの前の字を取れるが、iOS のキーボードは使っているアプリを教えてもらえず、通信には「フルアクセス」の許可が要る
