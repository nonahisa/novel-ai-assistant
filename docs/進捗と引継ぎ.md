#### 2026-08-05 実接続テストの結果

「こちら冒険者ギルド生活保護課!!」（19話・約41,000字）で、実際にOllama（`gemma4:e4b`）を呼び出して登場人物抽出を実行した。

**テスト方法の注記**：VSCode拡張のUI（セットアップウィザード・進捗通知・確認ダイアログ）は未経由。`chunker.ts` / `characterExtract.ts` / `characterMerge.ts` / `models/character.ts` など`vscode`APIに依存しない部分は本物のコードをそのまま呼び出し、Ollamaへのリクエストも `ollamaProvider.ts` と同じパラメータ（`num_ctx`, `format`, `think: false` 等）で送った。`extractCharacters.ts` のオーケストレーション部分（進捗表示・キャンセル・確認ダイアログ）と `registry.ts` のセットアップウィザードはUI経由でしか検証できないため、**F5でのExtension Development Host起動によるテストは依然として未実施**。

**接続・実行結果**：
- Ollama接続：成功（モデル3件検出）
- 19チャンク中19件成功、失敗0件
- 所要時間：合計169秒、チャンクあたり平均8.9秒（最短4.8秒、最長15.1秒）
- 結果：登場人物37名を`設定/characters/*.json`に保存（新規37 / 更新13 / 要確認32件）

**見つかった品質課題**（想定通り、gemma4:e4bの精度限界が主因）：

1. **一人称が正式名として採用される**：主人公はケースワーカー「ホンゴー」だが、第1話の抽出で一人称「僕」が`name`として登録され、「ホンゴー」「ホンゴーさん」は逆にaliasとして格納された（`char_002_僕.json`）。
2. **敬称違いで別人物化する**：「シル」（`char_027`）と「シルさん」（`char_029`）が別レコードとして生成された。マージ処理はチャンクの処理順に依存しており、後の話数で敬称付き別名が判明しても、すでに確定した別レコードは統合されない（同様の例：「カッパー」/「カッパーさん」）。
3. **不正な`name`値がそのまま保存される**：`char_032`は`name: "null"`という文字列がそのまま人物名になっていた。`extractCharacters.ts`の`collect()`は`typeof c.name === "string" && c.name.trim()`しかチェックしておらず、"null"のような非空文字列は通過してしまう。
4. **集団名詞・汎用役職名が人物として登録される**：「取調官たち」「金貸したち」「冒険者」など、個人ではなく集団やその場限りの役割を指す語がそのまま人物レコード化された。

これらは「6. 設計で未確定のまま残している事項」や「5. 既知の課題」に記載していた懸念（8Bモデルの精度、話者取り違え）が実データで裏付けられた形。次のプロンプト調整（`CHARACTER_EXTRACT_VERSION`を上げること）の材料として使う。

#### 2026-08-05 課題3への対応：`collect()`に妥当性チェックを追加

上記3（不正な`name`値）に対応した。`extractCharacters.ts`の`collect()`に以下を追加：

- `name`が`"null"` `"不明"` `"なし"`等のプレースホルダー文字列と一致するものを除外
- `name`が30文字を超える（文章まるごとが入っている疑い）ものを除外
- `evidence`が本文中に見つからない（句点・改行区切りのいずれの断片も本文に存在しない）ものを除外。AIが単に`evidence`を書かなかっただけの場合まで弾かないよう、`evidence`が空・短すぎる場合は素通りさせる

**検証方法**：この修正はAIの応答そのものではなく事後フィルタなので、新規のAI呼び出しは行わず、前回実行時に保存済みのキャッシュ（`.aiwriter/cache/chunks.json`、生の抽出結果86件分）を読み直して`collect()`に通し直す形で検証した（`collect()`を`export`して再利用）。

**結果**：86件中2件を除外（`name: "null"`のレコード1件、および第10話で`evidence`が本文と一致しなかった「僕」の重複抽出1件）。登場人物数は37名→36名になった。「シル」/「シルさん」の別人物化、一人称「僕」が正式名になる問題、集団名詞の人物化（課題1・2・4）は今回は未対応、意図的に対象外とした。`設定/characters/`の内容はこの修正後の結果に更新済み。

課題1・2は「プロンプトを調整してAIの出力自体を改善する」方向、課題4（集団名詞）は「ネームドキャラとは別の『モブキャラ』カテゴリとして管理する」という設計案が出ている。いずれも未着手。

#### 2026-08-05 課題1・2への対応：敬称マッチング／承認制／プロンプト調整

課題1（一人称が正式名になる）・2（敬称違いで別人物化する）・役職名が本名と一体化する問題に対応した。

**実装1：敬称を無視した同一人物マッチング**（`characterMerge.ts`）
`normalizeName()`に敬称サフィックス（さん・くん・君・ちゃん・様・さま・殿・先輩・氏）の除去を追加。比較用の正規化にのみ使い、保存する`name`/`aliases`自体は元の表記のまま残す。合成データでのテストで「シル」/「シルさん」、「カッパー」/「カッパーさん」が1人にまとまることを確認。実データ再実行でも同様に統合された。

**実装2：プロンプトへの一人称除外ルール追加**（`CHARACTER_EXTRACT_VERSION: 1.0 → 1.1`）
「一人称・自称だけをnameにしない」ルールを追加したが、**実データで再検証した結果、8Bモデルはほぼ従わなかった**。第1話で「僕」が再びnameとして採用され、むしろ「ホンゴーさんの部下として派遣されました」という文章まるごとがaliasに紛れ込む等、改善しなかった。合わせて、次のチャンクに渡す「既知の登場人物」リストが今回抽出中の人物については`name`だけでaliasesを渡していないバグ（[extractCharacters.ts](src/features/extractCharacters.ts)の`knownNames`組み立て箇所）を発見。これにより「僕」「ホンゴーさん」「（主）」が同一人物なのに別レコードに分裂する現象が起きている。**この既知名リストの修正は未着手。**

**実装3：新規人物の承認制**（`extractCharacters.ts`）

#### 2026-08-07 実装5・6の実データ検証と`ungrounded`判定の是正

実装5（既知名リストのalias欠落修正）・実装6（`entityType`/`isMob`）を反映した状態で、19話を再実行した（gemma4:e4b、プロンプトv1.5）。

- 所要時間134秒（前回209秒）。出力量が減った分速くなっている。

**発見した不具合と修正：`ungrounded`判定が会話文と構造的に噛み合っていなかった**

初回の再実行で、実在する主要人物が11件も`ungrounded`（根拠なし）として除外された（グレイ、ホンゴー、ギルドマスター、ハルト、カーラーン等）。カーラーンは第15話のタイトル人物にもかかわらず最終一覧から消えていた。

診断スクリプトでAI出力を直接確認したところ、除外された候補のevidenceは**すべて正確な逐語引用**であり、落ちていたのは「引用の中に本人の名前が含まれない」という条件だった。

```
カーラーン の evidence:
「なぁホンゴーさん。来月分の保護費、前借りさせてくれよ」
→ 本文に存在: ○ / 名前を含む: ×
```

これはカーラーンの台詞である。**話者は自分の名前を自分の台詞で言わない**ため、会話する人物は構造的に必ず落ちる。実際、除外された引用にはすべて呼びかけられた側の「ホンゴーさん」が入っており、この判定は「地の文で名前を書かれた人物」しか通していなかった。

**修正**（[characterExtractionValidation.ts](src/core/characterExtractionValidation.ts)の`isGrounded`）：単一条件を2条件に分離した。

1. 呼称が本文に実在すること（名前の捏造を防ぐ）
2. evidenceの断片が本文に逐語で存在すること（引用の捏造を防ぐ）

引用が「その人物についてのものか」はコードでは判定できないため、捏造でないことの確認に留めた。捏造検出能力が落ちていないことは、「引用は本物で名前が本文にない場合」「名前は本物で引用が捏造の場合」「空白だけの引用」の3ケースをテストで固定して確認済み。既存の検証テスト32件は変更なしで通っている。

**あわせて文字化けの正規化を追加**：gemma系は全角スペースを`<0xE3><0x80><0x80>`というバイト表記のまま出力することがあり、逐語一致に失敗していた。照合時にバイト表記と空白の全角・半角差を無視するようにした。

**修正後の結果**：人物数19→25名、`ungrounded`除外11件→0件。除外は`invalid_name`（「僕」「（主）」）4件と`non_person`（「取調官」「冒険者」）2件のみとなり、いずれも正しい除外である。

**プロンプトのversionは上げていない**（v1.5のまま）。AIへの指示は変えておらず、受け取った結果の判定ロジックだけを直したため、キャッシュを無効化する必要がない。

- **`isMob`が0件で、実質デッドコードになっている。** `entityType`による`non_person`除外の方が先に効くため、モブは「別管理」ではなく「消滅」している。当初の「モブキャラも別枠で管理したい」という意図と食い違っており、扱いを決め直す必要がある。

#### 2026-08-07 省略形の統合候補・`isMob`の有効化・大規模作品の計測

**省略形の統合は「候補提示」に留めた**（[characterMerge.ts](src/core/characterMerge.ts)の`findMergeCandidates`）

「ギルドマスター」と「ギルマス」は敬称除去では吸収できない。カタカナの部分列（省略は語頭を残して文字を順に抜き出す形が多い）を手掛かりに候補を検出するが、**自動では統合しない**。統合し損ねるのは手間で済むが、別人を1人にまとめる誤統合は作者のデータを壊し、取り消しも難しいためである。抽出結果の要約に「同一人物かもしれない組」として提示する。

誤検出を避けるため、カタカナのみ・語頭一致・長さの比が2.5倍以内・部分列である、の全条件を課している。19話の実データに現れた18名で誤検出ゼロをテストで固定した（「グランス」と「グラックス」のような紛らわしい組も候補にしない）。

**`isMob`を有効化し、モブを集団名詞に限定した**（[characterExtractionValidation.ts](src/core/characterExtractionValidation.ts)）

`isMob`がデッドコードだった問題に対応。「兵士たち」のような**集団名詞のみ**を`isMob: true`として残し、除外しないようにした。

当初は`entityType: "group"`と汎用役職も対象にしようとしたが、品質ゲートが誤りを検出して方針を絞った。理由は2つ。

- `entityType: "group"`は「星環評議会」（組織）や「銀翼族」（種族）にも使われる。組織や種族はモブキャラではない。
- `GENERIC_ROLES`には「姉」「兄」「母」などの家族関係語が含まれる。これらは特定個人を関係で指す参照であり、群衆ではない。

品質ゲート（`characterExtractionQuality.test.ts`）は、モブを`falsePositives`の集計から除外しつつ、禁止名が**ネームドキャラとして**現れないことを引き続き検査する。あわせてモブが黙って失われていないことも検査する。

**大規模作品での性能を計測**（既知の課題「大量ファイルでの表示速度」に対応）

## 4. 設計上の重要な判断とその理由

実装時に「なぜこうなっているのか」で迷わないよう、判断の経緯を残す。

### マージをAIではなくコードで行う

設計書のP-04bではReduce段階もAIに任せる案だったが、実装ではコード側（`characterMerge.ts`）で行った。

理由：作者の加筆を確実に保護できる（AIの指示追従に依存しない）／同じ入力なら必ず同じ結果になる／AI呼び出しが減る。

AIには「本文から取り出す」ことだけをさせ、「既存データとどう統合するか」はコードが決める方針。

### 登場人物を1人1ファイルで保存する

`characters.json` ひとつだと、別環境で別々の人物を追記しただけでGitの競合が起きる。JSONは行単位マージと相性が悪い。

ファイル名に人名を含める（`char_001_月島灯.json`）のは、GitHubの差分画面やスマートフォンから見たときに何の変更か判別できるようにするため。

### 呼称を関係データとして持つ

`second_person: "君"` という単一フィールドでは、以下が表現できない。

- AがBを「白瀬さん」、BがAを「灯」と呼ぶ（非対称）
- 場面で変わる（平時「澪」／怒った時「白瀬」／人前「白瀬さん」）
- 関係の変化で変わる（第7話まで「白瀬さん」、第8話から「澪」）

そのため呼ぶ側のレコードに `addressTerms` として、相手ごと・呼び方ごとの二重配列で保持している。`status: past` を残すのは、過去の話を書き直すときに当時の呼び方を確認できるようにするため。

### 統計を端末ごとに分離する（未実装、設計のみ）

同じ日に2台で書くと「今日3000字」と「今日2500字」が必ず競合する。端末ごとにファイルを分け、読み込み時に合算する。書き込みは自分の端末のファイルのみなので構造上競合しない。

### 自動フォールバックを既定でOFFにする

Ollamaのつもりが勝手にClaudeで実行されて課金される事態を避けるため。
