## 1. この文書の範囲

この文書は統合小説執筆環境の**拡張機能（VS Code）と Android 版に共通する決まり**を1か所に集めたものである。作者の裁定（2026-10-25 夜）「設計書の整理が終わったら、拡張機能の設計書から共通設計書を切り出し、その上で Android 用の詳細設計書を作成する。テスト方法についてはこちらのやり方を踏襲する」に従って作った。

### 1.1 何がこの文書の正になるか

この文書が正になるのは、どの端末で動いても変わらない次のものである。

- 作者の原稿と作者のデータを守る決まり（2章）
- 作品フォルダーの形とデータの形（3章）
- AI の扱い（4章）
- 機能ごとの、端末を問わない決まり（5章）
- テストの分け方（6章）

### 1.2 ほかの文書に残すもの

| 文書 | 残すもの |
|---|---|
| `docs/設計書.md`（拡張機能の設計書） | 画面の作り、入口（コマンド・メニュー・右クリック）、VS Code の API の使い方、ブラウザ版の VS Code への対応（設計書 5.8）、配布（設計書 8.4） |
| Android の詳細設計書（これから書く。作業場は `novel-ai-android`） | 画面の作り、入口、Android と Capacitor の API の使い方、7章の未決の答え |
| `docs/プロンプト設計書.md` | **プロンプトの狙いと版。拡張機能と Android の両方の正である。** プロンプトの本文は `src/prompts/*.ts` にあり、食い違えば実装が正 |

この文書は詳しい決まりを書き写さない。設計書に詳しい節があるものは「詳しくは設計書 X.Y」と節番号で指す。2つの文書に同じことを書くと、片方だけ直す日が来て食い違うためである。

### 1.3 コードとの関係

型と定数の正は、いつもコードである。この文書に書いた名前（`writeTextFilePreservingFormat` など）は 2026-10-27 時点の `src/` で確かめた。コードの置き場は次のとおり。

- `src/models/`：データの型（VS Code に依存しない）
- `src/core/`：決まりの中身（大半は VS Code に依存しない）
- `src/ai/`：AI の接続（プロバイダ）
- `src/prompts/`：プロンプトの本文と版

Android 版の README の見積もりでは、`models`・`core`・`ai`・`prompts` の約2.3万行はそのまま持っていける。つまり、この文書の決まりの多くは**同じコードを使うことで守られる**。差し替えが要るのは、ファイルの読み書き（`core/paths.ts`・`core/textFile.ts`）、端末の識別（`core/device.ts`）、git（`core/git.ts`）など、端末の機能に触れる部品である。差し替えた部品もこの文書の決まりを守らなければならない。

## 2. 守る決まり

CLAUDE.md の実装ルール1〜7のうち、端末を問わない決まりをここに置く。全文と理由はスキル `implement`。ルール7（ブラウザ版の VS Code でも動く形で書く）は拡張機能だけの決まりなので設計書 5.8 に残す。ただしその考え方のうち「使えない操作は消さず、押せなくして理由を出す」は Android でも同じに守る。

### 2.1 作者の原稿を壊さない（ルール1）

いちばん優先する決まりである。詳しくは設計書 5.4.1・5.4.2・5.4.6・5.5.3。

- **書き戻す前にハッシュを照らし合わせる。** 読んだときのハッシュを控え、書く直前にもう一度計算する。食い違えば書かず、外で変わったことを知らせるだけにする（`modified_externally`）。「それでも書く」の道は置かない。AI の応答を待つ数十秒〜数分のあいだに外で足された文を、古い本文で消さないためである
- **文字コード・改行コード・末尾の改行を、読んだときのまま書き戻す。** 文字コードは UTF-8・BOM 付き UTF-8・Shift_JIS、改行は LF・CRLF・CR。勝手に UTF-8 や LF へ変えない
- **変わった箇所だけを置き換える。** 行全体やファイル全体を作り直さない。1文字直しただけで全行が変更扱いになると、git の差分が読めなくなる
- **本文の書き戻しは `writeTextFilePreservingFormat`（`core/textFile.ts`）を通す。** 書き換える前の本文を `.novelai-recovery` へ退避し（1ファイルにつき5世代。`RECOVERY_GENERATIONS_PER_FILE`）、そのあと新しく作る。退避先を返すので「元に戻す」を出せる
- **未保存の編集がある本文には、AI が直した文を当てない**（`unsaved_changes`）。字数を数えるときは、未保存の中身を優先する
- **git の競合の印（`<<<<<<<` など）を含むファイルは、AI に渡さない**（`conflict_markers`）。字数の計算からも外し、警告を出す
- **改行コードを揃えるのは作者が頼んだときだけ。** 保存でも同期でも AI の修正でも、改行を自動で変換しない（設計書 5.4.2）
- **設定資料の JSON も元のファイルの改行コードと末尾の改行で書く**（`core/jsonFileFormat.ts`）。新しく作るファイルは LF と末尾の改行
- **ファイルを握り続けない。** 読み書きは短く終え、ロックファイルは作らない。異常終了で残ると作者が対処できない（設計書 5.4.8）

### 2.2 作者が書いたデータを上書きしない（ルール2）

印の意味はどの種類の資料でも同じである。詳しくは設計書 5.2「作者のデータを守る印」と 6.18。

| 印 | 守り方 |
|---|---|
| `authorNotes`・`exportNote` | AI も自動の処理も書き換えない |
| `autoGenerated: false` | 作者（または編集部）が確定させた記録。AI は登場話数（`appearedChapters`）を足すことしかしない |
| `authorLocked: true` | その呼称（`addressTerms`）・場所の関係（`relations`）を抽出で変えない |
| `distinctFrom` | 作者が別人と決めた組。抽出のマージで1人にまとめない。記録も消さない |
| `rejectedRelations`・`rejectedValues`・`isProtagonist`・`dwellings` | 作者だけが付け外しする |

- **食い違いは話数で扱いを分ける。** 違う話の値どうしは作中の変化として `changes` に両方を残し、本体には最後の話の値を入れる。同じ話の中の矛盾と、話数の分かる値が1つしか無いときは `conflicts` に残して作者に決めてもらう。読み仮名は作中で変わらないので畳まない。どの道でも値は消えない
- **壊れた JSON は直さずに止める。** 読めないファイルを勝手に直したり、上書きしたりしない。エラーを出して作者に直してもらう（設計書 5.4.7）
- **書き込み口 `atomicWriteFile`（`core/atomicWrite.ts`）の3つの道を取り違えない。** 指定なしは上書き（場所・組織などの設定資料。外の変更は呼ぶ側のハッシュ照合で防ぐ）、`create` は新規だけ、`replace`＋`expectedHash` は必ず失敗する（直に呼ぶ処理を新しく作らない）。人物は `CharacterStore.saveOrUpdate()` で、本文と同じく退避してから作り直す
- **編集部の書いたものは作者の書いたものと同じに守る**（作者の判断、2026-08-19。設計書 5.5.0）。外で変わった資料に人が確定させた印を付けるのは、作者が［この変更を守る］を押したときだけにする。黙って付けると、ほかの AI の書いたものまで AI から守ることになる
- **外の書き換えは止めない**（設計書 5.4.9）。ファイルの中身そのものが作者のデータなので、書き戻すと作者のデータを上書きすることになる。できるのは、気づいて知らせ、確かめる場所へ案内することである

### 2.3 AI の出力を信用しない（ルール3）

- 字数の上限（サブタイトル15字、人物の紹介80字＝`SUMMARY_MAX_CHARS` など）は、コードで数え直す
- AI が指した本文の箇所が、本文に本当にあるかを照らし合わせてから使う。引用も同じ（4.6）
- **マージは AI でなくコードが行う。** AI には本文から取り出すことだけをさせる
- 同じ相手への別々の呼び方を、AI は1つにまとめたがる。プロンプトで禁じ、マージでもまとめない
- 指示の言葉がそのまま答えとして返ってくる前提で検査する（CLAUDE.md の失敗3。`"suggestion": "空文字"` が実際に返った）

### 2.4 処理量を節約する（ルール4）

- 本文はチャンクに分けて送り、結果をチャンクごとに控える。**控えの鍵は「プロンプトの版｜プロバイダID｜モデル名｜内容のハッシュ」**（`core/chunkCacheStore.ts` の `makeKey`）。プロバイダID を抜くと、名前の同じ別のプロバイダのモデルの結果を使ってしまう
- **プロンプトを変えたら、そのファイルの `_VERSION` を上げる。** 上げると、その機能の控えはすべて使われなくなる。版を上げる変更はまとめて入れる（プロンプト設計書 1.1）
- 版が上がっても、作り直しは自動で走らせない。走らせるのは作者が選んだときだけ
- 問いの分け方は相手で変える（設計書 6.103）。課金されるクラウドの高位の AI は手数を減らし（1回で多くを問う）、電気代だけの手元の AI は1回を軽くして回数で解く。控えはどちらにも効く。ただし矛盾検知では、分けても当たりが増えなかったので分けない（2026-09-19 の実測）

### 2.5 クラウドの AI の失敗の扱い（ルール5）

詳しくは設計書 7.8「拒否された指定を1つずつ外す」「失敗の種別の見分け方」。

- **覚えるのは通ったときだけ。** 失敗しただけで「この指定は使えない」と覚えると、原因が別（残高不足など）だったときに機能を失ったままになる
- **エラー文から原因を当てない。** 任意の指定を1つずつ外して試す（`ai/optionFallback.ts`）
- **HTTP 400 を「頼み方が悪い」と決めつけない。** Anthropic は残高不足も 400 で返す
- **エラーの本文を捨てない。** 通知が短くても、ログには種別と中身を残す。API キーらしい文字列は伏せる
- 失敗の種別（`AIError.kind`）ごとに、作者が次にできる操作を1つ示す（`recoveryForAIError`）
- **案内の文にサービス名を決め打ちしない。** 使っているプロバイダの表示名から引く。Gemini を使っているのに「Claude の…」と出た不具合が複数あった

### 2.6 手元の AI（ルール6）

拡張機能での決まりは次のとおり（Ollama。LM Studio は設計書 6.24）。

- `num_ctx` を必ず明示する。指定しないと短い既定で動き、入力が黙って切り捨てられる。送るたびに値を変えるとモデルを読み込み直すので、4096 の段に切り上げて揃える（設計書 6.53）
- `format` に JSON スキーマを渡して、答えの形を強いる
- `think: false` で思考を止める
- モデル名とコンテキスト長は API（`/api/tags`・`/api/show`）から取り、コードに書かない。同梱してよいのは「測らないと分からない値」の初期値だけで、API の値と作者の実測が常に勝つ（スキル `implement` のルール6の例外）

**Android で手元の AI をどう扱うかは、まだ決めていない（7章）。** README は「Ollama はスマホで動かない。パソコンの Ollama を LAN 越しに叩くか、クラウドの AI だけ」と書いている。どちらにするにしても、パソコンの Ollama を呼ぶなら上の4つはそのまま守る。

### 2.7 外部ツールとの共存（設計書 5.4）

本文と設定資料は、この製品以外のエディタ・執筆ソフト・投稿サイトからの取り込み・スマートフォン・ほかの AI からも書き換えられる。2.1・2.2 に加えて、次を守る。

- **外の変化に追従する。** 本文の変化は作品ごとにまとめてから、変わった作品だけを読み直す。AI の結果の控えは内容のハッシュが鍵なので、読み直しの影響を受けない（設計書 5.4.3）
- **本文が変わったら、前に出した指摘は古くなる。** 指摘は行番号だけでなく引用も持ち、当てるときは引用で探し直す。見つからなければ当てない（設計書 5.4.4）
- **話の参照は話数で持つ。** 無い話数を指していても、データから消さない。作者がファイルを一時的に動かしただけかもしれない（設計書 5.4.5）
- **`.aiwriter/` は製品の管理領域。** 外のツールが書くことは想定しない。壊れても作り直せるようにする（設計書 5.4.7）
- **`設定/` は作者やほかの AI が手で書いてよい場所。** 外の AI へは `設定/_schema/` の JSON Schema と日本語の注意書きで形と約束を渡す（`core/settingsSchema.ts`）。この製品が知らない鍵も持ったまま読み、書き戻しても消さない（設計書 5.4.9）
- **製品自身の書き込みと、外の書き込みを見分ける。** 書き込み口の1か所で印を付け、3秒以内の変化は自分のものとみなす（`SELF_WRITE_WINDOW_MS`）。外の変化の知らせはまとめて1回にする

### 2.8 GitHub 同期（設計書 5.5）

作者は同じ人のまま、複数の機械を渡り歩いて書く。編集部は別の GitHub アカウントで加わる。

**作者どうしの競合は事故であり、編集部との競合は起こさない。** 事故は解決より予防で防ぐ。編集部は本文を書き換えず提案として置くので、編集部との競合は構造として起きない（5.6。3.7）。対策は次の順で組む。

1. **そもそも競合させない**（設計書 5.5.1）。自動で行うのは取得（fetch）だけで、書いている途中に取り込み（pull）や送信（push）を勝手にしない。例外は2つで、機械を行き来する境目である「開いたときの点検」と、記録済みで送れていない分の送り直し。どちらも書きかけは巻き込まない。別の機械で進んでいれば、書き始める前に知らせる。未取得や送信待ちの警告は、消えない場所に出し続ける
2. **起きたら確実に気づかせる**（設計書 5.5.2・5.5.3）。どの機械がいつどのファイルを書いたかを、端末ごとのファイル（`.aiwriter/sessions/<端末ID>.json`）に残す。競合の印の入ったファイルは AI に渡さない
3. **決められるものは機械が決め、決まらないものは作者が選ぶ**（設計書 5.5.4・5.5.18）。設定資料は「作者が書いた部分」が両側で同じなら新しいほうへ揃える（`core/settingsConflictRule.ts`）。本文は git が別々の箇所を合わせ、同じ箇所だけを作者が選ぶ。原稿では「両方とも残す」を必ず用意する。同じ箇所を機械で結合しない

同期の形について、ほかに守ること。

- **単独の取り込みは早送り（`--ff-only`）だけ。** 合流の記録を勝手に作らない。未記録の変更があるときは、git に任せず先に止める
- **認証を訊かれても待たない。** 入力する手段が無いので、すぐ失敗させてログに残す
- **同期されるファイルには毎回変わる値（時刻・連番）を入れない。変わっていなければ書かない。** 作者が何もしない時間にリポジトリが育ち続けるため（設計書 5.5.8）
- **機械ごとの値は同期しない。** 端末IDは作品の外に持つ（拡張機能は VS Code の `globalState` の `novelai.deviceId`）。作品の中に置く MCP の登録（束への絶対パス）や外部 AI の利用許可などは `.gitignore` で外す（`core/workRegistry.ts` の `IGNORED_PATHS`。3.6）
- **git が改行を書き換える設定（Windows の `core.autocrlf`）は、こちらでは止められない。** 止められないことと止め方を伝える。できないことを、できるように見せない

### 2.9 鍵とログ（設計書 8 章）

- **API キーは平文の設定ファイル・`.aiwriter/config.json`・URL のクエリに置かない。** 端末の暗号化された保管場所に、全作品で共通に持つ（拡張機能は VS Code の `SecretStorage`。Android の置き場は7章）
- **ログでは実際に使っているキーの値を控えて伏せる**（`registerSecret`・`redactSecrets`）。接頭辞での見分けに頼らない。8文字未満の値は控えない
- **ログは同期しない**（`.aiwriter/logs/`）。原稿の一部が入りうるので、既定で7日を過ぎた行を消す（`novelai.logs.retentionDays`。設計書 8.3）
- **方針の違う記録を同じファイルに混ぜない。** 動作の記録（`actions.log`）は本文を書かない。相談の記録（`chat.md`）は本文を含む。送った量の記録（`usage.md`）は数字だけ（4.5）

## 3. データモデル

データの形は拡張機能と Android で同じにする。同じ作品フォルダーを GitHub 経由で両方から開くためである。型の正は `src/models/`、外部の AI に渡す形と約束の正は作品に書き出す `設定/_schema/`（`core/settingsSchema.ts`）。ここには骨組みと守る決まりだけを置き、欄の一覧は書き写さない。

### 3.1 作品フォルダーの形

作品フォルダーは次の3つに分かれる（設計書 5.1）。

| 置き場 | 中身 | 誰が書くか |
|---|---|---|
| `本文/`（無ければ作品フォルダーの直下） | 原稿（`.txt`・`.md`）。章フォルダーで分けてもよい | 作者。製品は 2.1 の決まりでだけ書き戻す |
| `設定/` | 設定資料・プロット・あらすじなど | 作者・AI・ほかのツール（2.7） |
| `.aiwriter/` | 製品の管理領域（作品の設定・控え・記録） | 製品だけ |

フォルダーの名前は作品ごとに変えられる（`.aiwriter/config.json` の `manuscriptDir`・`settingsDir`。既定は `本文`・`設定`）。

**本文の場所の決め方は1か所で決める**（`core/manuscriptFolderRule.ts`。設計書 5.1「本文の場所の決め方」）。git は空のフォルダーを運ばないので、空の `本文/` の有無で機械ごとに話の数が違って見えたためである。

1. `本文/` が無い、または同じ名前のファイルがある → 直下
2. `本文/` に原稿が1件でもある（章フォルダーの中でも可）→ `本文/`
3. `本文/` が空で、直下に原稿がある → 直下
4. どちらにも原稿が無い → `本文/`（登録したばかりの作品）

直下を本文として歩くときは、はっきり原稿でないと分かる名前（`README*`・`LICENSE*`・`CHANGELOG*`、AI への指示書など）だけを外す。外したファイルは件数を作者に知らせる。「メモ」「あとがき」のような名前は原稿でありうるので外さない。原稿を黙って数えから外すほうが、README を1つ余計に数えるより困るためである。

**ファイル名から話数を読む規則も共通である**（設計書 6.2。`001`・`007_題`・`003-005_合本`・`第12話 再会`・`episode_0001` など）。日付の名前を話数と読まない。

### 3.2 設定資料は1件1ファイル

`設定/` の中では資料1件を1つのファイルに分ける（設計書 5.5.5）。

| 置き場 | 中身 | 型 |
|---|---|---|
| `設定/characters/` | 登場人物（1人1ファイル） | `models/character.ts` |
| `設定/abilities/` | 能力 | `models/ability.ts` |
| `設定/organizations/` | 組織 | `models/organization.ts` |
| `設定/locations/` | 場所 | `models/location.ts` |
| `設定/world/` | 世界観（世界の法則・社会・文化・用語） | `models/world.ts` |
| `設定/foreshadows/` | 伏線（設定資料の種類には数えない。設計書 6.35） | `models/foreshadow.ts` |

1件1ファイルにする理由は2つある。

- **2つの機械で別々の人物を足しても競合しない。** 1つの大きな JSON は別々の人物を足しただけでも競合し、行ごとの合流とも相性が悪い
- **ファイル名で中身が分かる。** 名前は `char_001_月島灯.json` の形で、頭の ID と中身の `id` を一致させる。GitHub の差分画面やスマートフォンから見たときに、何の変更か分かるようにするため

作品に1つしか無い資料は1ファイルにする。`設定/ability_system.json`（能力の体系）、`設定/custom_fields.json`（作者が足した項目）、`設定/keep_words.json`（直さない語）などである。一覧だけの情報を置くなら `_index.json` に分け、実データを入れない。名前が `_` で始まるファイルは資料として読まない。

`設定/*.md`（設定資料集）と `設定/_schema/` は製品が作る読み物で、手で直しても次の生成で消える。直すなら JSON のほうを直す。

### 3.3 主要なデータの形

欄の一覧の正は `src/models/` の型である。見本は設計書 5.2 にある。ここでは種類ごとに、端末を問わず守る点だけを並べる。

| データ | 置き場 | 守る点 |
|---|---|---|
| 人物 | `設定/characters/` | 欄の名前はキャメルケース。紹介（`summary`）は80字まで（`SUMMARY_MAX_CHARS`）。性別は男女なら「男性」「女性」に揃え、知っている言い方だけをコードで直す（`core/gender.ts`）。呼称（`addressTerms`）は「この人物がほかの人物をどう呼ぶか」で、同じ相手への別々の呼び方をまとめない |
| 能力 | `設定/abilities/`・`設定/ability_system.json` | 能力の定義は人物から切り出し、人物は `abilityId` で指す。総称（魔法・スキルなど）は作品ごとに持つ |
| 組織 | `設定/organizations/` | 所属する人物は組織の側に持たず、人物の `affiliation` から引く |
| 場所 | `設定/locations/` | 地域は各場所の `region` で持つ。ほかの場所との位置関係（`relations`）は `within`・`adjacent`・`direction`・`distance` の4種類（設計書 6.93） |
| 世界観 | `設定/world/` | 物語の出来事を書かない。「城が燃えた」は出来事、「城は木造で燃えやすい」が世界観 |
| 作者が足した項目 | `設定/custom_fields.json` | キーは連番（`field_NNN`）で、見出しは別に持つ。外した項目のキーは使い回さず、値も消さない（設計書 5.2） |
| プロット | `設定/plot.md` | 作者が自由に書く Markdown。製品が読み書きする見出しは `core/plotDoc.ts` の `PLOT_SECTIONS`。作者が立てたほかの見出しは残し、消された見出しは戻さない |
| 作品紹介文・キャッチコピー | `設定/synopsis.md` | 設計書 6.6 |
| 各話あらすじ | `設定/chapter_synopses.json` | 設計書 6.6 |
| 作中の時間 | `設定/timeline.json` | 話数（書かれた順）と時系列（作中の順）を別の軸で持つ（設計書 6.18） |
| 読者像 | `設定/読者像.json` | 設計書 6.91・6.108 |
| 章立て・投稿の状態・スケジュール | `設定/章立て.json`・`設定/投稿状態.json`・`設定/スケジュール.json` | 設計書 6.66・6.68・6.111 |
| 作品ごとのメモ | `設定/メモ/` | 1メモ1ファイル（設計書 6.71） |
| 作品の設定 | `.aiwriter/config.json`（`WorkConfig`） | 同期されるので、機械ごとの絶対パスを持たない。省ける欄は省けるままにする（必須にすると今ある設定が読めなくなる）。**AI の選び方は置かない**（4.2） |

人物・能力・組織・場所・世界観の JSON は `schemaVersion` を持つ。作者のデータを守る印（`authorNotes`・`autoGenerated` など）は 2.2 のとおりで、どの種類でも意味は同じである。

### 3.4 統計は端末ごとに分ける

執筆量の記録は `.aiwriter/stats/<端末ID>.json` に、端末ごとに1ファイルで持つ（設計書 5.5.6。`core/writingStatsStore.ts`）。同じ日に2台で書くと、1つのファイルでは必ず競合するためである。

- 書き込むのは自分の端末のファイルだけ。読むときは全部を読み、日付ごとに足し合わせる（`mergeDailyStats`）。週・月・年は日ごとの記録から作る
- 同じ人の記録なので、足した値がその人の執筆量になる。統計は同期する
- 壊れたファイルは知らせずに読み飛ばす。同期の途中で競合の印が混ざることがあり、例外を投げると統計が開けなくなる
- 字数が変わらなければ書かない（2.8）

端末ID は同期しない（2.8）。同期すると全部の機械が同じ ID を名乗る。どの機械がいつ書いたかの記録（`.aiwriter/sessions/<端末ID>.json`）も同じ形で端末ごとに分ける（設計書 5.5.2）。

### 3.5 AI の結果の控え（キャッシュ）

- 控えは `.aiwriter/cache/chunks.json`。鍵は 2.4 のとおり（プロンプトの版｜プロバイダID｜モデル名｜内容のハッシュ）。拡張機能と MCP サーバー（別のプロセス）が同じファイルを使う
- 内容のハッシュが鍵なので、本文が変われば鍵から外れ、変わっていない話の結果はそのまま使える。読み直しや pull のあとに控えを捨てる処理は要らない（設計書 5.4.3・5.5.8）
- 控えは既定で同期しない。複数の機械で書く作者のために、同期する選択肢を持つ（設計書 5.5.7。拡張機能では `novelai.git.syncCache`、既定は切）
- 全文を横断して作る資料（人物・場所・世界観）は、変わったチャンクだけを読み直し、今ある一覧にコードでマージする。毎回全部を作り直さない（設計書 5.3）

### 3.6 同期するもの・しないもの

作品の `.gitignore` に足して外すものの正は `core/workRegistry.ts` の `IGNORED_PATHS`。2026-10-27 時点で外しているのは次のとおり。

| 外すもの | 理由 |
|---|---|
| `.aiwriter/cache/`（同期の選択肢あり） | 作り直せる。大きい |
| `.aiwriter/logs/` | 原稿の一部が入りうる（2.9） |
| `.aiwriter/exports/`・`exports/`・`.aiwriter/generated/` | 作り直せる読み物 |
| `.aiwriter/reports/` | 障害報告の記録。作者が貼ると決める前のもの（設計書 8.5） |
| `.aiwriter/external-access.json` | 外部 AI の利用許可。作者がその機械で与えるもの（設計書 6.87） |
| `.aiwriter/history/spotlight.jsonl`・`.aiwriter/ai-instruction-usage.json` | その機械の画面や使い方の控え |
| MCP の登録（`.mcp.json` など）と、束の絶対パスを書いた指示書 | 機械ごとに場所が違う |
| `.novelai-recovery/` | 書き換える前の退避先（2.1） |

それ以外の `.aiwriter/` の中身（作品の設定・承認待ち・提案・ロック・編集履歴・統計・端末ごとの記録）は同期する。外すものを足すときは、ここと `IGNORED_PATHS` の両方を見る。

### 3.7 編集部（設計書 5.6）

**編集部にできるのは本文の校正・校閲だけで、本文を書き換えない**（作者の判断、2026-08-19）。編集部の「適用」は本文に書かず、提案として置く。作者の許しなく本文が変わることが構造として起きず、編集部との競合も起きない。

| 記録 | 置き場 | 形 |
|---|---|---|
| 提案 | `.aiwriter/proposals/proposals.jsonl`（`core/proposalStore.ts`） | 1行1件の追記だけ。承認・却下も行を足して表す。決定は後から来たものが勝つ。同じ場所の同じ直しは同じ番号（`proposalId`）になる |
| 校閲のロック | `.aiwriter/locks/locks.jsonl`（`core/fileLockStore.ts`） | ファイル単位。取る・外すを積み重ねて表す。作者はいつでも外せる。24時間を過ぎたら外し忘れを疑う言い方を添える |
| 編集の履歴 | `.aiwriter/history/edits.jsonl`（`core/editHistory.ts`） | 1行1件の追記だけ。書き換えない・消さない。読めない行は捨て、読める行は残す |

- 採るときは、当てる直前に本文と照らし合わせる。合わなければ書き換えずに理由を出す
- 操作した人は作者・編集者・AI（作者が承諾したもの）の3種類で、色と記号の両方で分ける
- 「誰が」の名前は git の `user.name` に揃える。編集の履歴と競合の画面で同じ名前を出すため
- 編集者モードは許すものを並べて作る（禁じるものを並べると、機能を足したときに編集部へ開いてしまう）。戻る道を必ず残す。ロックは紳士協定で、ほかのエディタで書くことまでは止められない

### 3.8 書庫（設計書 5.7）

**1つのリポジトリに、同じ作者の作品フォルダーを並べて置く**（作者の判断、2026-08-21。呼び名「書庫」は 2026-08-22 に作者が命名）。取り寄せも同期も1回で済むためである。

- 書庫の直下に作品を並べるだけの浅い形にする。深く潜って探すと、設定フォルダーや章フォルダーまで作品として拾う
- 作品かどうかは `core/workCollection.ts` の `looksLikeWork` で見分ける。`.aiwriter/config.json` があれば作品。無ければ `本文`・`設定` のフォルダーの有無、それも無ければ直下に話数のファイルが並んでいるかを見る
- 「1フォルダー＝1作品」を前提にしない。登録の入口は、渡されたフォルダーが作品か書庫かを自分で見分ける
- 同期の相手は作品でなく置き場（リポジトリ）である
- **編集部には書庫を渡さない。** GitHub の権限はリポジトリ単位なので、書庫へ招くと全部の作品が読める。渡すときはその作品だけのリポジトリを切り出し、過去の履歴は渡さない（設計書 5.7.4・5.7.5）

## 4. AI の扱い

AI の扱いは設計書 7章とプロンプト設計書の第1部が詳しい。ここには、どの端末でも同じにする決まりを置く。プロンプトの本文・版・狙いの正はプロンプト設計書（1.2）。

### 4.1 プロバイダの抽象

**「1つだけ使う」を標準にする**（設計書 7.1）。全部の AI を用意する必要はなく、1つを選べば全機能が動く。使える AI は次のとおり（`ai/types.ts` の `ProviderId`）。

| `ProviderId` | AI | 場所 | 費用 |
|---|---|---|---|
| `ollama` | Ollama | 手元 | 無料 |
| `lmstudio` | LM Studio（OpenAI 互換の口） | 手元 | 無料 |
| `gemini` | Google Gemini | クラウド | 無料枠あり。超えると課金 |
| `sakura` | さくらの AI Engine（OpenAI 互換の口。国内） | クラウド | 無料枠あり。超えると課金 |
| `openai` | ChatGPT | クラウド | 送るたびに課金 |
| `claude` | Claude | クラウド | 送るたびに課金 |
| `vscode-lm` | VS Code の AI（`vscode.lm`） | — | 拡張機能だけ。Android には無い |

選ぶ画面には無料で始められるものから順に並べる。設定していない AI は選択肢に出さない。

**呼び出す側はプロバイダを意識しない**（設計書 7.4。型の正は `src/ai/types.ts`）。各プロバイダは `AIProvider`（`isConfigured`・`testConnection`・`listModels`・`generate`）を持つ。機能は `AIRegistry`（`ai/registry.ts`）の `resolve(機能)` で AI を受け取り、`generate` に `GenerateParams`（system と user のプロンプト・モデル・temperature・JSON スキーマ・出力の上限・中止の合図など）を渡す。各社の違いは各プロバイダの中で吸収し、機能の側へ出さない。

- **JSON スキーマの書き方の違い**は送る直前に変える（`ai/jsonSchema.ts`。設計書 7.8）。プロンプトの側は Ollama の形1つだけを持つ。スキーマを直に書き換えると版を上げることになり、控えがすべて使えなくなるためである
- **コンテキスト長は API から取る。** 申告しない AI（ChatGPT・さくら・LM Studio の古い版）は「AI チューニングで測った値 → 設定 → 同梱の実測 → 既定」の順に読む（`resolveContextWindow`。設計書 6.49）。実際より大きいと、入力が黙って切り捨てられる
- **モデルの地力（`capabilityTier`：high・standard・light）で変えるのは、プロンプトの指示の幅と一度に扱う指摘の数だけ**（設計書 7.6）。チャンクの大きさは tier で変えない（変えると全機能の控えが外れる）。light でも JSON スキーマを送る

### 4.2 機能別の AI の割り当て

機能ごとに別の AI を割り当てられる（設計書 6.28.9。プロンプト設計書 1.7）。割り当てられるのは11の機能である（`ASSIGNABLE_FEATURES`）。

> extract（設定資料の抽出）・typo（誤字脱字）・proofread（推敲）・contradiction（矛盾検知）・factExtract（場面の事実の抽出）・deviation（プロットからの逸脱）・foreshadow（伏線の検知）・generate（あらすじ・紹介文・キャッチコピーなど）・chat（AI に相談）・transcribe（写真の書き起こし）・readingDictionary（読み上げの読みの確かめ）

- **「割り当てを有効にする」の旗は作らない。** 割り当てが無い機能は既定の AI を使う。旗と中身の2か所が食い違うと、割り当てたのに効かない状態ができるため
- **既定の AI と割り当ては、作品ではなく端末に持つ**（拡張機能は `globalState` の `novelai.ai.provider`・`novelai.ai.model`・`novelai.ai.featureAssignments`）。作品の `config.json` には AI の選び方を置かない（設計書 5.2）。API キーの置き場は 2.9
- 手元の無料の AI と有料の AI を組み合わせて有料の量を減らす道は、この割り当てである（設計書 6.28）

### 4.3 落とし先（フォールバック）

| 起きたこと | 振る舞い（設計書 7.5） |
|---|---|
| 割り当てた AI が使えない（登録が無い、手元の AI が使えない環境） | 既定の AI へ落として実行し、ログに残す |
| 既定の AI も設定されていない | 止めて、AI を選ぶ画面へ案内する |
| 鍵が通らない・期限切れ | はっきりした文で知らせ、設定への道を出す |
| 手元の AI が動いていない | 起動を促す（設計書 6.51）。何度も叩き直さない |

**汎用の「自動で別の AI に切り替える」設定は作らない**（設計書 6.28.8）。気づかないうちに課金される入口になるためである。無料の AI へ落ちるときはそのまま実行し、有料の AI へ落ちるときは実行の前の確認（4.4）が必ず挟まる。使ったあとで「○○で実行しました」と知らせる形は採らない。

### 4.4 有料の AI を使う前に知らせる

**有料の AI を使う機能は、実行の前に料金がかかることを伝える**（作者の指示、2026-08-15。設計書 7.1.1）。無料（手元の AI）のときは何も出さない。

確かめる窓の本文は課金の機能に共通の3行にする（作者の裁定、2026-10-19）。組み立ては `core/paidUsageNotice.ts` の1か所。

```
Claude（有料）で送ります
送るもの：プロットと直近の会話（本文は送りません）
料金：送るたびに、使った量だけかかります
```

- 1行目のサービス名はプロバイダの表示名から作り、決め打ちしない。無料枠のある AI は「（無料枠あり・超えると有料）」と書く
- 本文を送る機能では、2行目に量（字数・話数）を必ず書く。作者が量を見て決めるためである
- まとめて処理する機能（抽出・誤字脱字など）は、量の行を3行に畳まない。料金の言い方だけを揃える
- 何度も押す画面（相談など）では、確認は一度だけ取り、有料であることを見える場所に出し続ける。AI を切り替えたら確認を取り直す

### 4.5 送る・待つ・記録する

**AI への送信は全体で1本ずつ並べる**（設計書 6.76。`core/aiSequence.ts`）。どの機能も送る直前の関所（`ai/meteredProvider.ts` の `MeteredProvider`）を通り、同時に送るのは1件だけ。チャンクを繰り返すまとまった処理は、始めに実行の札を取り、先の処理が終わるまで待つ。札を持ったまま関所を待ってよいが、関所を持ったまま札を待つ道は作らない。

**入らないものは送らない**（設計書 6.27.10）。プロンプトの実際の字数と出力の見込みが、モデルの上限を超えるときは送らずに `context_overflow` で返す。

**待ち時間の既定は300秒**（各 AI の `novelai.<プロバイダ>.timeoutSeconds`。2026-10-26 に全プロバイダで揃えた）。クラウドの AI の待ち時間の上限は既定600秒で、1800秒まで延ばせる（`novelai.cloudMaxTimeoutSeconds`）。手元の AI の上限は1800秒（package.json の設定の説明文による）。待ち時間は通信の部品にも渡す。渡さないと、Node の通信部品（undici）の既定の300秒で先に切れる（設計書 6.63。`ai/fetchTimeouts.ts`。Node だけの部品なので、Android での扱いは7章）。

**レート上限ではサーバーが示した時間だけ待って送り直す**（設計書 7.8。`features/rateLimitRetry.ts` の `callWithRateLimitWait`。置き場は features だが VS Code に依存しない）。

- 1回の待ちは示された時間より1秒長く、90秒まで（`MAX_RATE_LIMIT_WAIT_MS`）。示されなければ待たない
- 歯止めは回数でなく合計時間で、最後に通ってから180秒（`MAX_TOTAL_RATE_LIMIT_WAIT_MS`）。1回の待ちの長さはサーバーが決めるため
- 待つあいだは何秒待っているかを出し、諦めたときは合計で何秒待ったかを理由の頭に付ける

汎用の「間を空けて何度も叩き直す」再試行は持たない（設計書 7.7 の「指数バックオフによるリトライ」は、2026-10-27 時点のコードに見当たらない）。

**送った量は1回ごとに記録する**（`core/usageLog.ts`。`.aiwriter/logs/usage.md`。同期しない）。字数と機能名とトークン数だけで、本文は1文字も書かない。関所で送らなかった回も残す。何字送っているかは動かして測らないと分からないためである（設計書 6.27）。

**中止は AI まで届ける**（設計書 6.43）。中止のボタンを出すなら、同時に `GenerateParams.signal` へつなぐ。

**チャンクの中身が原因の失敗では全体を止めない。待っても直らない失敗では残りを試さない**（設計書 6.50）。鍵・権限・残高・モデルが載らない・レート上限（`isFatalProviderFailure`）は、そこで残りを止める。**一部が失敗したら「完了」と言わない**（設計書 6.47）。何チャンクを見られなかったかを出す。

### 4.6 AI の答えの検算

ルール3（2.3）の中身である。AI の答えは使う前に必ずコードで確かめる。確かめた結果は捨てるか、作者に判断を回すかのどちらかにし、黙って直して使わない。

| 確かめること | 例 |
|---|---|
| **字数** | サブタイトル15字、人物の紹介80字（`SUMMARY_MAX_CHARS`）。上限の数はプロンプトにも同じ定数から埋め込む（プロンプト設計書 1.1）。2か所に書くと必ずずれる |
| **本文への実在** | 抽出した名前は本文に出ているか。根拠の引用（`evidence`）は、句点などで区切った4字以上の断片のどれかが本文にそのまま出ているか（`core/groundedEvidence.ts` の `isGroundedInChunk`）。1つの文の中で離れた箇所をつないだ引用は本文に無いので落ちる。直しの案は、原文と同じ範囲を覆っているか（設計書 6.60） |
| **写しの一致** | 本文を切り分けて書き込むときは、つなぎ直したものが元と1文字も違わないかを確かめ、合わなければ書かない（設計書 6.2「書き込む前に検算する」） |
| **形** | JSON として読めるか、スキーマの形か。読めない答えは捨て、その回を失敗として数える。ログには抜粋に加えて総字数と最上位の鍵を残す（設計書 7.8） |
| **埋め草** | 「特になし」「なし」「空文字」のような答えは、項目として並べない（プロンプト設計書 1.9） |

ほめる言葉も AI の出力なので、引用が本文に実在しなければ落とす（プロンプト設計書 1.9）。助言の数がゼロでも失敗にしない。

**「見つける」機能では見逃しと誤検出の両方を測る**（CLAUDE.md の失敗2）。片方だけを測ると、何も指摘しない実装が満点になる。AI の出来が悪いときは、プロンプトのせいと決める前にモデルを替えて測る。測るときは製品と同じ検算を通す（CLAUDE.md の失敗5）。
